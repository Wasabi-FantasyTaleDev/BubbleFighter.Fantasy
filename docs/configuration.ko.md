Bubble Fighter Fantasy에는 고정된 서버 구성 요소 집합이 없습니다. `profiles/` 아래의 **프로필**이 실행할 플러그인 행, 제공할 클라이언트 빌드, 열 포트, 사용할 저장소를 결정합니다. 이 페이지는 프로필이 실행 중인 서버가 되는 과정, 구성 파일의 위치, 환경 변수와 포트의 동작 방식, 영속성과 클라이언트 데이터를 전환하는 방법을 설명합니다.

**대상 독자:** 서버가 실행하는 내용을 바꿔야 하는 운영자와, 시작 전에 실제 구성을 확인해야 하는 개발자입니다.

**시작하기 전에:**

- 서버를 한 번 빌드하십시오. `dotnet build BubbleFighter.Fantasy.sln -c Release`가 경고 0개로 끝나야 합니다. [설치](installation.md)를 참고하십시오.
- 저장소 루트에서 터미널을 여십시오. 이 페이지에서 `dotnet run`을 사용하는 명령은 현재 디렉터리가 저장소 루트라고 가정합니다. 프로필, 패킷, 클라이언트 데이터가 작업 디렉터리를 기준으로 확인되기 때문입니다.
- 실제 배포에서는 `.env.example`을 `.env`로 복사하십시오. MySQL을 비활성화하거나 메모리 또는 SQLite를 사용하는 점검에는 `BFF_MYSQL_*` 변수가 필요하지 않습니다. 실제 자격 증명을 커밋할 파일에 넣지 마십시오.
- 게임 빌드를 시작할 계획이라면 클라이언트 데이터를 준비하십시오. 저장소에는 포함되어 있지 않습니다. 이 페이지의 "클라이언트 데이터" 절을 참고하십시오.

## 설정 작동 방식

서버를 시작하는 방법은 두 가지입니다.

- `bff run --profile <id>`는 YAML 파일에서 프로필을 구성하고 그 행을 시작합니다. 아래의 모든 절은 이 경로를 설명합니다.
- `bff start`(실행 파일을 인수 없이 시작할 때도 사용)는 설치 도우미와 관리 행이 포함된 패키지된 최초 설치 프로필을 실행합니다. 이 경로는 저장소 `.env`를 의도적으로 읽지 않습니다. 이 페이지의 "환경 변수" 절을 참고하십시오.

### 구성 순서

프로필은 계층으로 구성되며, 뒤 계층이 앞 계층의 결과를 바꿉니다.

1. `profiles/<id>/profile.yaml`은 프로필 ID, 제공할 클라이언트 빌드, 사용할 번들, 자체 `vars`, 적용할 패치 파일을 선언합니다.
2. `profiles/bundles/<name>.yaml`의 각 번들이 파일 순서대로 플러그인 행을 제공합니다.
3. `patches:`에 나열된 순서대로 프로필의 패치 파일을 적용합니다. 빌드 프로필은 보통 자체 `patch.yaml`을 적용한 뒤 `profiles/bundles/shop-supplement-lucci.yaml` 같은 공용 보충 패치를 적용합니다.
4. 프로필이 `profiles/<id>/local.patch.yaml`을 나열하면 그 파일을 그다음에 적용합니다. 이 파일은 Git에서 제외되며 없으면 조용히 건너뛰므로, 개발자 재정의를 두기에 적합합니다.
5. 명령줄의 각 `--patch <file>`은 모든 프로필 패치 뒤에 주어진 순서대로 적용됩니다.
6. 문자열 값은 프로필의 `vars`와 프로세스 환경을 기준으로 보간됩니다. `--dump-config`가 최종 결과를 보여 줍니다.

명령줄 패치가 마지막에 적용되므로, 로컬 재정의 파일이 `persistence.mysql`을 특정 데이터베이스로 가리키더라도 명령줄 패치로 한 번의 실행에서 끌 수 있습니다.

### 플러그인 행

실행되는 모든 것은 **플러그인 행**입니다. 행은 플러그인 구현을 지정하고 설정을 전달합니다.

```yaml
- id: admin.http
  plugin: admin.http
  config:
    listen: "${BFF_ADMIN_HOST:-127.0.0.1}:${BFF_ADMIN_PORT:-7300}"
```

| 키 | 필수 | 의미 |
| --- | --- | --- |
| `id` | 예 | 패치와 관리 API가 사용하는 안정적인 행 식별자입니다. 한 프로필 안에서 고유합니다. |
| `plugin` | 예 | 플러그인 디렉터리에서 검색된 플러그인 구현 id입니다. |
| `config` | 아니오 | 플러그인의 옵션 형식에 바인딩되는 매핑입니다. 알 수 없는 키는 바인딩에 실패합니다. |
| `disabled` | 아니오 | `true`이면 행은 구성에 남지만 활성화되지 않습니다. 기본값은 `false`입니다. |

고급 행은 `parent_id`, `isolated_services`, `version`, `lifecycle`도 선언할 수 있습니다. 이 키들은 중첩, 빌드별 서비스 격리, 리소스 예산을 제어하며, 제공되는 프로필은 필요한 곳에 이미 설정해 두었습니다. 배포 설정이 아니라 프로필 정의의 일부로 취급하십시오.

서버는 목록 순서가 아니라 "필요한 서비스가 언제 사용 가능한지"에 따라 행을 활성화합니다. 활성화된 두 행이 같은 서비스 인터페이스를 게시할 수는 없습니다. 레지스트리가 두 번째 등록을 거부하기 때문입니다. 이 때문에 한 번에 하나의 영속성 공급자만 활성화되며, 저장소 전환은 런타임 스위치가 아니라 구성 변경입니다.

### 패치 작업

패치 파일은 단일 키 작업으로 이루어진 YAML 목록입니다.

| 작업 | 형식 | 효과 |
| --- | --- | --- |
| `replace` | `{id, plugin?, disabled?, config}` | 지정한 행을 교체합니다. 주어진 `config`는 행 구성 전체를 교체합니다. |
| `set` | `{id, config: {...}}` | 지정한 구성 키만 바꾸고 나머지는 유지합니다. `null` 값은 키를 제거합니다. |
| `insert` | 행 목록 | 새 행을 추가합니다. |
| `remove` | 행 id | 해당 행을 제거합니다. |

행이 없으면 `replace`와 `set`이 실패하고, 알 수 없는 작업은 구성을 실패시킵니다. 로컬 점검에 사용하는 메모리 격리 패치는 아주 작은 `replace` 패치입니다.

```yaml
- replace:
    id: persistence.mysql
    disabled: true
- replace:
    id: persistence.memory
    disabled: false
```

### 보간과 검증

`${VAR}`는 변수 값을 삽입하고 `${VAR:-default}`는 기본값을 제공합니다. 프로필의 `vars`와 프로세스 환경 모두 변수를 정의하지 않았고 기본값도 없으면 구성이 실패하며 파일, 행, 변수를 알려 줍니다. 프로필 자체 `vars`가 같은 이름의 환경 변수보다 우선하며, 비활성화된 행은 보간되지 않습니다.

구성 바인딩은 `snake_case` 키를 플러그인의 형식화된 옵션에 매핑합니다. 알 수 없는 키, 잘못된 형식, 범위를 벗어난 숫자, 옵션 검증 실패는 하나의 `Invalid configuration for row '<id>': ...` 오류로 함께 보고됩니다.

### 인벤토리 게시 제한

`dialect.messages` 행은 연결별로 인벤토리, 상점 상태 및 구형 과학실 완료 결과를 순서대로 게시합니다. `max_inventory_publications_per_connection`은 실행 중인 게시와 대기 호출의 합계를 제한합니다(기본값 `8`, 범위 `1..256`). `max_shop_sessions`는 시간 기준이나 승인된 게시를 보유한 연결 수를 제한합니다(기본값 `512`, 범위 `1..65536`). 폐기되었지만 아직 종료되지 않은 작업도 계산에 포함됩니다. 다른 연결은 독립적으로 게시할 수 있습니다. 어느 한도든 초과하면 대기 호출을 추가하지 않고 즉시 실패합니다.

연결 종료 또는 행 언로드는 대기 호출을 취소하고 진행 중인 준비를 무효화하므로, 지연된 호출이 이전 시간 기준을 다시 설치할 수 없습니다. 결정적인 인코딩 오류는 기존 시간 기준을 유지합니다. 전송 순서가 시작된 뒤 실패하면 해당 연결의 게시 상태를 폐기하고 연결 종료를 요청합니다. 이미 커밋된 인벤토리는 유지되며 정리 과정에서 비용을 다시 차감하거나 아이템을 다시 지급하지 않습니다. 대기 한도를 높여도 게시는 클라이언트 확인이나 데이터베이스 트랜잭션이 되지 않습니다.

## 파일 위치

| 경로 | 내용 |
| --- | --- |
| `profiles/<id>/profile.yaml` | 프로필 ID, 클라이언트 빌드, `parent`, 번들 목록, `vars`, 패치 목록입니다. |
| `profiles/<id>/patch.yaml` | `profile.yaml`에 나열된 프로필 자체 패치입니다. |
| `profiles/<id>/opcodes.yaml` | 해당 클라이언트 빌드의 이름 기반 opcode 표입니다. |
| `profiles/<id>/local.patch.yaml` | 선택 사항이며 Git에서 제외되는 개발자 재정의입니다. 있으면 자동으로 적용됩니다. |
| `profiles/bundles/*.yaml` | 프로필이 참조하는 공용 행 집합입니다. |
| `packets/*.yaml` | 패킷 레이아웃과 `builds.yaml`의 빌드 상속입니다. 시작 시 읽으며 컴파일되지 않습니다. |
| `.env` | 배포 변수입니다. Git에서 제외됩니다. |

Host 프로젝트는 `bootstrap/`, `profiles/`(`local.patch.yaml` 제외), `packets/`, 두 `data/` 파일(`data/level-experience.csv`, `data/locales/*.json`)을 빌드 및 게시 출력으로 복사합니다. 플러그인 어셈블리는 `plugins/<ProjectName>/` 아래에 게시되며, 이는 Host 옆의 기본 플러그인 루트입니다. 따라서 릴리스는 런타임, 클라이언트 데이터, MySQL 공급자를 사용할 때의 데이터베이스를 제외하면 자체 포함입니다.

행 안의 경로는 프로세스 작업 디렉터리를 기준으로 확인됩니다. `dotnet run`을 사용할 때는 저장소 루트에서, 게시된 Host를 사용할 때는 릴리스 디렉터리에서 실행하십시오. 다른 위치에서 시작하면 `--profiles-dir`를 전달해야 하며, `packets`와 `client-data` 경로는 여전히 작업 디렉터리를 기준으로 확인된다는 점에 유의하십시오.

## 실행 전 확인

현재 체크아웃이 제공하는 프로필과 검색된 플러그인 구현을 나열합니다.

```sh
dotnet run --project src/BubbleFighter.Fantasy.Host -c Release -- profiles list
dotnet run --project src/BubbleFighter.Fantasy.Host -c Release -- plugins list
```

`profiles list`는 각 줄에 프로필 id, 탭, 설명을 출력합니다. 이 릴리스에는 총 19개 프로필이 있습니다(클라이언트 빌드 프로필과 `all`, `management`, `setup`). `plugins list`는 플러그인 id, 버전, 지원하는 클라이언트 빌드, 출처를 출력합니다. `--plugin-root <dir>`(반복 가능)로 검색 위치를 다른 디렉터리로 지정할 수 있습니다.

서버를 시작하지 않고 실제 구성을 출력합니다. 실제 데이터베이스를 가리키는 개발자 `.env`나 `local.patch.yaml`에 접속하지 않도록 항상 메모리 격리 패치를 추가하십시오.

```sh
dotnet run --project src/BubbleFighter.Fantasy.Host -c Release -- run --profile kr-812 --patch tools/local-checks/isolated-memory.patch.yaml --dump-config
```

덤프는 각 행의 `id`, `plugin`, 행을 제공한 `source` 파일, 설정된 경우 `disabled`, 수명 주기 예산, 보간된 `config`를 나열합니다. 포트나 저장소를 바꾸기 전에 읽어 보십시오. 서버가 실제로 실행할 구성 그대로입니다. 구성이 실패하면 Host는 stderr에 `error: <message>`를 출력하고 종료 코드 1로 끝납니다. 메시지는 실패한 파일, 행, 키를 알려 줍니다.

## 환경 변수

### 로드 규칙

- `start`를 제외한 모든 명령은 먼저 작업 디렉터리에서, 다음으로 Host 디렉터리에서 위로 올라가며 `BubbleFighter.Fantasy.sln` 또는 `.git` 항목이 있는 저장소 루트를 찾습니다. 그곳에 `.env`가 있으면 아직 설정되지 않은 변수에만 값을 적용합니다.
- 이미 존재하는 프로세스 환경 변수가 우선합니다. `.env`는 빈 곳을 채울 뿐 셸이나 서비스 관리자를 덮어쓰지 않습니다.
- `start`는 저장소 `.env`를 절대 읽지 않습니다. 최초 설치 프로필은 프로세스 환경과 `--state-dir`에서 자체 변수를 받습니다.
- 파일은 UTF-8로 읽으며 크기 제한은 64 KiB입니다. 각 줄은 `KEY=VALUE`이고 `export KEY=VALUE`도 허용됩니다. 값은 따옴표로 감쌀 수 있고, 공백 뒤의 인용되지 않은 `#`은 주석을 시작하며, 형식이 잘못된 줄은 파일 경로와 줄 번호를 포함해 실패합니다. 값은 절대 로그에 남지 않습니다. 파일을 읽으면 콘솔에 `Loaded unset variables from <path>.`가 출력됩니다.
- 릴리스 디렉터리에는 솔루션 파일이나 `.git` 항목이 없으므로 게시된 Host 옆에 복사한 `.env`는 **읽지 않습니다**. 배포에서는 프로세스 환경, 서비스 관리자 또는 컨테이너 환경으로 변수를 설정하십시오.

### 자주 설정하는 변수

| 변수 | 용도 | 기본값 |
| --- | --- | --- |
| `BFF_BIND_HOST` | 게임 및 릴레이 리스너가 바인딩할 주소입니다. | `0.0.0.0` |
| `BFF_PUBLIC_HOST` | 클라이언트에 연결 및 릴레이용으로 알려 줄 주소입니다. | `127.0.0.1` |
| `BFF_ADMIN_HOST` / `BFF_ADMIN_PORT` | 관리 HTTP 바인딩 주소입니다. | `127.0.0.1` / `7300` |
| `BFF_LOG_LEVEL` | 콘솔 로그 수준: Trace, Debug, Information, Warning, Error, Critical, None. | `Information` |
| `BFF_LOG_FILE` | 선택적 Host 로그 파일. `--log-file`이 우선하며 미설정 시 파일 로깅이 꺼집니다. | 미설정 |
| `BFF_LOG_FILE_LEVEL` | 파일 로그 기준 수준. `--log-file-level`이 우선하며 콘솔과 같은 수준 이름을 사용합니다. | `Warning` |
| `BFF_LOG_FILE_MAX_BYTES` | 보관 파일 하나의 UTF-8 바이트 상한. 1024–1073741824. | `16777216` (16 MiB) |
| `BFF_LOG_FILE_COUNT` | 현재 파일을 포함한 보관 파일 수. 1–32. | `5` |
| `BFF_LOG_FILE_QUEUE_CAPACITY` | 쓰기 대기 기록 슬롯 수. 1–65536. | `256` |
| `BFF_LOG_FILE_MAX_QUEUED_BYTES` | 현재 쓰는 기록을 포함한 UTF-8 본문 바이트 예산. 1024–268435456. | `16777216` (16 MiB) |

| `BFF_SQLITE_DATABASE_PATH` | 패치가 SQLite 공급자를 활성화할 때 사용하는 절대 저장 파일 경로입니다. | 없음 |

## 포트와 주소

`BFF_BIND_HOST`는 서버가 수신 대기하는 인터페이스이고, `BFF_PUBLIC_HOST`는 서버가 클라이언트에 알려 주는 주소입니다. NAT 뒤에서는 두 값이 다를 수 있습니다. 클라이언트에 닿는 인터페이스에 바인딩하고, 클라이언트가 실제로 접근할 수 있는 공용 주소를 알리십시오. `BFF_PUBLIC_HOST`를 루프백 기본값으로 두는 것은 클라이언트가 같은 머신에서 실행될 때만 유효합니다.

리스너 포트는 보통 빌드별 변수와 `vars`를 통해 프로필에서 옵니다. 이 릴리스의 두 기준선은 다음과 같습니다.

| 엔드포인트 | kr-1256(모던) | kr-812(레거시) |
| --- | --- | --- |
| 게임 TCP | `7100`(`KR_1256_GAME_PORT`) | `7110`(`KR_812_GAME_PORT`) |
| 릴레이 TCP | `7101`(`KR_1256_RELAY_PORT`) | `7111`(`KR_812_RELAY_PORT`) |
| 관리 HTTP | `7300`(`BFF_ADMIN_PORT`) | `7300`(`BFF_ADMIN_PORT`), 동일한 하나의 WebUI |
| 선택적 네이티브 선택기 | 사용하지 않음 | `center-selector.yaml`을 마운트하면 `7112` |

`all` 프로필은 기동된 클라이언트 빌드를 하나의 프로세스로 구성하며, 각 빌드는 자체 게임 리스너를 사용합니다. 기본 게임 포트는 `7100`에서 10씩 증가합니다(`kr-1256` 7100, `kr-812` 7110, `id-400` 7120, `cn-408` 7250까지). 각 빌드의 릴레이는 게임 포트보다 1 큰 포트에서 수신합니다(`<BUILD>_RELAY_PORT`, 클라이언트에는 `<BUILD>_PUBLIC_RELAY_PORT`로 안내). 레거시 빌드는 릴레이가 연결되면 릴레이로 라운드를 진행하고, 실패하면 게임 연결로 돌아갑니다. `cn-706`과 `cn-705`는 릴레이 패킷이 감사되지 않아 라운드가 게임 연결에 남습니다. 방화벽 규칙을 열기 전에 `--dump-config`로 선택한 프로필의 정확한 `listen` 문자열을 확인하십시오.

관리 포트는 루프백이나 통제된 네트워크에 두십시오. 선택한 프로필이 제공하는 게임 및 릴레이 포트만 열고, MySQL은 공용 인터페이스에 노출하지 마십시오.

## 영속성

핵심 번들은 세 가지 영속성 행을 제공합니다.

| 행 | 지속성 | 사용 시점 |
| --- | --- | --- |
| `persistence.memory` | 프로세스 수명 동안만 유지되며 재시작 시 초기화됩니다. | 일회성 로컬 점검과 테스트. |
| `persistence.sqlite` | 로컬 저장 파일 하나입니다. | 데이터베이스 서버 없이 영속 데이터가 필요한 단일 호스트. |
| `persistence.mysql` | 외부 MySQL 데이터베이스입니다. | 실제 배포, 특히 여러 프로세스나 호스트를 사용할 때. |

한 번에 하나의 공급자만 활성화할 수 있습니다. 레지스트리가 같은 저장소 인터페이스의 두 번째 등록을 거부하므로, 같은 패치에서 하나만 활성화하고 나머지 둘을 비활성화해야 합니다. 핵심 번들에서는 MySQL 행이 활성화되어 있고 나머지 둘은 비활성화되어 있으며, 패치가 이를 전환합니다.

### 패치로 공급자 전환

기본 MySQL 구성에서 SQLite로 전환합니다.

```yaml
- replace:
    id: persistence.memory
    disabled: true
- replace:
    id: persistence.sqlite
    disabled: false
    config:
      database_path: "${BFF_SQLITE_DATABASE_PATH}"
```

MySQL로 돌아가려면 `persistence.mysql`을 `disabled: false`로 바꾸고 활성화한 다른 공급자를 비활성화하십시오.

### MySQL

기본 연결 문자열은 `BFF_MYSQL_*` 변수를 보간하고 `SslMode=none`을 고정합니다. TLS가 필요한 배포는 번들을 수정하지 말고 패치에서 `connection_string` 전체를 덮어쓰십시오.

행이 활성화되면 연결을 열고 `SELECT 1`을 실행합니다. 암호 누락, 잘못된 연결 문자열, 서버 접속 불가는 행을 실패시키며, 시작은 저장소 없이 계속 실행되는 대신 실패를 보고합니다. `auto_migrate`의 기본값은 `true`이며, 이때 플러그인이 내장 마이그레이션을 적용합니다.

- 마이그레이션 스크립트는 `NNNN_description.sql` 이름의 내장 리소스이며 파일 이름 순서로 적용됩니다. 이 릴리스의 최고 버전은 `0032`입니다.
- `schema_migrations`를 먼저 만들고(없는 경우), 이후 각 대기 버전이 자체 트랜잭션에서 실행되고 기록됩니다. 콘솔에는 `Applied migration <version> (<name>).`이 출력됩니다.
- 이름이 잘못되었거나, 버전이 중복되었거나, 내용이 빈 스크립트는 건너뛰지 않고 실행을 실패시킵니다.
- 마이그레이션은 **순방향 전용**입니다. 다운그레이드 경로가 없으므로, 이전 서버 바이너리는 새 릴리스가 마이그레이션한 데이터베이스에서 실행되지 못할 수 있습니다. 백업과 롤백 절차는 [배포](deployment.md)를 참고하십시오.

### SQLite

SQLite 행은 절대 `database_path`를 요구하며, 이 옵션은 상대 경로를 거부합니다. 릴리스를 교체해도 사라지지 않도록 파일을 릴리스 및 로그 디렉터리 밖에 두고, 실행 중인 두 서버가 하나의 저장 파일을 공유하지 않도록 하십시오. 이 행에는 플레이어 수, 계정 수, 데이터베이스 크기, 잠금 대기 한도도 있으며 같은 구성 매핑에서 설정할 수 있습니다.

메모리 공급자는 같은 저장소 인터페이스를 제공하는 경계가 정해진 프로세스 내 저장소입니다. 상태는 종료 시 사라지며, 이 행은 의도적으로 데이터베이스 팩토리를 게시하지 않습니다. 메모리와 MySQL은 상호 배타적입니다.

### 전적 기록

`ingame`의 `record_battle_statistics` 기본값은 `false`입니다. 활성화하려면 전적을 명시적으로 지원하는 진행 저장소, 레벨 표 및 공통 결과 전송기가 필요합니다. 승인된 버블, 팡, 도움, 사망 및 점수를 게임 모드별로 최종 결과와 함께 저장합니다. 진행 중 이탈은 탈주로 기록하며 완료 보상을 지급하지 않습니다. 완료 기록은 결과 화면을 보내기 전에 정산하므로 결과 화면에서 나가도 완료한 경기가 사라지지 않습니다. 로딩 실패와 취소된 경기는 결과를 만들지 않습니다.

Memory, MySQL 및 SQLite가 이 옵션을 지원합니다. MySQL 마이그레이션 `0039`는 `player_battle_records`를 추가하고 SQLite 스키마 `9`는 플레이어 스냅샷에 모드별 통계를 추가합니다. 두 영구 저장소는 통계, 진행 상태, 지갑 보상과 기존 경기 영수증을 하나의 트랜잭션으로 저장합니다. 데이터베이스를 다시 열어도 기록이 유지되며 같은 경기를 재시도해도 중복 누적되지 않습니다. 기존 영수증에 새 통계를 소급하여 추가하지 않습니다. 업그레이드 전에 저장소를 백업하세요. 이전 SQLite 판독기는 스키마 `9`를 거부합니다. 과거에 기록되지 않은 전적은 복원하지 않습니다. 모든 저장소의 `max_battle_modes_per_player` 기본값은 `128`이며 MySQL과 SQLite의 범위는 `1..4096`입니다. 모드 한도에 도달하면 기록을 제거하지 않고 새 정산 전체를 거부합니다. Memory는 임시 저장소이며 `max_battle_settlements_per_player`(기본값 `4096`)도 제공합니다. 영구 저장소는 기존 데이터베이스 경기 영수증을 유지합니다.

폭파 시리즈는 다음 라운드 로딩 중에도 하나의 경기 식별자와 누적 수치를 유지합니다. 이미 진행한 라운드 사이에서 상대 팀이 이탈하면, 다음 이탈이 결과 표시를 취소하기 전에 남은 최종 참가자를 기록합니다. 최초 로딩만으로는 경기가 성립하지 않습니다. 정산 재시도 횟수는 제한되며 최종 실패는 로그에 남습니다. 임의의 지속적인 저장 장애를 복구하는 영속 outbox는 없습니다.

### 캐릭터 외형과 기록된 전적

`lobby.fighter_info`는 조회 대상 온라인 계정의 캐릭터 가방에서 현재 착용한 아이템을 읽고, 만료되거나 수명이 소진된 항목을 제외합니다. 캐릭터 정보 응답 전에 대상의 장비 캐시를 전송합니다. 캐릭터가 없거나 여러 개 선택되어 있거나 로그인 세션이 교체되었다면 성공 스냅샷을 반환하지 않습니다. 조회는 읽기 전용이며 같은 빌드와 데이터 영역의 온라인 플레이어로 한정됩니다. 별도 프리셋 페이지나 인스턴스별 속성을 만들어 보내지 않습니다.

별도 옵션 `lobby.fighter_battle_statistics`의 기본값은 `false`입니다. 활성화하려면 `fighter_info`와 같은 데이터 영역의 전적 저장소가 필요합니다. 원본 주 페이지인 노템/아이템에는 모드 `1`, `3`의 기록된 승, 패, 무, 도망, 버블, 팡, 헬프 합계만 전달합니다. 다른 모드, 서버 개인 점수와 아레나 계급은 표시하지 않습니다. 각 클라이언트가 자신의 무승부 규칙에 따라 구성 수치로 경기 수와 승률을 계산합니다.

주 모드의 기록이 없거나 실제 수치가 클라이언트의 부호 있는 연산 범위를 넘으면 원본 실패 응답을 보냅니다. 수치를 자르거나 축소하거나 0인 전체 경력으로 대체하지 않습니다. 옵션을 끄면 외형 조회는 원본 생성자의 통계 기본값을 유지하며, 그 값은 실제 기록이 아닙니다. Memory는 현재 프로세스에서 기록한 경기만 포함하며 원래 서버의 전체 경력이나 랭크 참가 규칙을 복원하지 않습니다.

검토한 주 페이지 구조는 `kr-1256`(KR2026), `kr-812`, `id-400`, `id-1809`, `cn-324`, `cn-717`, `cn-774`, `tw-454`, `cn-279`, `cn-406`, `cn-706`, `cn-404`, `cn-408`을 포함합니다. TW454의 전체 캐릭터 정보 교환은 별도로 `BFF_TW_454_FIGHTER_INFO=false`에 의해 제어됩니다. `true`로 설정해야 방언과 로비 바인딩이 함께 활성화됩니다. 구조 검토는 실제 클라이언트 검증 완료를 의미하지 않습니다.

격리된 단일 빌드 프로필에서 다음 패치를 `tools/local-checks/isolated-memory.patch.yaml`과 함께 적용합니다. `set`은 기존 프로토콜, 레벨과 결과 설정을 유지합니다. 필요한 기능이 없으면 시작이 실패하며 가짜 데이터를 만들지 않습니다.

```yaml
- set:
    id: ingame
    config:
      record_battle_statistics: true
- set:
    id: lobby
    config:
      online_players: true
      fighter_info: true
      fighter_battle_statistics: true
```
### 커플 관계 저장소

메모리 행은 기반 작업인 `ICoupleStore` 관계 계약도 제공합니다. `couples` 매핑에는 별도 한도가 있습니다: `max_relationships`(기본값 4096, 범위 1–65536), `max_pending_invitations`(1024, 1–65536), `max_pending_per_account`(16, 1–1024), `max_completed_invitations`(1024, 1–65536), `max_message_length`(UTF-16 코드 단위 512개, 1–4096), `max_authority_length`(UTF-16 코드 단위 128개, 1–1024). 초대 수락과 커플 해제는 같은 프로세스에서 두 계정의 관계를 원자적으로 갱신합니다. 완료 결과의 보관 수는 제한되므로 오래된 결과가 제거될 수 있으며, 호출자는 항상 서버에서 생성한 새로운 초대 식별자를 사용해야 합니다. 이 계약에는 아직 MySQL 또는 SQLite 공급자가 없고 반지를 소비하지 않으며, 네이티브 커플 요청, 로그인 복원, 노드 간 알림도 활성화하지 않습니다. 패킷 테이블 지원만으로 이러한 게임 기능이 활성화되지는 않습니다.

### 로컬 격리 점검

`tools/local-checks/isolated-memory.patch.yaml`은 `persistence.mysql`을 비활성화하고 `persistence.memory`를 활성화합니다. 명령줄 패치가 마지막에 적용되므로 실제 데이터베이스를 가리키는 개발자 `.env`나 `local.patch.yaml`보다 우선합니다. 모든 로컬 `run`(`--dump-config` 점검 포함)에 추가하십시오. 아래 "격리된 로컬 점검" 레시피에 전체 명령이 있습니다. 프로세스가 멈추면 메모리 데이터는 사라지며, 이 패치는 운영 영속성 구성을 대신할 수 없습니다.

## 클라이언트 데이터

게임 프로필은 선택한 클라이언트 빌드 자체의 데이터를 읽습니다. 저장소에는 게임 클라이언트와 그 파일이 포함되지 않습니다. 데이터 루트의 기본값은 `client-data`이며 `BFF_CLIENT_DATA`로 옮길 수 있습니다. 구조는 다음과 같습니다.

```text
client-data/
  <build>/
    data/      클라이언트 원래 경로를 유지한 클라이언트 패킷(예: Packs/, Config/)
    dataraw/   같은 클라이언트 경로의 압축 해제된 개별 파일, 먼저 읽음
```

`<build>`는 프로필 id입니다(예: `kr-812`, `kr-1256`). 레거시 프로필은 `${BFF_CLIENT_DATA:-client-data}/${BFF_PROFILE_ID}/data`와 `.../dataraw`를 읽고, 모던 `kr-1256` 프로필은 `kr-1256`에 대해 같은 구조를 사용합니다.

두 디렉터리가 모두 없으면 `clientdata` 행이 활성화 단계에서 실패하며, 오류 메시지는 찾은 두 경로를 알려 주고 서버는 시작을 완료하지 못합니다. 게임 프로필을 시작하기 전에 데이터를 준비하십시오. 이 파일은 읽기 전용 입력이므로 Docker 구성은 읽기 전용으로 마운트합니다.

`management`와 `setup`은 클라이언트 데이터 행을 마운트하지 않습니다. 최초 설치 흐름은 준비된 데이터를 상태 디렉터리로 가져올 수 있습니다. [설치](installation.md)를 참고하십시오.

설치된 클라이언트 업로드와 `tools/client-data/bfdata.py`는 같은 생성 규칙을 사용합니다. 중첩된 `Maps/<Directory>/track.wb`를 포함한 지도 `.wb` 리소스는 원래 클라이언트 경로로 `dataraw`에 추출되며, `sources.tsv`에 출처와 SHA-256이 기록됩니다. 준비된 `data`/`dataraw` 가져오기도 이 파일을 보존합니다. 이전 데이터 트리에 지도 WB가 없다면 해당 기능을 켜기 전에 같은 빌드의 클라이언트에서 새 디렉터리로 다시 생성하십시오. 공용 `WorldBlockFile` helper 리더는 이름, 위치, 회전을 그대로 제공하며 모드별 처리는 호출자가 담당합니다. 서버에 지도 좌표를 하드코딩하지 않습니다.

CN2011(`cn-279`)의 `ingame.item_mode_fallback_point_count: 4`는 일반 아이템 모드에서 방장의 지도 보고에 무작위 상자 지점이 없을 때 서버 보충 정책을 켭니다. 현재 지도의 `#sp_star_` helper에서 서로 다르고 공간적으로 분산된 위치를 최대 네 개 선택하며, 별 지점이 없으면 `#ic_` helper를 사용합니다. 중립 kind-0 상자는 `supply_default_min_ms` / `supply_default_max_ms`(기본 15–30초)에 따라 생성됩니다. 이 주기적 공급은 서버 정책이며 원래 클라이언트에 고정 무작위 상자 표식이 있었다는 의미가 아닙니다. 보고된 기존 무작위 지점은 유지되고 다른 프로필의 옵션 기본값은 0입니다. `item_mode_fallback_maximum_file_bytes`의 기본값은 8388608, `item_mode_fallback_maximum_candidates`는 4096입니다. 지도 리소스가 없거나 지원되지 않거나 잘못되면 좌표를 추측하지 않고 보고를 거부합니다.

CN279는 등급별 가중치 표의 17종 아이템과 기본 보유 슬롯 하나를 유지합니다. 충돌 시 클라이언트가 선택한 아이템을 서버가 검증합니다. CN279는 `item_mode_resolve_invalid_random_pickups`도 켭니다. 존재하고 획득 조건을 충족하는 무작위 상자의 요청 종류가 0이거나 허용 목록 밖이면, 서버가 허용 목록에서 균등하게 한 번 선택합니다. 유효한 클라이언트 결과는 유지되며 고정 종류 상자와 부적격 객체에는 적용되지 않습니다. 옵션이 꺼져 있으면 미해결 종류 0 요청을 거부하고 상자를 보존합니다. 이 보충 분포는 서버 정책이며 기본 등급별 가중치와 다릅니다. 기본 행동 게이지 드롭은 초기 속도를 보존합니다. 슬롯이 비면 가득 찬 슬롯 때문에 거부되었던 살아 있는 상자를 새 객체 ID로 다시 생성하며, 드롭 상자의 재생성 속도는 0입니다. 팀 메디팩 129를 포함한 아이템 사용은 사용자와 모든 참가자에게 방송되어 클라이언트의 기본 효과 경로를 실행합니다. 서버에 별도의 HP 장부를 도입하지 않습니다. 이 자동화 경로는 실제 클라이언트 검증이 여전히 필요합니다.

## 일반 구성

첫 번째 레시피는 격리 점검입니다. 나머지는 의도적으로 영속 저장소를 향하는 구성입니다. 즉, 직접 소유한 저장소를 가리키며 구성 중인 공급자를 비활성화하므로 격리 패치를 포함하지 않습니다. 영속 레시피를 변경할 의도가 없는 데이터베이스에 겨냥하지 마십시오.

### 격리된 로컬 점검

```sh
cp .env.example .env
# 데이터베이스 설정은 필요하지 않습니다. 격리 메모리 패치가 MySQL을 비활성화합니다.
dotnet run --project src/BubbleFighter.Fantasy.Host -c Release -- run --profile management --patch tools/local-checks/isolated-memory.patch.yaml
```

콘솔은 활성화된 행을 보고하고, Host가 준비되면 `Server started with <n> active row(s).`를 출력합니다. `http://127.0.0.1:7300/`의 `GET /health`를 확인하십시오. `status` 필드가 있는 JSON을 반환합니다. `Ctrl+C`로 중지합니다.

### SQLite 서버

저장소 루트에 `sqlite.patch.yaml`을 만듭니다.

```yaml
- replace:
    id: persistence.mysql
    disabled: true
- replace:
    id: persistence.memory
    disabled: true
- replace:
    id: persistence.sqlite
    disabled: false
    config:
      database_path: "${BFF_SQLITE_DATABASE_PATH}"
```

`.env`에서 `BFF_SQLITE_DATABASE_PATH`를 절대 경로로 설정한 뒤 대상 프로필을 시작하십시오(게임 빌드는 클라이언트 데이터가 필요합니다).

```sh
dotnet run --project src/BubbleFighter.Fantasy.Host -c Release -- run --profile kr-1256 --patch tools/local-checks/isolated-memory.patch.yaml --patch sqlite.patch.yaml
```

콘솔에서 SQLite 활성화 줄을 찾고 저장 파일이 설정한 경로에 생겼는지 확인하십시오. `Ctrl+C`로 중지합니다. 저장 파일은 남습니다.

### MySQL 서버

`.env`에 실제 연결 값을 설정하고 기본 MySQL 행을 활성화된 상태로 두십시오.

```sh
BFF_MYSQL_HOST=127.0.0.1
BFF_MYSQL_PORT=3306
BFF_MYSQL_USER=bff
BFF_MYSQL_PASSWORD=<your-database-password>
BFF_MYSQL_DATABASE=bf_game_db
```

로컬 설정을 확인할 때는 이 데이터베이스에 연결하지 말고 격리된 메모리 저장소로 프로필을 검사하십시오.

```sh
dotnet run --project src/BubbleFighter.Fantasy.Host -c Release -- run --profile kr-1256 --patch tools/local-checks/isolated-memory.patch.yaml --dump-config
```

이 덤프는 MySQL을 명시적으로 비활성화하며 리스너를 시작하지 않습니다. 데이터베이스 연결을 검증하거나 마이그레이션을 실행하지 않습니다. 영구 저장소로 운영하려면 데이터베이스 설정을 명시적으로 검토한 후 [배포](deployment.md)를 따르십시오. 실제 MySQL 활성화 시에는 `MySQL persistence connected to <host>:<port>/<database> as <user>.`가 기록되고 대기 중인 마이그레이션이 적용됩니다.

### NAT: 바인드 및 공개 주소

리스너가 모든 인터페이스에 바인딩되고 클라이언트에는 공용 주소가 알려지도록 두 주소를 `.env`에 설정하십시오.

```sh
BFF_BIND_HOST=0.0.0.0
BFF_PUBLIC_HOST=<public-address-clients-use>
```

포트 변수도 같은 방식으로 바꿀 수 있습니다(예: `KR_1256_GAME_PORT`, `KR_1256_RELAY_PORT`). 방화벽에서는 해당 포트만 열고, 시작 전에 `--dump-config`로 주소를 확인하십시오. 특정 리스너의 주소가 프로필 기본값과 달라야 한다면 그 리스너 행에 `set` 패치를 쓰는 방법도 있습니다.

```yaml
- set:
    id: game-listener
    config:
      listen: "0.0.0.0:7100"
```

## 다중 클라이언트 프로필

프로필은 서로 다른 역사적 클라이언트를 제공합니다. 빌드 id는 `<region>-<wire version>`이며, 여기서 wire version은 파일 버전이 아니라 클라이언트의 `ClientVersion_Major`입니다(`kr-812`, `cn-324`, `id-400`, `tw-454`, `kr-1256`). 프로필 디렉터리 이름이 패킷 표 전체에서 사용하는 빌드 id입니다.

`kr-812`(한국 2015)는 **레거시 기준선**입니다. `profiles/bundles/legacy.yaml`이 그 행 집합이며, 레거시 빌드는 자체 `vars`와 `patch.yaml`에 차이(포트, 암호 표, 좌석 수, 좌석 관련 설정, 패킷 스위치)만 선언합니다. `kr-1256`(한국 최종 빌드)은 **모던 기준선**입니다. 자체 `kr-1256`, `ingame`, `shop` 번들을 가지며, 그 패킷 레이아웃이 `cn-774`와 `tw-454`의 기준입니다.

| 프로필 | 클라이언트 빌드 | 역할 |
| --- | --- | --- |
| `kr-812` | `kr:812:458` | 레거시 계열의 기준선입니다. |
| `kr-1256` | `kr:1256:1304` | 모던 기준선이며 Dockerfile의 기본 프로필입니다. |
| `all` | 16개 빌드 | 기동된 모든 빌드를 하나의 프로세스에서 각자의 리스너 포트로 실행합니다. |
| `management` | 없음 | 관리 HTTP와 저장소만 제공하며 게임/릴레이 포트가 없습니다. |
| `setup` | 없음 | 데이터베이스와 무관한 최초 설치 및 관리입니다. |

나머지 클라이언트 빌드 프로필은 각각 하나의 빌드를 제공합니다. 패킷 레이아웃은 `packets/builds.yaml`과 프로필 자체 `parent:` 계보를 통해 상속됩니다. `cn-279`는 `cn-324`를 기반으로 하고 `cn-324`는 `kr-812`를 기반으로 합니다. `cn-738`과 `cn-742`는 `cn-735`의 레이아웃을 따르며, `tw-454`는 `cn-774`를 기반으로 하고 `cn-774`는 `kr-1256`을 기반으로 합니다. 차이가 작은 빌드는 레이아웃을 다시 쓰지 않고 차이만 표기합니다.

빌드는 기능(capability)에서도 다릅니다. 기능은 `packets/builds.yaml`에 빌드별로 기록되고 기준선을 통해 상속됩니다. 예를 들어 만료된 아이템을 버릴 때 범주 6을 제외하는 제한은 `kr-812`에서 켜져 있고 `cn-324`에서 꺼져 있으며, 모던 `kr-1256`은 해당 빌드에서 소비자가 감사될 때까지 여러 레거시 기능을 꺼 둡니다. 레거시 방의 좌석은 기준선에서 12개, `cn-324`에서 8개입니다. 기능 스위치는 빌드의 프로토콜 계층이 무엇을 보내고 활성화할지 결정하며, 이는 추측이 아니라 데이터입니다.

연결하려는 클라이언트 빌드로 프로필을 선택하십시오. 클라이언트 버전을 읽고 일치하는 프로필 id를 찾은 뒤 그 프로필의 포트를 사용하고 해당 빌드의 클라이언트 데이터를 준비하십시오. `all`은 여러 빌드를 함께 실행할 때 사용하며, 각 빌드의 리스너를 시작하고 선택한 모든 빌드의 데이터가 필요합니다.

나열된 프로필이 의미하는 것은 저장소가 이 행들을 구성하고 이 빌드의 패킷 데이터와 기능 기록을 포함한다는 것입니다. 의미하지 않는 것은 모든 게임플레이 기능이 구현되었거나 실제 클라이언트가 검증되었다는 것입니다. 자동화 점검 통과, 기능 활성화, 프로필 목록 등재는 실제 클라이언트 호환성을 입증하지 않습니다. 기능 기록은 감사된 네이티브 지원을 설명하며, 네이티브 수용 테스트는 별도로 수행해야 합니다.

## 기본으로 켜진 기능

배포되는 프로필은 구현된 모든 기능을 기본으로 켜므로 새 서버에서 바로 전부 시험할 수 있습니다. 아래 표의 각 게임 기능 스위치는 기본값이 `true`이며, `.env`에서 `false`로 설정하면 해당 기능이 꺼집니다. 클라이언트가 값을 정하지 않는 항목(성공 확률, 차감 수량, 무기 풀)은 프로필에 동작하는 서버 정책이 들어 있으며 로컬 패치로 바꿀 수 있습니다. 아래 각 절에서 설명하는 필드는 모두 프로필이 채워 둡니다.

| 변수 | 기능 |
| --- | --- |
| `BFF_TITLES_ENABLED` | 칭호, 메달 교환, 자동 라운드 메달(`kr-812`, `kr-1256`) |
| `BFF_FAVORITE_WEAPON_ENABLED` | Favorite 무기 포인트와 등급 알림(`kr-1256`) |

각 빌드 프로필은 감사된 모든 모드 패치도 나열합니다. `kr-1256`은 폭탄, 캡틴, BnB, Extreme Racing, Final Zone, OneKill, 별, 유령·스크립트 좀비, Rhea, AI 방, Zombie Escape, 대기실 강퇴, 방어 시드, WeaponMaster를, `cn-774`와 `tw-454`는 감사된 일부를, 레거시 빌드는 폭탄과 캡틴을 포함합니다. 각 빌드의 `modes.patch.yaml`이 마지막에 와서 결과 점수판 모드의 합집합을 한 번에 지정합니다. 런처 티켓, UDP 전송, 클러스터 행, 패킷 로그는 꺼진 상태로 남습니다. 이들은 게임 내용이 아니라 클라이언트의 연결 방식을 바꾸기 때문입니다. 모든 시간대 설정은 어느 호스트에서나 IANA 이름(`Asia/Seoul`)과 Windows 이름(`Korea Standard Time`)을 모두 받습니다.

## 선택 기능 번들

일부 번들은 명시적으로 활성화해야 하며, 클라이언트 감사가 뒷받침하는 프로필에서만 나열됩니다.

**`player-settings`**는 `player.settings`를 마운트하며, 이는 플레이어 사용자 지정 키의 형식화된 저장소입니다. 패킷 자체는 `dialect.messages` 행의 `customized_keys` 옵션이 묶으며 `kr-812`, `kr-1256`, `cn-774`, `tw-454`가 선언합니다. 다른 프로필은 먼저 네이티브 컨트롤 이름과 패킷 경로를 감사해야 합니다. 각 `player.settings` 행은 `protocol`이 필요하고 프로필별 `scope`를 사용해 서로 다른 빌드의 이름이 섞이지 않게 합니다. 영속성 공급자는 계정별로 매핑을 저장하며, MySQL은 마이그레이션 `0032_customized_keys.sql`을 통해 저장합니다. 계정당 예산은 각 공급자의 `customized_keys`로 설정합니다(`max_scopes` 1–64, `max_mappings` 1–512, `max_name_characters` 1–1024이며, 세 값의 조합이 패킷 본문에 들어가야 합니다). 예산을 넘기면 다른 저장 매핑을 밀어내지 않고 실패합니다.

`dialect.messages.config.science_lab`의 기본값은 `false`이며 `kr-1256`, `cn-774`, `tw-454`의 검증된 실험실 작업을 라우팅합니다. 담당 처리기가 없는 작업은 클라이언트의 실험실 닫힘 결과(KR은 5, CN/TW는 4)를 반환합니다. 활성화하려면 모든 요청과 응답 쌍이 검증되고 해당 레이아웃이 있어야 하며, 불완전한 테이블은 실패합니다. 이 옵션만으로는 조합법, 경제 정책, 아이템 변경 또는 실험실 설정을 제공하지 않습니다. [선택적 아이템 강화](#선택적-아이템-강화) 번들은 `kr-1256`에서 이 옵션과 `science_lab_configuration`, 강화 처리기를 함께 활성화하고, 해당 빌드에서 별도로 활성화하는 선택적 개조(Modification) 정책을 제공합니다. 레거시 `kr-812`의 합성과 분해는 별도의 [선택적 레거시 과학실](#선택적-레거시-과학실) 설정을 사용합니다. 네이티브 실험실 UI 검증은 아직 남아 있습니다.

만료된 아이템 버리기도 같은 방식으로 선언합니다. `dialect.messages` 행의 `inventory_actions` 옵션이 `gcpReqInventoryThrowItem`/`gspRepInventoryThrowItem`을 묶고(모든 legacy 빌드와 `kr-1256`에서 켬), 빌드 자신의 bundle 안 `inventory.throw` 행이 저장 장비 서비스를 통해 해당 아이템을 제거합니다. 동작은 의도적으로 좁습니다. 인증된 한 플레이어의 두 가방에서 해당 만료 아이템만 제거하고, 일치하는 이용 권한이 유효하면 제거 전체를 거부하며, 빌드의 범주 6 제외 규칙을 따릅니다. 경기 중 요청은 거부됩니다. 실제 클라이언트 수용은 아직 남아 있으며, 패킷 표 지원만으로 다른 빌드에서 이 옵션을 선언할 수는 없습니다.

**`launcher.http`**는 선택적 공용 런처 API입니다. 기본적으로 비활성화되며 관리와 분리됩니다. `minimum_launcher_version`(비우면 검사 안 함)과 런처가 적용하는 플러그인별 유형 규칙인 `client_policy`를 받습니다. 규칙은 스토어 ID와 선언된 스토어 소스만 가리키며 실행 파일 경로는 절대 포함하지 않습니다. 최소 버전이 설정되면 구버전 런처는 HTTP 426을 받습니다. 각 로비 행의 `authentication` 옵션(`BFF_LOGIN_AUTHENTICATION`, 기본값 `ticket`)은 런처 티켓을 교환하는 로그인만 허용하며 이때 이 행이 활성 상태여야 합니다. `open`은 모든 계정 이름을 허용하므로 신뢰할 수 있는 LAN에서만 사용하십시오. [런처](launcher.md) 페이지에서 API, 클라이언트 프리셋, 계정과 티켓 흐름, 운영자 설정을 설명합니다.

런처 요청 및 로그인 세션 제한은 `launcher.http` 행에서 설정합니다.

| 키 | 기본값 | 동작 |
|---|---|---|
| `requests_per_minute` | `120` | 전송 연결의 원본 IP별 1분 요청 수입니다. 전달 헤더로 원본 IP가 바뀌지 않습니다. |
| `max_rate_limit_addresses` | `4096` | 보관할 IP별 시간 창 수(1–100000)이며, 가득 차면 가장 오래된 창을 제거합니다. |
| `max_sessions_per_account` | `8` | 계정별 유효한 영구 로그인 세션 수(1–1024)이며, 새 로그인 시 생성 시간이 가장 오래된 세션을 취소합니다. |
| `max_sessions` | `1024` | 기존 프로세스 내 접근 토큰 및 대기 중 게임 티켓 수 제한입니다. |

오래된 세션을 취소하면 이 프로세스의 접근 토큰과 대기 중 게임 티켓도 제거됩니다. 만료된 갱신 세션은 리스너 시작 전에 삭제하며, 이후 로그인 과정에서는 최대 1시간에 한 번 삭제합니다. 계정 제한은 세션 저장소에서 적용되므로 서버를 다시 시작해도 유지됩니다.

## 수동 릴레이 지연 응답

`relay-latency` 번들은 `kr-1256`, `cn-738`, `cn-742`, `cn-774`, `tw-454`에만 기본 비활성 상태인 `dialect.relay-latency`와 `match-latency` 행을 추가합니다. 네이티브 클라이언트 수용 테스트에서는 배포 패치로 두 행을 함께 활성화할 수 있습니다.

```yaml
- set:
    id: dialect.relay-latency
    disabled: false
- set:
    id: match-latency
    disabled: false
    config:
      reply_word: 0
```

두 행의 `protocol`은 `kr-1256/relay`처럼 해당 빌드의 릴레이 프로토콜이어야 하며 번들이 이 값을 제공합니다. dialect의 `packets_directory` 기본값은 `packets`입니다. 로직 행의 `reply_word`는 `0..4294967295`를 허용하며 기본값은 `0`입니다. 네이티브 응답 처리기가 읽은 뒤 버리는 의미 미확정 4바이트 값이며, 요청 타임스탬프를 되돌려 주는 값이 아닙니다.

완전한 요청마다 인증을 마쳤고 임대가 여전히 유효한 원래 릴레이 연결로 한 번 응답합니다. 응답은 연결 소유자의 직렬화 게이트를 핸드셰이크 전송과 공유하며 장면 초기화 완료를 요구하지 않습니다. 잘못된 본문, 무효 임대, 전송 실패는 연결 오류로 처리하고 기존 연결 및 송신 큐 예산으로 자원을 제한합니다. 핸드셰이크 순서와 클라이언트 샘플러 설정은 유지됩니다. 두 행을 활성화해도 클라이언트 탐측은 시작되지 않습니다. 네이티브 클라이언트 수용 검증이 끝날 때까지 두 행은 기본 비활성 상태입니다. `all` 프로필 패치에서는 빌드 접두사가 붙은 행 ID를 사용합니다.

## 선택적 UDP 전송

`net.udp` 플러그인이 UDP를 제공합니다. 게임 로그인, 방 입장 및 경기 인증은 TCP를 유지하며, UDP는 검증된 네이티브 이동 및 탐색 트래픽을 전달합니다. 기본 프로필은 UDP 리스너를 활성화하지 않습니다.

| 선택적 패치 | 검증된 프로필 | 전송 방식 |
| --- | --- | --- |
| `profiles/bundles/udp-relay.patch.yaml` | `kr-812`, `cn-717`, `id-1809`, `kr-1256`, `cn-774`, `tw-454` | 서버 UDP 엔드포인트로 인증된 이동을 전송하며, 수신자의 엔드포인트가 없으면 TCP로 전달합니다. |
| `profiles/bundles/udp-peers.patch.yaml` | `cn-279`, `cn-324`, `cn-406`, `id-400`, `cn-404`, `cn-408`, `cn-705`, `cn-706` | 서버가 탐색과 피어 간 직접 이동을 조정하며, 실패한 경로는 경기 TCP 전송을 유지합니다. |

일치하는 단일 프로필에 두 패치 중 하나를 적용하세요. 두 패치는 대안이며, 버전 접두사가 없는 행 ID를 `all`에 직접 적용할 수 없습니다. `BFF_UDP_PORT`는 사용 가능한 UDP 포트, `BFF_BIND_HOST`는 수신 주소입니다. 선택적 `BFF_UDP_PUBLIC_PORT`는 외부에 매핑한 UDP 포트이며, 0이면 실제 바인딩 포트를 알립니다. UDP 포워딩은 기존 게임 및 릴레이 TCP 포트와 별개입니다. 피어 탐색은 인증된 게임 서버의 IPv4 주소를, 릴레이 우회는 릴레이 서버의 IPv4 주소를 사용하므로 외부 UDP 매핑도 해당 공인 주소를 사용해야 합니다.

일반 TCP/관리 포트를 사용 가능한 로컬 포트로 지정하고 해당 빌드의 클라이언트 데이터를 준비한 뒤 다음과 같이 실행합니다.

```powershell
$env:BFF_LOGIN_AUTHENTICATION = "open"
$env:BFF_BIND_HOST = "127.0.0.1"
$env:BFF_UDP_PORT = "7603"
dotnet run --project src/BubbleFighter.Fantasy.Host -c Release -- run --profile cn-324 --patch tools/local-checks/isolated-memory.patch.yaml --patch profiles/bundles/udp-peers.patch.yaml
```

선택적 UDP 패치를 적용하면 `BFF_UDP_ENABLED`의 기본값은 `true`입니다. `false`로 설정하면 TCP를 유지하며 UDP 리스너와 협상을 시작하지 않습니다. 혼자 있는 방은 기본적으로 TCP를 사용합니다. 경기가 시작되고 모든 relay가 초기화되며 엔드포인트 검증이 완료된 뒤에만 UDP 이동을 허용합니다.

UDP 설정은 공개된 게임 방으로 제한합니다. CN279, CN324, CN406 및 ID400은 게임 장면에서 탐색 패킷을 전송하지 않으므로 대기실에서 엔드포인트를 탐색하고 피어 테이블을 확인합니다. 전체 방 설치는 준비된 테이블을 무효화합니다. 제어 메시지는 방 작업과 같은 직렬 큐를 사용하므로 방 설치나 장면 진입을 추월하지 않습니다. 펀칭과 직접 이동은 경기 시작 및 모든 relay의 초기화 이후에만 수행합니다. 다른 검증된 빌드는 이 장벽 이후에 협상을 시작합니다. 로그인 및 자동 장면, 메뉴, 로비, 광장과 1인 훈련에서는 UDP를 협상하지 않으며, 방의 강제 설정으로도 이 제한을 우회할 수 없습니다.

방장은 `!udp on`으로 혼자 있는 방에서도 UDP 협상을 강제하고, `!udp off`로 TCP를 유지하거나, `!udp`로 현재 방의 설정을 전환할 수 있습니다. 방 명령으로 전역 비활성화 상태이거나 사용할 수 없는 UDP를 켤 수는 없습니다. 검증되지 않았거나 연결할 수 없는 경로는 TCP를 유지합니다. 모든 플러그인 명령에서 `/`, `!`, `！`는 같은 명령 시작 문자입니다. 게임에서는 `/`가 클라이언트 기본 명령으로 처리될 수 있으므로 사용법에 `!`를 표시합니다. 관리 화면과 콘솔에서는 `udp on`처럼 시작 문자 없이도 입력할 수 있으며 사용법에는 `/`를 표시합니다.

방의 모든 구성원은 `!udp status`로 UDP 사용 여부를 확인할 수 있습니다. 전송 방식(서버를 거치는 `relay` 또는 직접 연결하는 `peer`), 방 설정, 그리고 구성원마다 `UDP`, `NEGOTIATING` 또는 `TCP` 상태와 이유(라운드 대기, 제안했지만 UDP 프로브를 받지 못함, 검증됨, 클라이언트의 TCP 전환 등)를 보여 줍니다. 서버에서 UDP가 꺼져 있거나 해당 클라이언트 버전에 UDP 설정이 없을 때도 알려 줍니다. `!plaza`는 라운드 중에도 현재 방을 즉시 나가 광장으로 갑니다. 좌석은 스스로 나갈 때와 똑같이 해제되므로 라운드는 나간 플레이어를 정산하고 나머지는 계속 플레이하며, 마지막 플레이어가 나가면 방이 삭제됩니다. TCP로 전환되면 그 이유를 표시합니다. UDP 프로브가 서버에 도달하지 못함, 챌린지 응답이 돌아오는 길에 손실됨, 좌석별 탐색 또는 피어 표 시간 초과, 매치 연결 종료, 플레이어 사이에 직접 경로 없음 등입니다.

`match-udp-directory.max_sessions`는 인증된 우회 임대 수를 제한합니다. `match-udp-peers`의 `max_rounds`와 `max_peers`는 보관할 경기와 피어 수를 제한하며, 탐색, 테이블 확인, 펀칭 및 제어 전송 기한도 설정할 수 있습니다. 사설 엔드포인트 후보는 같은 공인 IPv4에서 관측된 피어끼리만 공유합니다. 방/경기 변경, 연결 종료, 소비자 언로드 및 릴레이 교체 시 해당 경로를 무효화합니다. IPv4만 지원하며, 모든 NAT나 방화벽에서 피어 간 직접 전송이 가능한 것은 아닙니다.

패킷 테이블은 `cn-735`, `cn-738`, `cn-742`의 4바이트 쿠키 및 부동소수점 이동 우회 형식도 검증합니다. 전송 어댑터의 격리 테스트는 있지만, 연구 프로필에는 릴레이 패치에 필요한 전체 방/경기 구성이 아직 없습니다. 이는 패킷 지원 범위이며 완전한 프로필 지원을 뜻하지 않습니다. 자동 소켓 시나리오는 클라이언트의 네이티브 프로토콜을 모사하며, 실제 게임 클라이언트 검증은 별도입니다.

여러 빌드를 실행할 때는 각 대상 빌드의 선택적 `local.patch.yaml`에 해당 패치 작업을 넣고 빌드 접두사 없는 행 ID를 사용합니다. 공유 프로필 패치는 빌드 행을 추가하기 전에 적용되므로 `all`의 패치에서 `kr-812.dialect.rooms` 같은 빌드 접두사 행을 수정할 수 없습니다. 빌드마다 서로 다른 UDP 포트를 지정합니다. peer 패치는 필요한 네이티브 relay 행도 활성화합니다. `cn-705`와 `cn-706`은 패치가 없으면 해당 행을 비활성 상태로 유지하며, 패치는 장면 시드 테이블 권한을 활성화하지 않습니다.

UDP 소켓 구독, 임대 등록, 방 큐 콜백, Span/out 매개변수 조회 및 IP 엔드포인트 레코드는 현재 네이티브 플러그인이 필요하며 원격 SDK 어댑터는 아직 없습니다. 직렬화할 수 있는 방 스냅샷과 릴레이 제어 작업은 계약 스키마를 통해 계속 사용할 수 있습니다.

`match-udp-peers`의 `punch_retry_ms` 기본값은 250이며 0이면 재시도를 끕니다. `punch_window_ms` 안에서 네이티브 펀칭 시작 명령을 다시 보내며 시간 창을 연장하거나 피어 ID를 바꾸지 않습니다. 직접 경로는 현재 인증된 매치 연결의 피어별 멤버십 보고가 있어야 허용됩니다. `!udp status`는 네이티브 결과 미수신과 클라이언트가 보고한 성공 경로 0개를 구분합니다. 이 결과만으로 방화벽이나 NAT 장애를 단정하지 않습니다.

대기실에서만 탐색하는 빌드는 `discovery_refresh_ms`(기본 1000, 0이면 갱신 비활성화) 간격으로 같은 피어 ID의 네이티브 일회성 탐색 요청을 다시 보냅니다. 로딩 중에는 해당 클라이언트가 탐색을 처리하지 않으므로 요청을 중지합니다. 공인 엔드포인트나 로컬 후보가 바뀌면 테이블을 다시 보내고 확인을 다시 기다립니다. 초기화된 라운드에서 펀칭을 시작하기 전에 탐색을 중지합니다.

## 검증과 안전

`nodes[].authentication`은 `authority_id`, `api_url`, `mode`(`master-issued` 또는 `own-authority`), `policy_mode: authority`를 명시합니다. 한 인증 ID는 운영자가 설정한 하나의 HTTP 또는 HTTPS 출처만 가리킵니다. 해당 인증 서비스의 카탈로그와 선택한 빌드 정책을 적용하며 독립 인증 서비스 사이의 암시적 상속이나 병합은 없습니다. 메타데이터가 없으면 인증 신뢰를 부여하지 않습니다.

선택적 `cluster-ticket-authority.patch.yaml`은 로컬 Launcher 티켓 발급자 옆에 `cluster.ticket-authority`를 탑재합니다. 각 신뢰 노드는 서로 다른 교환 키와 명시적인 빌드 허용 목록을 갖습니다. 비공개 `POST /v1/nodes/{node}/tickets/redeem`은 `{ticket,build}`를 한 번 소비하고 계정, Launcher 언어, 실행 ID를 반환합니다. `cluster-ticket-client.patch.yaml`은 작업 노드의 로컬 티켓 제공자 대신 원격 제공자를 탑재합니다. 게임 로그인에는 티켓이 필수여야 합니다. `BFF_CLUSTER_TICKET_URL`, `BFF_CLUSTER_NODE_ID`, `BFF_CLUSTER_REDEMPTION_KEY`를 설정하고 인증 주소의 HTTP 또는 HTTPS를 명시적으로 선택하십시오. 비동기 요청은 제한되며 리디렉션, 재시도, 계정 이름 폴백이 없습니다. 시간 초과 전에 티켓이 소비되었을 수 있으므로 새 실행 티켓을 발급받으십시오. 독립 인증 서비스는 해당 출처에 로그인한 Launcher 세션과 자체 실행 티켓을 요구합니다. 전역 세션 소유권이나 기본 선택 UI의 인증 통합은 아직 제공하지 않습니다.

- 알 수 없는 구성 키와 잘못된 값은 구성 또는 활성화를 실패시킵니다. 무시되지 않습니다. 활성화에 실패한 행은 조용히 건너뛰지 않고 상태와 진단과 함께 보고됩니다.
- `--dump-config`는 자격 증명을 포함한 보간된 값을 출력합니다. 버그 보고서에 공유하기 전에 민감 정보를 제거하십시오.
- `.env`나 `local.patch.yaml`을 커밋하지 마십시오. 둘 다 Git에서 제외되며 비밀 정보나 머신별 경로를 담을 수 있습니다.
- 모든 로컬 `run`에 `--patch tools/local-checks/isolated-memory.patch.yaml`을 추가하십시오. 개발자의 `.env`가 실제 데이터베이스에 닿지 않게 하는 유일한 신뢰할 수 있는 방법입니다.
- 프로필이나 패치 파일 변경은 다음 시작부터 적용됩니다. 프로필은 시작할 때 한 번만 구성됩니다. 관리 API로 개별 행을 재로드할 수 있지만 이는 플러그인 수명 주기 작업이며 새 프로필을 적용하는 방법이 아닙니다. 재로드 동작은 [플러그인](plugins.md)을 참고하십시오.

## 선택적 서버 검색

schema-1 서버 디렉터리는 응답의 `generated_at_utc`와 대상의 `observed_at_utc`, `expires_at_utc`, `status_revision`을 제공합니다(Contracts 4.5.0). 시간은 UTC RFC3339이며 첫 보고가 승인되기 전에는 대상의 세 필드가 모두 null입니다. 대상 필드는 소스가 관리하는 동일한 보고를 나타냅니다. 반복 조회나 같은 임대의 재등록은 만료를 연장하지 않습니다. 만료된 수동 항목은 만료 정보를 보존하며 임대 철회나 시계 변경은 만료를 앞당길 수 있습니다. 만료는 소스의 남은 임대를 UTC로 환산한 시점보다 늦을 수 없습니다. 리비전은 동등 비교만 가능한 불투명 값이며 정렬 가능한 버전이나 임대 자격 증명이 아닙니다. 배치에 사용할 때 누락되거나 잘못되었거나 만료된 정보를 거부해야 합니다. 새 응답 생성은 대상의 만료를 갱신하지 않습니다. 공개된 최신성 필드는 계정의 접속을 승인하거나 티켓을 백엔드 구성원에 바인딩하지 않습니다. 자동 실행에는 보고 만료와 인증 승인 만료 모두로 제한되는 명시적으로 승인된 실행별 후보 집합이 별도로 필요합니다.

선택적 `cluster-launch-selection.patch.yaml`은 티켓 발급 측에 `cluster.launch-selection`을 등록합니다. `BFF_CLUSTER_NODE_ID`, `BFF_CLUSTER_AUTHORITY_ID`, `BFF_CLUSTER_AUTHORITY_URL`, `BFF_CLUSTER_DATA_SCOPE`, `BFF_CLUSTER_AUTOMATIC_SELECTOR_ID`로 로컬 노드, 인증 기관 식별자와 정확한 API 원본, 영구 데이터 범위 및 자동 선택 항목을 명시합니다. 인증된 `POST /v1/launch`에 `serverSelection: true`를 전달하면 티켓에 결합된 `serverSelection`에 `schema`, `grantId`, `build`, `authorityId`, `policyRevision`, `dataScope`, `expiresAtUtc`, `generated_at_utc`, `servers`가 반환됩니다. 허용된 구성 노드 풀에는 오프라인이거나 아직 보고하지 않은 노드도 포함될 수 있으며, 이는 인증 허용 범위이지 현재 배치 가능 상태가 아닙니다. 스냅샷은 해당 실행의 네이티브 선택 항목, 물리 노드 및 엔드포인트 바인딩을 고정합니다. 티켓은 인증 bearer로 제한되는 기존 수명을 유지하며 짧은 하트비트가 느린 게임 시작의 로그인 시간을 줄이지 않습니다. `POST /v1/launch/servers`는 같은 인증 세션과 `{ticket,build,grantId}`를 요구하고 원래 바인딩의 관측 상태만 갱신합니다. 티켓을 소비하거나 교체하지 않고 구성원을 추가하거나 엔드포인트 또는 원본 만료를 변경하지 않습니다. 소비되었거나 만료되거나 유효하지 않은 허가는 HTTP 409 `admission_closed`를 반환하여 정상 로그인 뒤 갱신 루프를 종료할 수 있습니다. 신뢰된 작업 노드의 교환은 일회성 소비와 같은 잠금 안에서 인증된 노드가 티켓 구성원인지 확인하고, 로컬 교환은 명시된 로컬 노드 식별자를 사용합니다. 일반 실행 동작은 유지됩니다. 이 API는 네이티브 리디렉션 승인, 공유 저장소 또는 노드 간 방 입장을 구현하지 않습니다. Center가 gateway 모드로 명시적으로 활성화되고 디렉터리에 자동 항목이 있을 때만 발급 측 선택 행을 등록하면 플래그를 생략해도 모든 인증된 티켓에 범위가 적용되며, 명시적인 `serverSelection: false`는 HTTP 409 `server_selection_required`를 반환합니다. 이전 요청 형태로 이를 우회할 수 없습니다. `launcher.http`의 `max_selection_targets`는 허가당 보관되는 선택 항목별 엔드포인트 수의 합을 제한하며 기본값은 128입니다. 허용된 각 작업 노드에는 같은 엔드포인트 바인딩을 가진 유일한 표준 수동 선택 항목이 필요합니다. 발급 측은 서비스 게시 전에 구성된 빌드를 검사하며 네이티브 매핑이 없거나 모호하면 활성화가 실패합니다. 자동 항목을 통한 갱신도 해당 표준 선택 식별자를 바꿀 수 없습니다.

단독 서버 프로필은 기본적으로 `cluster.directory`나 `cluster.node`를 탑재하지 않습니다. `profiles/bundles/cluster-directory.patch.yaml` 예제는 `kr-1256`용 디렉터리와 보고 플러그인을 함께, `cluster-node.patch.yaml`은 보고 플러그인만 탑재합니다. `builds`와 각 노드의 `endpoints`를 명시하고 배포 비밀을 통해 노드마다 다른 임의의 `BFF_CLUSTER_NODE_KEY`를 제공하십시오. 기본 비공개 리스너는 `127.0.0.1:8093`입니다. 보고 주소의 HTTP 또는 HTTPS는 운영자가 명시적으로 선택하며 자동 업그레이드는 없습니다.

선택적인 `profiles/bundles/cluster-room-directory.patch.yaml`은 `cluster.room-directory`를 탑재하여 `IFederatedRoomDiscovery`를 제공합니다. `node_id`, `directory_url`, `access_key`와 명시적인 `builds` 허용 목록을 설정합니다. 호출마다 인증된 현재 방 목록을 가져오며 실패 시 이전 목록을 반환하지 않습니다. `max_rooms`, `max_response_bytes`, `max_concurrent_requests`, `request_timeout_seconds`는 방 수, 버퍼 바이트 수, 동시 요청 수와 전체 요청 기한을 제한합니다. 동시 요청 한도를 초과하면 대기열 없이 오류를 반환합니다. 리디렉션, 잘못된 응답과 설정되지 않은 빌드도 명시적으로 실패합니다. 방 디렉터리 구성원 관계는 계정 데이터와 독립적으로 가시성만 제어합니다. 검색 서비스는 방 입장 권한이나 좌석을 부여하지 않으며 게임의 방 목록도 변경하지 않습니다. 독립 서버 프로필은 이 행을 탑재하지 않습니다. Contracts 4.6.0에 검색 인터페이스를 추가합니다.

`cluster.directory.room_preparation_permits`는 인증된 노드 전용 준비 허가 경로를 선택적으로 켜며 기본값은 false입니다. 원본은 `/v1/nodes/{source}/room-preparations`에 현재 임대 토큰/세대와 대상 노드/세대, 빌드, 방 번호, 방 생성 ID, 계정 번호를 보냅니다. 발급에는 신선하고 준비된 노드, 같은 비어 있지 않은 데이터/입장 범위, 공유 방 가시성, 명시적인 동일 master-issued 인증 기관 및 같은 권위 데이터베이스 ID가 필요합니다. 대상은 자체 노드 키와 현재 프로세스 임대로 `/v1/nodes/{destination}/room-preparations/claim`에서 한 번만 교환합니다. 교환은 임대, 엔드포인트 권위와 정확한 대기 중 방을 다시 확인하므로 해제된 노드나 재사용된 방 번호는 허가를 상속하지 않습니다. 원본은 발급 경로에 인증된 DELETE를 보내 자신의 허가를 취소할 수 있습니다. `max_room_preparation_permits`는 보관 수를 제한하며 기본값은 512입니다. `room_preparation_permit_lifetime_ms`는 단조 시계 수명으로 기본 10000, 허용 범위 100..60000입니다. 디렉터리는 토큰 해시만 보관하고 방 비밀번호를 받지 않습니다. 허가는 대상 준비만 허용하며 좌석 예약, 네이티브 게임 연결 인증, 계정 소유권 이전 또는 원격 방 클릭을 활성화하지 않습니다. 친선 및 독립 디렉터리는 계속 가시성만 공유합니다.

공개된 실제 게임 방은 `IPublishedRoomDirectory`(Contracts 4.7.0)를 통해 분리된 원본 목록 스냅샷을 제공합니다. 생성할 때마다 새로운 `instanceId`를 부여하여 재사용 가능한 방 번호와 구분합니다. 하트비트에는 방장 닉네임, 모드와 설정을 포함하지만 비밀번호, 계정 레코드나 세션 접두사는 포함하지 않습니다. 디렉터리와 검색 클라이언트는 원본 메타데이터가 요약과 일치하는지 검사하고 `max_room_settings_bytes`(기본 65536)로 모든 설정 블록과 라운드 선택의 총 바이트 수를 제한합니다. 숨겨진 방, 연습 및 튜토리얼 방은 공개하지 않습니다. 이 메타데이터는 아직 원본 브라우저에 원격 방을 표시하거나 노드 간 입장을 허가하지 않습니다.

선택적 `profiles/bundles/cluster-room-browser.patch.yaml`은 `client_build`마다 `cluster.room-browser`를 하나 등록하며 인증된 검색을 사용하고 `IRoomBrowser`를 제공합니다(Contracts 4.8.0). `node_id`는 디렉터리 클라이언트와 같아야 합니다. 브라우저 상태는 게임 연결과 수명이 같으며 연결 수는 이미 리스너가 제한합니다. `max_aliases_per_connection`은 연결 수명 동안의 방 식별자 수를 제한합니다(기본값과 최댓값 모두 원래 클라이언트의 부호 있는 16비트 별칭인 32767). 로컬 레지스트리 스냅샷은 오래된 로컬 하트비트 항목을 대체합니다. 완전한 네이티브 메타데이터가 있는 다른 노드의 방에는 서로 다른 양수 별칭이 할당되며 정렬 변경으로 바뀌거나 연결 중 재사용되지 않습니다. 원격 방을 클릭할 때 새 디렉터리 응답으로 노드 세대와 방 생성 식별자를 확인합니다. 참가 힌트는 인증이 아닙니다. 사라지거나 재생성되거나 조회할 수 없는 대상은 거부하며 같은 번호의 로컬 방으로 대체하지 않습니다. 갱신 실패 시 별칭을 무효화하고 연결 종료 또는 플러그인 해제 시 상태를 반환합니다. 인증된 게임 소유 연결만 검색할 수 있습니다. 로컬 참가는 비밀번호, 정원, 단계와 생성 식별자를 확인합니다. 아래 마이그레이션 패치를 마운트하고 디렉터리가 두 노드의 `native_migration_builds`에 해당 빌드를 모두 나열한 경우에만 원격 방 클릭이 로그인 상태 마이그레이션을 시작하며, 그렇지 않으면 거부됩니다. 단독 서버 프로필에는 이 행이 없습니다.

선택적 `profiles/bundles/cluster-plaza-federation.patch.yaml`은 `cluster.plaza-federation`을 탑재하여 노드 사이에서 광장을 공유합니다. 같은 클라이언트 빌드의 플레이어는 어느 노드에 로그인했든 광장에서 서로를 볼 수 있습니다. 디렉터리 행에 `plaza_federation: true`를 설정하고 각 노드에서 공유할 `builds`를 나열하며, `node_id`, `directory_url`, `access_key`는 하트비트 행과 같아야 합니다. 비어 있지 않은 같은 `data_scope`를 가지고 하트비트로 그 범위의 데이터베이스를 증명한 노드만 광장을 공유하며, 자체 데이터를 가진 우호 서버는 서로 보이지 않습니다. 각 노드는 광장 입장, 이동, 퇴장을 보내고(`flush_interval_ms`, 기본값 100) 모든 빌드에 대해 하나의 요청으로 다른 노드의 변경을 롱 폴링합니다(`poll_wait_seconds`). 원격 플레이어는 로컬 광장의 좌석 하나를 차지하고 로컬 플레이어와 같은 좌석 및 위치 패킷으로 표시되므로 클라이언트에서는 차이가 없습니다. 임대가 만료된 노드는 자기 플레이어를 함께 내보내며, 재연결이나 디렉터리 재시작 후에는 스냅샷을 받고 자기 광장을 다시 보냅니다. `max_queued_events`, `max_plaza_events`, `max_plaza_members`는 대기열 크기를 제한하며 클라이언트 광장은 여전히 36석입니다. Contracts 4.25.0이 `IPlazaFederationEndpoint`를 추가합니다.

선택적 `profiles/bundles/cluster-migration.patch.yaml`은 노드 단위 마이그레이션 행(broker, arrivals, destination)을, `cluster-migration-build.patch.yaml`은 빌드별 행(브라우저, 출발지, 승인 및 `lobby`, `dialect.messages`, `ingame` 스위치)을 담습니다. node, room-directory, account-store, account-sessions, write-fencing 패치 다음에 마운트하고 디렉터리에 `migrations: true`와 `native_migration_builds`를 설정하세요. 목적지 엔드포인트의 `listener_id`는 게임 리스너 행으로, 단일 빌드 프로필에서는 `game-listener`, 다중 빌드 프로필에서는 `<build>.game-listener`입니다. 출발지 행의 `channel`과 승인 행의 `channels`에 해당 빌드에서 확인한 값을 설정하세요. 패치에는 값이 없으므로 확인되지 않은 빌드는 다른 빌드의 값을 물려받지 않고 시작에 실패합니다. 클라이언트는 허용하는 채널의 이동 응답만 받아들입니다. kr-812는 50, 60, 80을 무조건 허용하고 cn-324는 50, 60을 허용하며 80은 거부합니다. 보유된 계정마다 데이터베이스 연결 하나가 열려 있으므로 데이터베이스 연결 한도는 모든 노드의 접속 플레이어를 감당해야 합니다.

빌드별 번들은 `protocol.config.accept_retained_moves: true`도 설정하므로, 이동한 클라이언트의 `gcpReqMoveInto`가 패치 요청보다 먼저 대상 연결을 열 수 있습니다. 이때도 핸들러가 핸드셰이크 계속을 승인해야 합니다. 부트스트랩 목록에는 숫자가 아니라 패킷 이름을 씁니다. `pre_handshake_opcodes`와 `alternate_handshake_sequence`는 클라이언트에서 서버로 가는 패킷 이름을 받으며, 각 빌드가 자기 opcode 표로 해석합니다. 숫자, 알 수 없는 이름, 서버에서 클라이언트로 가는 이름, 릴레이 전용 이름은 시작 시 서버를 멈춥니다. 모든 보조 연결에서 빈 표시 패킷을 먼저 보내는 빌드는 프로필에 `auxiliary_prefix`로 한 번만 적습니다(cn-279, cn-324, cn-406은 `gcpStartGPK`를 보냅니다). `answer_center_status: true`는 네이티브 서버 선택기의 상태 조회를 이 접두사 다음의 `gcpReqCenterUserCnt`로 받아들이며, 명시한 `alternate_handshake_sequence`가 여전히 우선합니다. 대상 엔드포인트는 프로필 자신의 빌드와 `<BUILD>_PUBLIC_PORT`에서 읽는 `GAME_PUBLIC_PORT` 프로필 변수를 알립니다. 다중 빌드 프로필은 엔드포인트 목록을 빌드마다 한 항목씩으로 바꿉니다.

기본 13개 빌드의 `all` 프로필에서는 단일 빌드용 노드 마이그레이션 패치 대신 `profiles/all/migration.patch.yaml`을 사용합니다. 각 `<build>.game-listener`를 지정하며, 빌드별 `<BUILD>_PUBLIC_PORT`를 공개 포트로 사용합니다. 기본값은 해당 빌드의 기본 포트입니다. 선택한 각 빌드의 선택적 `local.patch.yaml`에 `cluster-migration-build.patch.yaml`의 작업을 추가하고, 출발지 `channel: 60`과 입장 `channels: [60]`을 명시합니다. 접두사가 없는 행 ID를 사용하면 조합 과정에서 출발지와 입장 행이 해당 빌드의 `inventoryview` 하위 트리로 이동합니다. 노드, 방 디렉터리, 계정 소유권, 세션 및 쓰기 보호 행은 공유 프로필에 한 번만 마운트합니다. 노드 보고기와 방 디렉터리의 빌드 목록도 선택한 빌드로 설정합니다. 디렉터리 권한 서버에서 마이그레이션을 활성화하고 참여 노드마다 지원 빌드와 일치하는 데이터, 참가 및 방 디렉터리 범위를 설정합니다. 독립 데이터베이스는 별도 범위를 유지해야 하며 검색만으로 공유 계정 이동 권한을 얻을 수 없습니다. 독립 실행형 `all` 프로필은 변경되지 않습니다.

`home_unavailable_notice_enabled`의 기본값은 `true`이며 기본 알림 공급자가 필요합니다. 이전 패치는 검증된 알림 처리기가 없는 cn-406, cn-774, tw-454에서만 빌드 변수 `MIGRATION_HOME_NOTICE`로 이를 끕니다. 홈 복귀가 거부되면 항상 경고를 기록하며 플레이어는 계정 권한을 유지한 채 방문 노드에 남습니다.

유지된 플레이어의 입장 서비스는 빌드별 `inventoryview` 하위 트리에서 격리되므로 로비와 이전 입장 처리는 해당 빌드의 로그인 공급자만 공유합니다.

`ingame` 행에서 `room_admission_reservations: true`를 설정하면 빌드별로 해제 가능한 `IRoomAdmissionDirectory`를 등록하여 목적지 좌석을 예약합니다(Contracts 4.9.0). `room_admission_lifetime_ms`의 기본값은 10000이며 범위는 100–60000입니다. 예약 수는 방 좌석 수로 제한되고 단조 시계로 만료되며 방 생성 식별자와 계정을 고정합니다. 일반 참가와 봇은 예약 좌석을 사용할 수 없습니다. 취소, 만료, 방장의 좌석 잠금, 게임 시작, 방 폐쇄 및 플러그인 해제 시 미사용 예약을 반환합니다. 사용 시 비밀번호를 다시 확인하고 같은 계정과 빌드로 독립 인증된 게임 소유 연결 및 변경되지 않은 메뉴 또는 광장 상태를 요구한 뒤 일반 입장과 멤버 알림을 사용합니다. 예약은 인증이나 계정 소유권이 아니며 원격 방 클릭, 새 네이티브 소켓 인증 또는 원본 노드 소유권 이전을 아직 연결하지 않습니다. 단독 서버에서는 기본적으로 비활성화됩니다.

`launcher.http`의 `center: { enabled: false, mode: gateway }` 설정은 기본적으로 꺼져 있습니다. 명시적 `enabled: true`만 Center를 켜며 mode를 생략하면 `gateway`, 명시적 `native`는 서버 자체 Center를 사용합니다. `GET /v1/catalog`와 `GET /v1/servers/{build}`는 같은 최상위 `center: {enabled,mode}` 객체를 반환합니다. 이전 catalog에 Center가 없거나 mode만 있으면 비활성 상태입니다. Launcher는 catalog를 먼저 읽으며 비활성/native 모드는 게임 엔드포인트를 유지하고 디렉터리나 Gateway를 요구하지 않습니다. 활성 gateway 모드만 schema-1 디렉터리를 읽고 Center 설정의 일치를 확인합니다. Launcher 항목은 하나이며 게임의 기본 UI에서 서버를 선택합니다. 서버가 제공한 `automatic: true` 항목만 자동 배치를 켜고 `targets`가 후보 풀을 제한합니다. 자동 항목이 없으면 수동 전용이며 허가를 발급하지 않습니다. 선택 서비스가 등록되어도 비활성/native 모드는 허가를 발급하지 않으며 명시적 요청은 HTTP 409 `server_selection_unavailable`을 반환합니다. 선택 ID/이름과 물리 노드 ID/엔드포인트는 별개입니다. 이 설정 자체가 선택 후 인증이나 노드 간 방 입장을 구현하지는 않습니다.

수동 선택 항목은 대상 주소를 추측하지 않고 비활성 항목을 예약하도록 빈 `nodes` 목록을 허용합니다. 자동 선택 항목에는 여전히 구성된 후보가 필요합니다. Launcher API는 빈 항목을 유지하며, 클라이언트는 이를 비활성으로 유지하고 임의 주소를 확인하거나 연결해서는 안 됩니다.

선택 항목은 선택적 `short_name`을 지원합니다. 길이는 UTF-16 코드 단위 1..128개이며 공백만 있는 문자열, 제어 문자 및 짝이 없는 서로게이트는 허용하지 않습니다. 디렉터리와 실행 권한은 `short_name`으로 반환하며, 생략하면 전체 `name`을 사용합니다. 상태 갱신은 권한 발급 시의 두 이름을 유지합니다. 짧은 지역 이름은 전체 이름에서 추출하지 않고 명시적으로 설정하며, 이름은 엔드포인트나 인증 바인딩을 변경하지 않습니다.

선택 항목은 `sections`(예: Main, Test Server, Oversea Server)로 묶을 수 있으며 첫 번째 섹션이 기본 섹션입니다. 각 섹션에는 `id`, `name`, 선택적 `api_url`이 있습니다. `api_url`이 없는 섹션은 디렉터리를 게시하는 런처 API의 로그인을 공유하므로 한 번 로그인하면 게임 내 목록으로 해당 서버에 들어갈 수 있습니다. `api_url`이 있는 섹션은 그 API로 로그인하고 자체 티켓을 발급하며, 런처는 그 계정을 따로 보관합니다. 그룹화는 전부 아니면 전무입니다. 섹션을 구성하면 모든 선택 항목이 `section`에 섹션 하나를 지정해야 하고, 구성하지 않으면 어느 항목도 지정하지 않습니다. `GET /v1/servers/{build}`에는 `sections`와 각 선택 항목의 `section`이 추가됩니다. 노드는 `start`와 `end`(초와 시간대 오프셋을 포함한 ISO 8601, 둘 다 생략 가능), Markdown 형식의 `description`으로 `maintenance`를 선언할 수도 있습니다. 점검이 적용되는 동안 대상에 점검 기간이 포함되고, 자동 배치는 해당 노드를 제외하며, 런처는 해당 서버를 점검 중으로 표시하고 게임 내 목록에서 뺍니다. 런처는 마지막으로 읽은 디렉터리를 보관하므로, 게시 API에 연결할 수 없는 동안에도 모든 섹션을 나열하고 독립 섹션은 자체 API로 상태를 확인하며 나머지 서버는 오프라인으로 표시합니다.

`selectors[].nodes`는 표시할 노드를 지정하며 수동 항목은 노드가 없거나 하나만 갖습니다. `selectors[].automatic`은 임대가 유효하고 준비되었으며 드레인 중이거나 정원이 찬 상태가 아닌 후보만 반환합니다. 풀 구성원은 동일한 비어 있지 않은 `data_scope`를 선언해야 합니다. `nodes[].data_scope`와 `nodes[].join_scope`는 불투명한 관계 선언입니다. 빈 값은 공유나 참가 권한을 주지 않으며 같은 이름도 해당 기능을 구현하지 않습니다. `nodes[].room_directories`는 방 요약 공유를 독립적으로 제어하므로 우호 서버가 계정을 분리한 채 방 목록만 공유할 수 있습니다.

자동 선택 항목에는 권한 데이터베이스의 `persistent_domain_id`도 필요합니다. `SELECT REPLACE(domain_id, '-', '') FROM cluster_data_domain WHERE singleton_id = 1`로 읽으며 MySQL 마이그레이션 0035가 한 번만 초기화합니다. 권한 데이터베이스에서 먼저 마이그레이션한 뒤 작업 노드는 `auto_migrate: false`로 시작하고 같은 권한 데이터베이스에 연결하십시오. 각 하트비트는 요청 기한 내에 식별자를 다시 읽으며 일치하는 후보만 자동 풀에 들어갑니다. 잘못 설정된 노드가 정상 후보를 제거하지 않습니다. 같은 고정 데이터 범위의 수동 항목은 식별자가 다르면 목록에 유지되지만 오프라인으로 표시됩니다. 복원된 데이터베이스 복사본은 식별자를 유지하므로 이 검사는 설정 오류를 감지할 뿐 데이터베이스 인증이나 실시간 복제를 증명하지 않습니다. 독립 복사본은 배치를 활성화하기 전에 다른 식별자를 사용해야 합니다. 식별자 제공자가 없는 노드는 빈 `data_scope`로만 보고할 수 있고 자동 풀에 들어갈 수 없습니다.

등록은 세대가 구분된 임대를 만들고 증가하는 순번의 하트비트가 갱신합니다. 만료되면 자동 후보와 방을 제거하되 수동 항목은 오프라인으로 남깁니다. 준비 상태에는 호스트 준비와 등록된 게임 리스너가 필요합니다. 보고에는 인증된 로그인 수와 공개 게임 방 요약만 포함하며 비밀번호나 플레이어 신원은 제외합니다. 실제 라우팅 구현 전 원격 방의 `joinAllowed`는 항상 `false`입니다.

노드/항목/방 수, 본문 크기, 연결 및 기한에는 상한이 있습니다. `lease_seconds`는 `heartbeat_seconds + request_timeout_seconds`보다 커야 하며 잘못된 조합은 보고 실패로 처리합니다. `draining`은 자동 배치를 제외하고 수동 상태와 방 요약을 유지합니다. 검색은 공유 저장소, 전역 세션 권한, 원격 방 참가, 파티 연동이나 릴레이 이전을 제공하지 않습니다. 다중 노드에서 실제 플레이어를 받기 전에 각 기능을 구현하고 검증하십시오.

선택적 `persistence.mysql-account-ownership` 행은 계정 점유 기본 기능인 `IAccountOwnershipStore`를 제공합니다. 마이그레이션 0036를 적용한 후에만 `profiles/bundles/cluster-account-store.patch.yaml`을 탑재하고 `BFF_CLUSTER_ACCOUNT_CONNECTION_STRING`과 권한 데이터베이스 식별자를 설정하십시오. 데이터베이스 메모리에 맞게 `max_owners`를 제한하십시오. 각 점유는 풀링하지 않는 전용 연결에서 대기 없이 명명된 잠금을 요청합니다. 검증은 원래 잠금과 고정 식별자를 모두 확인하며, 잃은 점유는 자동으로 다시 획득하지 않습니다. 언로드는 진행 중인 획득을 기다리고 기존 점유를 닫습니다. 이 기본 기능은 아직 게임 로그인이나 저장소 쓰기를 보호하지 않으므로 이것만으로 공유 노드 로그인이 안전해지지 않습니다. 단독 서버 프로필은 이를 탑재하지 않습니다. 계정 획득은 네이티브 연결 수명을 소유하는 핸들을 반환합니다. 원격 SDK에는 이 결과의 어댑터가 없으므로 스키마는 획득 작업을 지원하지 않는다고 명시합니다.

선택적 `cluster.account-sessions` 행은 계정 점유를 게임 로그인에 연결합니다. 계정 저장소 패치 다음에 `profiles/bundles/cluster-account-sessions.patch.yaml`을 탑재하고 각 로비에 `require_account_ownership: true`와 `duplicate_login: reject_new`를 설정하십시오. 접속 승인 서비스가 없으면 활성화가 실패합니다. 세션은 열린 게임 연결에만 생기므로 그 수는 리스너의 연결 제한을 따르며, `verification_seconds`와 `verification_concurrency`는 백그라운드 검사를 제한합니다. 권한을 잃으면 연결을 닫습니다. 언로드는 대기 중인 접속을 취소하고 승인된 연결을 닫은 뒤 정리가 끝날 때까지 기다립니다. `IAccountSession` 기능은 점유 수명을 넘기지 않고 검증을 제공합니다. 이 계층은 진행 중인 저장소 쓰기나 캐릭터 생성을 격리하지 않습니다. 해당 쓰기 경로의 격리와 종료 대기가 구현되기 전에는 공유 운영 데이터베이스를 활성화하지 마십시오. 기본 단독 서버 프로필은 두 패치를 탑재하지 않습니다.

계정 인계에는 마이그레이션 0037과 디렉터리의 노드 식별자와 일치하는 `persistence.mysql-account-ownership`의 명시적 `node_id`가 추가로 필요합니다. 기본 빈 값은 일반 점유 기능을 유지하며 `IAccountHandoffStore`를 제공하지 않습니다. 출발 노드는 자신의 인계만 기록할 수 있으며, 데이터베이스는 기록된 목적지 노드의 인수와 출발 노드의 철회만 허용합니다. `cluster.account-sessions`는 해당 저장소가 있을 때만 `IAccountSessionHandoff`를 제공합니다. 원격 SDK는 네이티브 점유 핸들, 마이그레이션 IP 주소 또는 브로커 콜백 등록을 전송할 수 없으므로 어댑터가 제공될 때까지 해당 메서드를 명시적으로 지원하지 않습니다. 이 설정은 단독 서버 프로필에서 네이티브 마이그레이션을 활성화하지 않습니다.

선택적 `cluster.migration-broker`는 `cluster.node`와 같은 `node_id`, `directory_url`을 사용해야 하며 `access_key`는 해당 노드의 비공개 키입니다. 디렉터리에서 `migrations`를 활성화해야 합니다 (기본 false). 요청은 현재 임대 자격 증명과 snake_case JSON을 TLS 또는 보안 터널로 전송합니다. 비밀번호는 진단 로그에서 제외됩니다. 공유 계정 이동은 같은 참가 및 데이터 범위, 인증 기관과 실제 영구 데이터 영역 식별자가 필요합니다. 방문자는 명시적 참가 신뢰와 다른 데이터 범위가 필요합니다. 전송만 활성화해도 네이티브 이동이나 좌석 예약이 활성화되지는 않습니다. 가득 찬 수신함은 503, 중복 식별자나 오래된 임대는 409, 응답 시간 초과는 504를 반환합니다.

HTTP 제한 시간은 폴링 대기 및 콜백 제한보다 커야 합니다. 관리되는 작업 하나가 목적지 수신함을 폴링하며 송신 동시 실행 한도를 넘는 요청은 즉시 거부됩니다.

선택적 `cluster.migration-destination` 행에는 broker, arrivals, 하트비트 식별자와 계정 세션 인계 서비스가 필요합니다. `node_id`는 하트비트 식별자와 같아야 하며 `endpoints`에는 서로 다른 `{ client_build, listener_id, host, port }` 항목을 1..64개 지정합니다. host는 정식 DNS 이름이어야 합니다. 목적지는 요청마다 이를 해석하고 IPv4 주소를 요구합니다. 방 요청에는 해당 빌드의 `IRoomAdmissionDirectory`도 필요합니다. 엔드포인트 누락, 만료된 목적지 임대 세대, DNS 실패 시 준비를 거절합니다. 원래 서버로 돌아가는 요청은 방 좌석을 예약하지 않습니다. 이 행은 아직 네이티브 게임 연결을 인증하거나 원격 방 클릭을 활성화하지 않습니다.

필수 `listener_id`는 프로필 접두사를 포함한 목적지 전송 행의 정확한 ID입니다. 활성화 시 이 ID와 해당 빌드의 게임 프로토콜을 가진 가시적인 활성 리스너가 정확히 하나 있어야 합니다. 도착 기록은 이 ID를 보관하며 `ConnectionAcceptedEvent`에서 실제로 관찰한 연결을 확인한 뒤 소비됩니다. 관찰되지 않았거나 닫힌 연결, IP가 아닌 연결, 다른 리스너의 연결은 빌드, 계정 번호 및 주소가 같아도 기록을 소비할 수 없습니다. 거절된 시도는 올바른 연결을 위해 기록을 보존합니다. 이 검사는 계정 권한을 부여하지 않습니다. 네이티브 이전 처리기는 플레이어 상태를 불러오기 전에 계정 인계를 인수해야 합니다.

`arrival_lifetime_ms`의 기본값은 10000(100..60000), `cleanup_interval_ms`는 1000(100..10000), `operation_timeout_ms`는 5000(100..30000)입니다. 방의 `room_admission_lifetime_ms`는 도착 유효 기간과 준비 시간을 포함하도록 설정합니다. `cluster.migration-arrivals`의 `max_arrivals`는 기본 64, 범위 1..4096이며 대기 중인 도착과 정리를 기다리는 만료 기록이 용량을 공유합니다. 만료된 도착은 사용할 수 없습니다. 취소 실패는 기록하고 재시도하며 성공 전까지 용량을 유지합니다. 해제 시 작업 제한 시간 내에 남은 예약을 취소하고 실패를 보고합니다. 도착 기록을 성공적으로 가져간 소비자는 이후 입장 또는 예약 취소를 책임집니다.

`INodeLeaseSource`와 `IMigrationArrivalCleanup`은 공유 Contracts 4.12.0 서비스이므로 독립적으로 로드한 플러그인에서도 같은 인터페이스 식별자를 사용합니다. 임대 기록은 SDK로 직렬화할 수 있지만 bearer 토큰은 비밀이며 진단 문자열에서 제외됩니다. 도착 정리 기록에는 IP 주소가 있고 완료 작업은 객체 식별자를 유지해야 하므로 네이티브 어댑터가 필요합니다.

선택적 `profiles/bundles/cluster-account-write-fencing.patch.yaml`에는 계정 저장소 및 세션 패치, 마이그레이션 0036, 계정 점유를 요구하는 로비가 필요합니다. 이 패치는 `core.packet-router.decoratable: true`와 `persistence.mysql.require_account_write_authority`를 설정하고 `cluster.account-mutations`를 탑재합니다. 명시적으로 장식을 켜지 않은 일반 라우터는 직접 호출을 유지합니다. `IAccountMutationScopes`는 변경되지 않는 점유 핸들을 원래 게임 세션에 연결합니다. 패킷 처리는 해당 세션을 선택하며 플레이어별 경기 정산과 보상 카드 지급은 수신자의 원래 세션을 선택합니다. 지연된 이전 작업은 새 세션의 권한을 빌릴 수 없습니다. 보호된 MySQL 쓰기는 플레이어 상태를 변경하기 전에 동일한 연결과 트랜잭션에서 권한 행을 잠그고 검증합니다. 점유 이전은 이미 승인된 트랜잭션의 종료를 기다립니다. 권한이 없거나 교체되면 다시 획득하지 않고 실패합니다. 새 계정의 캐릭터 생성은 원자적으로 초기화하며 기존 계정 변경에는 해당 점유가 필요합니다. Contracts 4.4.0은 이 네이티브 수명 및 트랜잭션 인터페이스를 제공하며 원격 SDK는 호출을 명시적으로 거부합니다. 이 기능은 공유 저장소를 구성하거나 다른 플러그인을 자동 보호하거나 노드 간 방 입장을 구현하지 않습니다. 공유 운영 데이터를 활성화하기 전에 나머지 모든 쓰기 경로를 검토하십시오. 단독 서버 프로필은 이 패치를 탑재하지 않습니다.

## 문제가 생기면

- **환경 변수 누락으로 구성이 실패합니다.** 오류 메시지가 변수 이름을 알려 줍니다. `.env`(또는 프로세스 환경)에 추가하거나, 빈 값이 유효한 곳에서는 `${VAR:-default}` 형식을 사용하십시오.
- **패치가 알 수 없는 행을 가리킵니다.** 프로필과 패치 목록이 어긋난 것입니다. 패치를 적용하지 않은 프로필이나 해당 행을 제공한 번들에서 `--dump-config`로 행 id를 확인하십시오.
- **게임 프로필이 클라이언트 데이터 메시지와 함께 활성화에 실패합니다.** 메시지에 나온 `data`/`dataraw` 디렉터리가 없습니다. 해당 빌드 id의 디렉터리를 준비하거나 `management`를 사용하십시오.
- **리스너가 바인딩할 수 없습니다.** 다른 프로세스가 포트를 점유하고 있습니다. 빌드별 포트 변수를 바꾸거나 해당 프로세스를 중지하십시오.

순서대로 확인하는 목록은 [문제 해결](troubleshooting.md)을 참고하십시오.

## 라운드 취소와 시작 규칙

다음 `ingame` 행 옵션은 모든 빌드에 적용됩니다. 라운드를 불러오거나 플레이하는 중에 연결이 끊긴 플레이어가 있으면 라운드가 취소됩니다. 결과는 표시되지 않으며 남은 모든 플레이어는 대기실에서 나간 플레이어와 같은 방식으로 광장으로 이동합니다. `cancel_round_on_disconnect`(기본값 `true`)로 이 동작을 끌 수 있으며, 그러면 연결이 끊긴 플레이어만 나갑니다. 스스로 방을 나가거나 `!plaza`를 입력하면 일반적으로 나머지는 계속 플레이합니다. 좀비 탈출을 활성화한 경우 Lua 방장이 나가면 보상 없이 라운드를 취소합니다. `load_timeout_ms`(기본값 `60000`, `0`은 제한 없음, 최대 `600000`)는 그때까지 모든 플레이어가 불러오기를 마치지 못하면 같은 방식으로 라운드를 취소합니다. 가장 느린 클라이언트의 맵 불러오기와 매치 연결 준비 시간보다 크게 두십시오.

좀비 모드에서는 현재 있는 모든 플레이어가 감염되어야 좀비가 이깁니다. 연결이 이미 닫힌 플레이어는 생존자로 세지 않습니다.

두 가지 시작 규칙은 기본적으로 꺼져 있습니다. `start_min_players`(0–32, 좌석과 AI 플레이어 합계)는 인원이 부족하면 방장의 시작을 거부합니다. `start_requires_team_balance`는 레드/블루 팀 모드에서 `assign_spawn_teams_on_start`가 팀 없는 플레이어를 배치한 뒤 두 팀 인원 차이가 한 명보다 크면 방장의 시작을 거부합니다. 그렇지 않으면 팀 없는 플레이어는 레드로 셉니다. 클라이언트에는 이 규칙에 맞는 거부 사유가 없으므로 서버는 로그만 남기고 방은 계속 대기합니다. 네이티브 자동 시작은 검사하지 않습니다.

## 최신 계열 대기방 강제 퇴장

`dialect.rooms.config.room_kicking`의 기본값은 `false`입니다. kr-1256, cn-774, tw-454에서 활성화하면 검증된 닉네임 요청과 퇴장 알림이 공통 방장 권한 로직에 연결됩니다. 대기 중인 방의 방장만 방 안의 다른 플레이어를 내보낼 수 있습니다. 좌석 제거 전에 알림을 보내며, 퇴장한 플레이어는 광장으로 돌아갑니다. 이 옵션은 `modern_rooms: true`가 필요하고 `plaza_only`와 함께 사용할 수 없습니다. 필요한 기본 패킷 이름이나 구조가 없으면 활성화에 실패합니다.

`dialect.rooms.config.npc_rounds`는 해적 모드가 기다리는 현대 클라이언트 방장의 기본 웨이브 관리자에 응답합니다. kr-1256 번들에서 기본으로 켜져 있습니다. 해적 모드 방에서는 방장의 웨이브 시작, 웨이브 종료, 몬스터 생성 표 응답을 모든 멤버에게 보내고, 전체 웨이브 종료 응답은 방장에게만 보냅니다. 다른 모드에서는 이 요청을 무시합니다. 일반 대전의 몬스터 생성 요청은 형식만 검사하고 아직 전달하지 않습니다. 전송 방식이 아직 확인되지 않았기 때문입니다. 초기 튜토리얼도 같은 바인딩을 사용하며 여전히 혼자 플레이하는 방장에게만 응답합니다. 이 옵션은 대전 바인딩이 있는 `modern_rooms: true`가 필요합니다.

단일 빌드의 격리 시험에서는 `--patch tools/local-checks/isolated-memory.patch.yaml`에 더해 `--patch profiles/bundles/modern-room-kicking.patch.yaml`을 지정합니다. `all` 배포에서는 패치의 `set` 작업을 대상 빌드별로 Git에서 제외된 `local.patch.yaml`에 복사하고, 접두사가 없는 `dialect.rooms` 행 ID를 사용합니다. 실제 클라이언트 승인 전에는 옵션을 꺼 두십시오. 기존 레거시 강제 퇴장 바인딩은 이 옵션의 영향을 받지 않습니다.

## 형식 구분 빠른 매칭

해당 기능이 검증된 빌드에서는 `dialect.rooms.config.quick_matching`이 기본 매칭 요청을 등록합니다. `quick_match_default_mode_id`는 공통 매칭 모드를 선택합니다(0–65535, 기본값 0은 요청 거부). 형식 1은 매칭을 시작하고 형식 2는 갱신하며, 서로 다른 기본 패킷 꼬리를 모두 검증합니다. 파티 참가와 목록 항목 요청은 해당 흐름이 구현될 때까지 기본 거부 응답을 반환합니다. 제공되는 최신 계열 프로필에서는 실제 클라이언트 검증 전까지 이 옵션이 꺼져 있습니다.

## 기본 서버 선택 후 로그인 연결

선택 항목 `dialect.messages.config.center_migration_prelogin`의 기본값은 `false`이며 일반 로그인이 필요합니다. kr-1256에서는 `protocol.config.pre_handshake_opcodes: [gcpReqMoveInto]`도 함께 설정해야 패치 요청 전의 새 서버 선택 연결을 허용합니다. 어댑터는 두 워드 본문의 정확한 길이, 보존된 식별자 0, 단계 플래그 0 또는 1을 검증하고 이미 인증되었거나 반복된 요청을 거부한 후 기본 패치 응답을 보내 일반 로그인을 계속합니다. `IInitialHandshakeContinuation`은 현재 패킷 디스패치 동안만 유효하며 핸들러가 성공적으로 반환한 경우에만 적용됩니다. 버전 검증 표시, 티켓 사용, 플레이어 식별자 등록 또는 마이그레이션 승인을 제공하지 않습니다. 로비는 여전히 유효한 일회용 Launcher 티켓을 요구해야 하며 계정 이름으로 대체할 수 없습니다. 기본 단일 서버 프로필은 변경되지 않습니다. 서버 와이어 테스트와 실제 클라이언트 검증은 별개입니다.

`dialect.messages.native_migration`의 기본값은 `false`입니다. `center_migration_prelogin`과 네이티브 이동 요청 라우터 하나를 공유합니다. 식별자가 0이면 명시적인 사전 로그인 옵션이 필요하며, 0이 아니면 `MoveIntoRequested`로 전달합니다. 전달만으로 초기 핸드셰이크 제한이 해제되거나 계정 소유권이 부여되지는 않습니다. 이 옵션은 표로 검증한 이동 응답과 연결 전환 메시지도 제공합니다. 확인 및 완료 메시지는 opcode 표에 선언된 경우에만 등록됩니다. 목적지 허용 처리기는 리스너에 연결된 도착 기록을 확인하고 계정 권한을 인수한 뒤 플레이어 상태를 설치해야 핸드셰이크 연속 처리를 요청할 수 있습니다. 목적지 허용은 아래의 선택적인 `cluster.migration-admission` 행이 제공합니다. 출발 노드 조정은 `cluster.migration-source`가 제공하며 배포 연결은 명시적으로 활성화해야 합니다.


선택적인 `cluster.migration-admission` 행은 대상 예약 후 공유 계정의 방 이동을 조정합니다. 해당 빌드의 로비와 방 서비스가 보이는 위치에 배치합니다. `lobby.native_migration`(기본 false)과 `dialect.messages.native_migration`을 활성화해야 하며, 로비는 계정 소유권, 영구 저장소의 기존 계정 조회, 저장형 인벤토리와 지갑, 캐릭터 생성 미리보기 비활성화를 요구합니다. 별도 조정 플러그인은 로비와 방 서비스의 순환 의존성을 방지합니다. Contracts 4.16.0은 `IRetainedPlayerAdmission`을 추가합니다. 설치 결과는 네이티브 플레이어 상태이므로 원격 SDK 어댑터는 없습니다.

`channels`에는 해당 빌드에서 검증된 네이티브 채널 바이트를 명시해야 합니다. 목록에 없는 출발 채널은 거부됩니다. kr-812에서는 50, 60, 80만 kr-812 sub_A4A440의 무조건 허용 분기를 통과하며 나머지 명명된 채널은 클라이언트 권한이 필요합니다. 현대 빌드의 로그인 채널을 레거시 배포에 복사하지 마세요. `max_migrations` 기본값은 64(1..4096), `timeout_ms`는 10000(100..60000), `cleanup_interval_ms`는 1000(100..10000)입니다. 승격 대기와 정리 실패는 같은 용량을 사용합니다. 만료, 연결 종료, 임대 변경 시 예약과 계정 점유를 해제하며 정리 실패는 재시도할 때까지 용량을 유지하고 언로드 시 남은 실패를 보고합니다.

입장은 리스너와 주소에 연결된 일회성 도착 기록 및 대상 임대를 확인하고, 플레이어 모델의 양수 부호 있는 정수 범위를 벗어난 ID를 거부합니다. 기존 계정 조회와 인벤토리·지갑 로딩 전에 정확한 계정 인계를 확보합니다. 계정을 생성하거나 일일 로그인 보상을 반복하지 않습니다. 플레이어 상태 설치와 승격 전송 성공 후에만 초기 핸드셰이크를 계속합니다. 승격 확인이 필요한 빌드는 확인 전까지 인증 단계에 머무르며 확인 후 승격을 완료하고 일반 방 입장을 수행합니다. 다른 빌드는 즉시 승격 후 입장합니다. 홈 복귀는 아래의 선택적 메인 메뉴 입장을 사용하며 방문자는 계속 거부됩니다. 방문자와 배포 연결은 아직 미완성이며 기본 프로필은 이 행을 사용하지 않습니다. 실제 클라이언트 검증도 필요합니다.

선택적인 `cluster.migration-source` 행은 다시 검증한 원격 방 클릭을 네이티브 출발에 연결합니다. 이동 브로커, 노드 임대, 계정 세션 인계, 온라인 플레이어 디렉터리 및 `client_build`에 맞는 단일 `ChannelMoveOffered` 전송기가 필요합니다. `channel`(1..255)을 명시해야 하며 목적지에서도 허용해야 합니다. `max_migrations` 기본값은 64(1..4096), `operation_timeout_ms`와 `migration_timeout_ms`는 10000(100..60000), `cleanup_interval_ms`는 1000(100..10000)입니다. 기본 프로필은 이 행을 사용하지 않습니다.

현재 로그인을 소유한 메인 메뉴 또는 광장 게임 연결만 출발할 수 있습니다. 방 흐름은 장면 잠금을 유지하며 파티 디렉터리는 원자적 단독 예약을 지원해야 합니다. 기존 초대를 취소하고 정리 전까지 해당 플레이어의 새 초대와 파티 가입을 거부합니다. 단독 예약의 상한은 설정된 대기 초대 용량입니다. 준비 전에 플레이어는 `Migrating` 단계에 들어갑니다. 목적지가 정확한 방 인스턴스를 예약한 뒤 출발지가 계정 쓰기 권한을 넘기고 표에 정의된 네이티브 이동 제안을 보냅니다. 시간 초과, 응답 유실, 전송 실패 또는 연결 무효화 시 정확한 목적지 요청을 취소하고 해당 인계만 철회합니다. 목적지가 이미 인수했다면 일반 계정 권한을 다시 획득하지 않고 출발 연결을 닫습니다. 정리 실패는 용량과 단독 예약을 유지하여 재시도합니다. Contracts 4.17.0은 출발 인터페이스와 네이티브 제안을 추가하며 소유된 파티 예약에는 원격 SDK 어댑터가 없습니다.

공유 계정 이동은 여러 방을 방문해도 최초 로그인 노드와 네이티브 채널을 유지합니다(Contracts 4.18.0). 출발 플러그인에는 `IMigrationTargetDirectory`가 필요하며 `home_unavailable_notice_enabled`가 true이면 단일 네이티브 `ServerNotice` 전송기도 필요합니다. 브로커는 인증된 조회로 홈 노드의 현재 임대를 확인하며 준비 상태, 용량, 참가 범위, 영구 데이터 도메인과 계정 발급자를 다시 검사합니다. 조회 자체는 도착 기록이나 계정 권한을 부여하지 않습니다. 홈 노드가 거부하거나 사용할 수 없으면 현재 노드에 머무르며 알림이 활성화된 경우 `home_unavailable_notice`(1..512자)를 표시합니다.

InGame의 `return_on_leave` 기본값은 `home`이며 `stay`는 방문 노드에 머무릅니다. `return_delay_ms` 기본값은 1500(0..60000)입니다. 정상 방 퇴장 정리와 경기 퇴장 정산을 마친 뒤 복귀를 기다립니다. 대기 중에는 장면 잠금을 유지하지 않습니다. 연결 종료, 연결 교체 또는 장면 세대 변경은 이전 복귀를 취소하며 이후 광장 퇴장으로 다시 시도할 수 있습니다. 홈 InGame에서 `home_migration_admission: true`를 설정하고 `room_admission_reservations`와 네이티브 메인 메뉴 전송기를 제공해야 합니다. 홈 준비는 방 좌석을 예약하지 않습니다. 같은 계정 인수와 연결 승격 후 보존된 장비로 출발 노드의 유휴 장면을 복원하고 튜토리얼을 다시 제안하지 않습니다. 홈 요청은 `home_scene` (`MainMenu` 또는 `Plaza`)을 전달하며 방 요청은 항상 `MainMenu`를 사용합니다. 광장에서 귀환하면 기존 네이티브 광장 설치를 사용하여 메인 메뉴로 다시 이동하지 않습니다. 광장 인코더가 없는 빌드는 메인 메뉴로 복귀합니다. Contracts 4.21.0은 `MigrationRequest`와 `IMigrationHomeAdmission.EnterAsync`에 장면 매개변수를 추가합니다. 파티 디렉터리가 있으면 목적지는 승격 확인과 장면 설치까지 원자적 단독 예약을 유지합니다. 정리 실패 시 자원 해제까지 예약을 유지합니다. 기본 프로필은 배포와 실제 클라이언트 검증 전까지 비활성화 상태입니다.

파티장은 파티와 함께 이동합니다. 파티장이 원격 방으로 출발하거나 원래 서버로 돌아갈 때, 같은 빌드에서 메인 메뉴나 광장에 있는 모든 온라인 파티원은 파티장의 이동 제안 직후 같은 목적지의 제안을 받습니다. 두 클라이언트 계열 모두 스스로 요청하지 않았어도 수락된 이동 제안을 받으면 대기 연결을 엽니다. 파티원은 단독 예약 없이 이동하며, 원래 서버 복귀는 원래 서버가 파티장과 같은 파티원만 데려갑니다. 방이나 라운드에 있는 파티원, 또는 목적지가 거절한 파티원(예: 방이 가득 참)은 자기 노드에 남아 로컬 파티를 유지하며, 파티장의 이동은 취소되지 않습니다. 파티장이 아닌 파티원은 혼자 출발할 수 없고 스스로 복귀를 시작하지도 않습니다. 각 요청은 `party_leader`에 파티장을 적고 단독 이동에서는 노드 전송에서 이 필드를 생략합니다. 목적지는 `IPartyDirectory.RejoinAsync`로 도착한 각 플레이어를 이미 도착한 파티장의 파티에 다시 넣으며 도착 순서는 상관없고, 짝이 없는 도착은 도착 기한이 지나면 버립니다. Contracts 4.23.0이 둘을 추가합니다. 아직 네이티브 클라이언트에서 확인되지 않았습니다.

디렉터리의 `nodes[].native_migration_builds` 기본값은 빈 목록입니다. 네이티브 출발, 리스너에 연결된 목적지 입장 및 연결 승격 처리기가 배포되고 클라이언트 경로를 검증한 빌드만 나열합니다. 항목은 중복 없이 설정된 엔드포인트를 지정해야 합니다. 디렉터리에서 `migrations: true`를 켜도 양쪽 노드가 빌드를 명시해야 공유 계정 원격 방을 참가 가능으로 표시하거나 이동 요청을 수락합니다. 홈 복귀에도 같은 검사가 적용됩니다. 참가 표시는 유효한 양쪽 임대, 준비된 빌드, 목적지 여유 용량, 일치하는 참가·방 디렉터리 범위, 동일한 영구 데이터베이스 ID와 계정 발급자도 요구합니다. 목록은 좌석 예약이나 계정 권한을 부여하지 않으며 준비 단계에서 경로를 다시 확인합니다. 방문자 입장이 구현되기 전에는 독립 데이터 도메인은 목록 검색만 제공합니다.

예약한 방이 플레이어 입장 전에 닫히거나 경기를 시작하거나 비밀번호를 변경하면, 입장 조정기는 좌석을 해제하고 대상 노드의 계정 쓰기 권한을 유지한 채 기존 플레이어 상태로 메인 메뉴를 설치합니다. `cluster.migration-admission`은 빌드마다 정확히 하나의 `IMigrationRoomRecovery` 서비스를 요구하며, InGame은 `home_migration_admission: true`일 때 이를 제공합니다. 복구는 원래 핸드셰이크 메시지 처리가 끝난 후 `return_on_leave`와 `return_delay_ms`를 적용합니다. 그동안 장면이 바뀌면 귀환을 취소하고, `stay`는 플레이어를 대상 노드에 남깁니다. 복구 작업은 `max_migrations` 용량을 공유하며 입장 잠금 밖에서 실행됩니다. 메인 메뉴 설치에 실패하면 연결을 닫고 획득한 자원을 해제합니다. Contracts 4.19.0에 이 복구 서비스가 추가되며 기존 메인 메뉴 메시지 형식은 유지됩니다.

방 서비스는 `IRemoteRoomMigrationEndpoint`(Contracts 4.20.0)를 제공하고, `cluster.migration-source`는 해당 `client_build`의 엔드포인트 하나에 연결됩니다. 방 서비스가 하트비트에 의존하는 이동 소스를 기다리지 않으므로 방 공개, 노드 하트비트 및 이동 기능을 함께 시작할 수 있습니다. 중복 소스나 일치하는 방 엔드포인트의 부재는 활성화 오류입니다. 소스를 해제할 때 새 원격 입장을 거부하고 진행 중인 입장 및 원래 서버 복귀 호출이 끝날 때까지 기다린 후 소스를 해제합니다. 소스 또는 하트비트를 다시 로드해도 방 서비스는 유지됩니다. 추가 프로필 행은 필요하지 않으며 이동 기능을 기본으로 활성화하지 않습니다.

레거시 방 어댑터는 연결 준비와 자동 튜토리얼을 따로 제어합니다. `dialect.rooms.config.tutorial_move_in`은 기본 메뉴 이동 응답을 활성화하고, `automatic_tutorial`(기본값 `true`)은 뒤따르는 자동 튜토리얼 알림을 별도로 제어합니다. 최초 튜토리얼을 건너뛰는 테스트 배포에서는 `automatic_tutorial: false`로 설정해도 방 동작에 필요한 연결 준비 응답은 유지됩니다. 로그인별 `OfferTutorial: false`도 알림만 억제합니다.

## 선택적 방 객체 경제

최신 방 프로토콜은 기존 버전과 같은 선택적 객체 경제 바인딩을 사용합니다: `supply_items`, `lucci_drops`, `star_items`, `horde_lottery`, `instant_revival`, `pve_points`, `rescue_missions`, `counted_pve_items`. 각 바인딩은 검증된 패킷 기능을 요구하며 지원하지 않는 옵션은 활성화에 실패합니다. kr-1256, cn-774, tw-454 프로필은 보급품, 협동 모드 수량제 아이템과 실시간 PvE 점수를 활성화합니다. 모드 3은 자체 활성 아이템 풀과 일반 보유 슬롯 두 개를 사용합니다. 모드 16은 수량제 슬롯 세 개를 초기화합니다. 슬롯의 아이템 선택과 즉시 적용하는 나머지 협동 모드 아이템은 각 빌드의 활성 ItemSpec 데이터에서 선택한 서버 정책이며 설정할 수 있습니다. 최신 지도 보고는 벡터 14개와 바이트 크기의 팀 값을 사용합니다. 생성 본문은 37바이트, 투하 본문은 33바이트입니다. KR 슬롯 전환 응답은 워드 세 개이며 CN과 TW는 네 번째 결과 워드를 포함합니다. 실제 클라이언트 검증은 아직 남아 있습니다.


`dialect.rooms.config.weapon_objects`의 기본값은 `false`입니다. 검증된 `weapon_objects` 기능을 선언한 빌드에서만 무기 드롭 생성과 획득을 바인딩하며 현재 대상은 cn-324입니다. 공통 `ingame` 행의 `max_weapon_objects_per_round`는 라운드 전체 생성 수를 제한합니다(기본 256, 범위 1..65536). 객체 식별자는 `weapon_object_id_base` 다음부터 할당합니다(기본 `0x64000000`). 이 범위는 플레이어 및 다른 라운드 객체의 식별자와 분리해야 합니다. 획득은 보고한 플레이어 자신의 캐릭터에만 허용되며 객체마다 한 번만 처리합니다. 라운드 초기화 시 상태를 지웁니다. 자동 검사가 실제 클라이언트 검증을 의미하지는 않습니다.

### 클라이언트 표시 레벨

각 클라이언트 빌드는 자체 `Images/Icons/LevelMark.smf`의 프레임 수를 기준으로 `packets/builds.yaml`에 `display_level_max`를 선언합니다. 플레이어 상태, 파티, 광장 및 방 좌석, 플레이어 정보, 대기 목록, 결과를 전송할 때 상한을 넘는 레벨은 해당 빌드의 최대 레벨로 표시합니다. 저장된 레벨, 경험치와 보상 계산은 원래 값을 유지합니다. 예를 들어194레벨은 cn-324와 cn-406에서180으로, kr-812에서는194로 표시합니다. 새 빌드는 자체 리소스가 지원하는 양의 정수 상한을 선언해야 합니다.

### 초기 임시 대기실 장비

`dialect.rooms.config.room_inventory_selection`의 기본값은 `false`이며 같은 이름의 패킷 빌드 기능이 필요합니다. CN2011/CN2012 프로필은 이를 켜고 방 행을 각자의 격리된 `clientdata` 행 아래에 둡니다. 이 옵션은 초기 `gcpRoomChangeInventory` / `gspRoomChangeInventory` 경로를 `weapon_presets`와 별도로 연결합니다. CN2011은 `room_inventory_selection_count`에 선택값 네 개, CN2012는 다섯 개를 선언하며 `room_inventory_selection_fields`는 `UserSlot`의 네이티브 캐릭터 및 무기 short 필드 이름을 지정합니다. 바인딩은 해당 빌드의 클라이언트 데이터를 요구하고 `Config/FighterConfig.xml` 및 `Config/WeaponSpecDetail.xml`에서 캐릭터와 무기 사양 ID를 검증합니다. 알 수 없는 값은 거부하며 용도가 확인되지 않은 마지막 선택값은 비어 있는 값만 허용합니다. 플레이어는 준비하지 않은 자신의 대기실 좌석만 변경할 수 있습니다. 선택값은 방 스냅샷에 유지되지만 소유 아이템을 지급하지 않으며 일반 장비 변경이나 퇴장 시 폐기됩니다. 네이티브 버튼 표시 여부는 별개입니다. CN2012는 초기화할 때 이전 버튼을 숨기므로 서버 경로 연결만으로 사용 가능한 네이티브 진입점이나 실제 클라이언트 검증을 확정하지 않습니다.

### 대장전

`dialect.rooms.config.captain_mode`의 기본값은 `false`이며 각 빌드에서 독립적으로 검증한 `captain_mode` 기능이 필요합니다. 지원 빌드는 kr-812, cn-717, id-400, id-1809, cn-404, cn-408, cn-706, kr-1256, cn-774, tw-454입니다. 완전한 legacy 또는 modern 라운드 어댑터를 사용하며 메뉴, 브라우저, 광장 및 대기실 전용 어댑터에서는 거부됩니다. 모드 20은 경기 시작 후 각 팀의 연결된 플레이어 중 무작위로 대장 한 명을 지정합니다. 변신, 무기 및 기술은 클라이언트가 처리합니다. 대장 본인의 사망 보고를 받으면 살아 있는 팀원에게 대장을 넘기며, 후보가 없으면 공통 부활 절차를 기다립니다. 일반 처치와 대장 처치는 같은 사망 기록을 사용하므로 한 번만 득점합니다. 대장 처치는 일반 팀 점수 1점을 주며 공통 제한 시간, 팀 점수, 무승부, 결과 및 보상 규칙을 따릅니다. 대장이 떠나면 살아 있는 팀원이 있을 때 교체합니다. 이 옵션은 `gspCaptainEvent`를 보내거나 검증되지 않은 빌드를 활성화하지 않으며 실제 클라이언트 검증을 의미하지 않습니다. `ingame.config.captain_ultra_item_kind`(legacy 번들 104, 0이면 끔)를 설정하면 현재 대장의 ULTRA 요청에 그 대장에게만 응답하며, 이후 클라이언트가 직접 다른 플레이어에게 ULTRA를 보여 줍니다. 다른 플레이어나 쓰러진 대장의 요청에는 응답하지 않고 임명을 반복하지 않습니다.

### 레아 캐릭터 기술

`dialect.rooms.config.rhea_character_skill`의 기본값은 `false`입니다. 해당 빌드의 `rhea-character-skill.patch.yaml`을 적용하면 kr-1256, cn-774 또는 tw-454의 검증된 변신 교환을 활성화합니다. 완전한 modern 라운드 바인딩과 해당 빌드의 네이티브 기능이 필요합니다. 현재 캐릭터 아이템 300029를 착용한 플레이어만 현재 라운드와 생명의 자기 액터에 변신을 요청할 수 있습니다. 허용된 변경은 본인과 방 참가자에게 전달됩니다. 중복 활성화는 무시하고 이미 비활성 상태인 종료 요청은 본인에게만 확인합니다. 사망, 부활과 전환은 저장된 변신 상태를 지웁니다. 충전과 종료 시점은 네이티브 클라이언트가 관리합니다. 이 옵션은 서버의 시간 강제 검증을 추가하거나 실제 클라이언트 승인을 의미하지 않습니다.

### 폭파 경기

`dialect.rooms.config.bomb_mission`은 검증된 기본 폭탄 동작과 결과 바인딩을 활성화합니다. `ingame.config.bomb_round_series`는 공격 진영을 라운드마다 교대하고 승리 횟수를 처치 점수와 별도로 유지합니다. legacy 형식은 3전 2선승, kr-1256, cn-774, tw-454는 5전 3선승입니다. 두 옵션의 기본값은 `false`이며 지원 빌드는 kr-812, cn-717, id-400, id-1809, cn-404, cn-408, cn-706, kr-1256, cn-774, tw-454입니다. 공통 결과 처리와 검증된 연속 라운드 입장 전송기가 필요합니다. 해당 `profiles/<build>/bomb.patch.yaml`을 적용하면 두 옵션을 활성화하고 모드 19를 일반 부활에서 제외합니다. 이 제외에는 관전 지원이 필요합니다. modern 활성화 패치는 모드 19와 20을 결과 점수판 선택에도 포함합니다. CN2013 cn-406의 모드 팩터리에는 두 전용 분기가 없어 제외되며 다른 CN2013 개정판에 대한 결론은 아닙니다.

`dialect.rooms.config.extreme_racing`의 기본값은 `false`이며 검증된 `extreme_racing` 빌드 기능(현재 kr-1256만 해당)과 `modern_rooms` 및 라운드 바인딩이 필요합니다. cn-774와 tw-454에는 검증된 타이머, 라운드, 기록, 골인, 코인 및 체크포인트 테이블 행이 있지만, 전체 라운드 검증이 끝날 때까지 레이싱 기능은 비활성 상태로 이 옵션을 거부합니다. `profiles/kr-1256/extreme-racing.patch.yaml`을 적용하면 활성화됩니다. 그러면 모드 24는 `ingame.config.extreme_racing_rounds`개의 레이스 라운드(1~5, 기본값 3)를 진행합니다. 각 라운드는 레이스 시계(`extreme_racing_round_ms`, 기본값 180000)를 시작합니다. 첫 번째 골인이 결승 카운트다운(`extreme_racing_finish_countdown_ms`, 기본값 10000)을 시작하며, 카운트다운이나 레이스 시계가 끝나거나 연결된 모든 플레이어가 완주하면 라운드가 끝납니다. 완주자는 순위에 따라 `extreme_racing_place_points` 점수(기본값 10, 8, 6, 5, 4, 3, 2, 1)를 받고, 레이스 기록판에 라운드 점수와 누적 점수가 표시되며, 라운드 사이에는 `extreme_racing_intermission_ms`(기본값 5000, 1000 초과) 동안 쉽니다. 마지막 라운드가 끝나면 공통 결과가 한 번만 실행됩니다. 점수가 더 높은 팀이 이기며, 방이 두 팀이 아니면 점수가 가장 높은 플레이어가 이깁니다. 공통 라운드 제한 시간은 레이스를 끝내지 않습니다. 체크포인트 통과는 중계되어 모든 플레이어의 진행 표시가 이동하며, 표시와 부활 지점은 클라이언트가 직접 배치합니다. 서버 오브젝트 목록이 필요한 맵 오브젝트는 아래의 별도 초기화 옵션으로 구성합니다. 라운드 수, 시계와 점수는 서버 정책이며 실제 클라이언트 검증은 아직 완료되지 않았습니다.

서버는 실제 조작자, 팀, 현재 라운드를 기준으로 설치, 취소, 해제를 검증합니다. 네이티브 방장 클라이언트가 폭발 및 목표 결과를 보고하며, 일반 경기 시간이 끝나도 설치된 폭탄의 자체 타이머는 유지됩니다. 각 라운드는 공통 로딩, 캐릭터 생명 및 취소 처리를 사용합니다. 같은 경기 식별자를 유지하여 경기 종료 후 보상을 한 번만 정산합니다. 한 팀 전체가 자발적으로 나가면 진행하지 않은 라운드 승수를 추가하지 않고 경기 기권으로 처리하며, 기존 연결 끊김 취소 정책은 유지됩니다. 이 옵션은 검증되지 않은 빌드를 켜거나 실제 클라이언트 검증을 확정하지 않습니다.

### 레이싱 맵 초기화

`dialect.rooms.config`와 `ingame.config`의 `extreme_racing_initialization`은 모두 기본값이 `false`이며 기존 레이싱 교환과 함께 양쪽에서 활성화해야 합니다. 현재 런타임 기능은 kr-1256만 지원합니다. 패킷 테이블은 cn-738, cn-742, cn-774, tw-454도 설명하며, 돌 제거기 필드가 없는 초기 두 맵 형식도 구분합니다. 테이블 항목만으로 해당 빌드의 게임플레이가 활성화되지는 않습니다.

`ingame.config.extreme_racing_stages`에 명시적인 맵 정책을 설정합니다. 각 항목에는 `stage_directory`, 양수인 `first_cannon_identity`, `first_coin_identity`, `first_stone_disposer_identity`, `coin_variant: 0`, 그리고 원본 코인 helper의 숫자 접미사 순서대로 각 코인의 1부터 시작하는 라운드를 지정하는 `coin_rounds`가 필요합니다. 맵의 `SavePoint/StageCount`는 `extreme_racing_rounds`와 같아야 합니다. 대포와 제거기, 코인, 돌의 식별자 범위는 서로 겹치지 않고 플레이어 actor 식별자 영역보다 작아야 합니다. 해당 `Maps/<stage_directory>/option.ini`와 `track.wb`를 가져옵니다. helper 누락, 식별자 중복 또는 불완전한 코인 라운드 설정은 활성화를 실패시킵니다.

리소스 한도는 `extreme_racing_maximum_file_bytes`(기본값 8388608, 범위 8..67108864), `extreme_racing_maximum_helpers`(4096, 1..65536), `extreme_racing_maximum_objects`(1024, 1..4096)이며 서로 다른 맵 정책을 최대 128개 허용합니다. 맵에 입장할 때마다 시작 카운트다운이 끝나기 전에 로딩된 각 참가자에게 동일한 오브젝트 식별자를 한 번 보냅니다. 일부 전송이 실패하거나 참가자가 바뀌면 해당 라운드를 취소하고 연결을 닫습니다. 이 기능은 초기 오브젝트 목록을 구성합니다. 이동 충돌 차량, 대포 스케줄링과 실제 클라이언트 검증은 아직 완료되지 않았습니다.

### 레이싱 대포 중계

`extreme_racing_cannon`은 `dialect.rooms.config`와 `ingame.config` 모두에서 기본값이 `false`이며, `extreme_racing_initialization`과 함께 양쪽에서 활성화해야 하고 빌드의 `extreme_racing_cannon` 능력(현재 kr-1256만)이 필요합니다. 활성화하면 방은 설정된 각 맵의 `option.ini` 옆에서 `Maps/<stage_directory>/cannon.ini`를 읽습니다. 선언된 대포 수는 맵의 `Cannon/PairCount`와 같거나 0이어야 하고, 각 대포에는 `WEAPONCOUNT`, 양수 `INTERVAL`, 맵에 있는 `STAGE`가 필요하며, 무기마다 `WEAPONID`(50000~50008), `COUNT`, 유한한 양수 `SCALE`을 담은 `[CannonN_WeaponM]` 구역이 있어야 합니다. 그 밖의 불일치나 형식 오류는 활성화를 실패시킵니다. 대포를 0개로 선언한 맵(예: 9쌍을 초기화하는 rel_Racing01_Extreme)은 대포를 예약하지 않으며, 그 대포 쌍은 유휴 상태로 남고 어떤 발사도 통과하지 않습니다. 방은 중계 대포 발사 프레임(중계 32902)의 행위자가 보낸 사람 자신의 좌석이고, 벡터가 유한하며, 대포 식별자가 이번 세대에 초기화되었고, 무기가 그 대포의 리소스 목록에 있으며, 아직 응답되지 않은 서버 명령 하나와 정확히 일치할 때만 이를 받아들인 뒤, 원본 바이트를 초기화된 다른 참가자에게 한 번 전달합니다. 보낸 사람에게 되돌리지 않고, 재시도하지 않으며, 일련번호도 바꾸지 않습니다. 대포 쌍마다 미응답 명령은 최대 하나이므로 장부 크기는 맵의 대포 수입니다. 이 옵션만으로는 대포 명령을 보내지 않으므로 아래 스케줄이 명령을 발행하기 전에는 어떤 발사도 통과하지 않습니다. 네이티브 클라이언트 검증은 아직 끝나지 않았습니다.

### 레이싱 대포 스케줄

`extreme_racing_cannon_fire`는 `ingame.config`에서 기본값이 `false`이며 `extreme_racing_cannon`이 필요합니다. 클라이언트에는 대포를 쏘는 타이머가 없으므로 이 옵션이 꺼져 있으면 대포는 발사되지 않습니다. 켜면 각 레이스 라운드는 레이스 시계(S2C 711)를 보낸 직후 대포를 가동하고, 명령(S2C 718)은 정확히 한 좌석, 즉 원점 좌석에만 갑니다. 그 클라이언트가 발사하고 중계(중계 32902)하면 방 경로가 이를 전달합니다. 원점 좌석, 주기, 무기 순서는 네이티브 동작이 아니라 서버 정책이며, `INTERVAL`을 읽는 클라이언트 코드는 찾지 못했습니다.

- 원점 좌석은 초기화를 받았고 게임 연결이 열려 있는 가장 낮은 슬롯의 좌석입니다. 각 수신자가 자기 탄환을 발사하므로 명령은 둘 이상의 좌석에 보내지 않습니다.
- 각 대포는 레이스 시계가 시작되고 `INTERVAL` 후에 처음 만기가 되고, 이후 만기 때마다 한 간격 뒤에 다시 만기가 됩니다. 쌍에 미응답 명령이 남아 있는 대포는 대기열에 넣지 않고 건너뛰며, 시계가 멈췄다고 놓친 발사를 몰아서 보내지 않습니다. `STAGE`는 사용하지 않습니다. 무기가 여러 개인 대포는 파일 순서대로 순환합니다.
- 명령은 그룹 0(모든 대포 그룹), 대포 쌍의 첫 식별자, 스케일 1.0을 담습니다. 중계되는 발사에는 스케일이 없으므로 다른 값은 원점의 대포만 바꿉니다.
- 레이스 라운드가 닫히거나, 라운드가 취소되거나 끝나거나, 방이 멈추거나, 세대가 바뀌면 주기가 멈추고 미응답 명령은 폐기됩니다. 다음 레이스 라운드에서 다시 가동됩니다.
- 원점 좌석이 나가거나 연결이 끊기면 그 미응답 명령은 폐기되고 다시 보내지 않으며, 초기화된 남은 좌석 중 가장 낮은 슬롯이 이후 명령에 한해 새 원점이 됩니다. 초기화를 받지 못한 좌석은 선택되지 않으며 명령 이력도 받지 않습니다.
- 전송이 실패하면 그 세대의 스케줄이 끝납니다. 명령은 폐기되고 재시도하지 않으며 레이스는 대포 트래픽 없이 계속됩니다.

네이티브 클라이언트 검증은 아직 끝나지 않았습니다.

### WeaponMaster 라운드

`dialect.rooms.config.weapon_master`의 기본값은 `false`이며, 빌드의 `weapon_master` 능력(현재 kr-1256만, cn-774와 tw-454는 상속하지 않음)과 함께 `modern_rooms`, 그리고 `result_scoreboard_modes`에 모드 26이 포함되어야 합니다. 이 옵션은 좌석에 무기를 지급하는 장비 프레임과, 여러 번 사망한 뒤 클라이언트가 새 무기를 요청하는 프레임을 마운트합니다.

같은 프로토콜의 인게임 행에 `ingame.config.weapon_master_levels`를 함께 설정해야 하며, 둘 중 하나만 있으면 활성화가 실패합니다. 이 옵션에는 기본값이 없습니다. 빈 목록이면 모드 26은 일반 시간제 라운드로 진행됩니다. 목록의 각 항목은 순서대로 한 레벨이며, `experience` 기준값(첫 레벨은 `0`, 이후 레벨마다 더 크고 65535 미만)과 선택적인 `weapons` 목록(`item`은 양수 아이템 ID로 같은 레벨 안에서 중복 불가, `weight`는 양수)을 가집니다. 무기를 나열하지 않은 레벨은 공유 `weapon_master_weapons` 풀에서 뽑으므로, 레벨과 무관한 무기는 한 번만 적으면 됩니다. `weapon_master_experience`는 인정된 각 이벤트가 주는 경험치를 `{ event, points }`로 나열합니다. 이벤트는 `kill`, `knockdown`, `rescue` 중 서로 다른 것이고 점수는 양수이며, 나열하지 않은 이벤트는 경험치를 주지 않습니다. 모드 26은 `native_life_every_mode` 또는 26을 포함한 `native_life_mode_ids`로 네이티브 생명 판정도 사용해야 합니다. 프레임은 무기를 무기 카탈로그 ID로 지정하며 `kr-1256 sub_4ADD70`이 이를 해석합니다. 주무기의 상점 아이템 ID는 200000에 그 ID를 더한 값입니다. `kr-1256` 프로필의 패치는 200 경험치 간격의 열 레벨, 킬당 100 경험치, 구형 L1, L2, L3, S1, S2, R3 주무기로 이루어진 하나의 무작위 풀을 사용합니다.

모든 좌석은 라운드 시작 시 무기를 받습니다. 인정된 이벤트는 경험치를 더하고, 좌석의 경험치가 다음 레벨의 기준값에 도달하면 그 레벨로 오르며 그 레벨의 무기 하나를 받습니다. 한 이벤트가 여러 기준값을 넘어도 무기는 하나입니다. 실시간 점수는 각 좌석의 레벨, 경험치, 현재 레벨의 시작 경험치, 다음 레벨의 경험치를 종류 31~34로 전달합니다(`kr-1256 sub_9E9160`이 좌석 기록 +204~+216에 저장). 마지막 레벨에서는 다음 값이 시작값보다 1 큽니다. 마지막 레벨에 가장 먼저 도달한 좌석이 승리하고 라운드는 즉시 끝납니다. 클라이언트가 마지막 무기 이후 정해진 횟수만큼 플레이어가 죽었다고 보고하면 서버는 같은 레벨의 새 무기를 줍니다. 서버는 그 횟수 `WeaponMasterNoPangDeadCount`를 클라이언트의 `Config/GameOption.xml`에서 읽으므로 이 파일을 가져와야 하며, 값이 없거나 중복되거나 양수가 아니면 활성화가 실패합니다. 너무 이른 요청은 기록되고 무시됩니다. 부활은 공통 규칙을 따릅니다. 아무도 마지막 레벨에 도달하기 전에 시간이 끝나면 가장 높은 레벨의 좌석이 승리하며, 모든 좌석의 레벨이 같으면 무승부입니다. 결과 화면의 레벨 열은 여전히 계정 레벨을 표시합니다. 네이티브 클라이언트 검증은 아직 남아 있습니다.

### BnB 라운드

`dialect.rooms.config`와 `ingame.config`의 `bnb`는 모두 기본값이 `false`입니다. 검증된 kr-1256 모드 41 교환을 활성화하려면 양쪽을 켜고 `modern_rooms`, 41을 포함하는 `result_scoreboard_modes`, `native_match_relay: true`, 그리고 `native_life_every_mode` 또는 41을 포함하는 `native_life_mode_ids`를 통한 생명 상태 처리를 설정해야 합니다. 다른 빌드는 전체 교환 검증 전까지 이 옵션을 거부하며, 이 경로는 봇을 허용하지 않습니다. `profiles/kr-1256/bnb.patch.yaml`을 적용하면 검증된 장면 경계로 `rel_bnb01_village06`의 교환을 활성화합니다.

`Config/GameSpec/BnBSpec.yaml`과 선택한 맵의 `Maps/<stage_directory>/CustomMap.json`, `BnBItemLayout.json`을 가져옵니다. `ingame.config.bnb_stages`에는 서로 다른 항목을 최대 128개 설정하며, 각 항목에 `stage_directory`, `tile_layer_minimum_x`, `tile_layer_maximum_z`가 필요합니다. 두 좌표는 JSON 오프셋을 적용하기 전 원본 TileLayer 경계이며, 선택한 맵의 장면 데이터에서 얻은 유한한 값을 명시해야 합니다. 원점을 추측하면 아이템 생성 결과가 같아도 잘못된 셀을 선택할 수 있습니다.

`bnb_maximum_file_bytes`의 기본값은 1048576(1..16777216), `bnb_maximum_cells`는 1024(1..4096), `bnb_maximum_position_cell_distance`는 1(최근 승인된 이동 위치에서 맨해튼 셀 거리, 0..4), `bnb_explosion_report_grace_ms`는 1000(0..10000)입니다. 퓨즈, 불꽃과 블록 파괴 시간 및 능력 한도는 원본 리소스에서 읽습니다. 로딩 전에 공통 맵 시드를 전달하며 각 라운드는 배치, 폭발, 획득 상태를 하나의 순서로 관리합니다. 이미 점유된 셀에 중복 배치해도 알림을 보내거나 순번을 늘리지 않습니다. 이미 획득된 아이템 요청에는 응답하여 입력 상태를 해제하되 보상은 중복 지급하지 않습니다. 잘못된 소유권, 이전 생명 및 이전 라운드는 현재 상태를 변경할 수 없습니다. 전파 실패나 필수 참가자 연결 손실은 해당 라운드를 취소합니다. 실제 클라이언트 검증은 아직 완료되지 않았습니다.

같은 캐릭터 생명 주기에서 버블 보고 직후 도착한 획득 요청에는 동일한 위치 및 소유권 검사를 적용합니다. 죽었거나 제거된 캐릭터는 아이템을 획득할 수 없습니다. 사망 정리가 완료되면 부활을 승인하지 않고 캐릭터 제거 응답을 한 번만 보내며, 이후 초기화 확인으로 해당 캐릭터를 되살릴 수 없습니다. 새 라운드는 새 캐릭터 생명 주기를 만듭니다.

### FinalZone

`dialect.rooms.config.final_zone`의 기본값은 `false`입니다. `profiles/kr-1256/final-zone.patch.yaml`을 적용하면 모드 23, 25, 30, 45에 공통으로 쓰이는 Area32 교환을 활성화합니다. modern 라운드 바인딩, `final_zone` 빌드 기능 및 점수판 모드 30이 필요하며, 현재 kr-1256만 검증되었습니다. 패치는 점수판 모드 1, 5, 6, 19, 20, 24도 유지하므로 다른 모드 패치 뒤에 적용할 수 있지만 해당 모드를 직접 활성화하지는 않습니다.

`client-data`를 통해 해당 클라이언트의 `Config/GameSpec/GenItemSetting.yaml`, `Config/GenDroneSpec.csv`, `Config/SurvivalMode.xml`, `ServerShared/MapMeta.xml`과 선택한 맵의 `GenClusterTable.csv`, `GenSpawnTable.csv`, `GenSpotList.csv`를 가져오십시오. 드론이나 황금 보급을 사용하는 맵에는 `GenDroneRewardTable.csv`도 필요합니다. 아파트 맵은 드론을 비활성화하며 이 표를 제공하지 않습니다. 누락되거나 잘못된 리소스는 카운트다운 전에 오류를 냅니다. 현재 명시적 아이템 생성 경로는 `rel_Sudden08_Finalzone`을 포함한 일반 생성 아이템을 지원합니다. 별도의 `AutoItem` 지형 클래스를 사용하는 맵(`rel_space04_64room` 포함)은 거부됩니다. 선택적 시작 팩의 네이티브 소비 및 지급 교환도 아직 통합되지 않아 시작 팩을 장착하면 카운트다운 전에 거부됩니다.

서버는 라운드 시작 후 지상 아이템을 게시하고 각 오브젝트를 한 명에게만 지급합니다. 지급 수량을 기준으로 직접 버리기와 한 번의 사망 배낭을 검증하며, 배낭 내용 이전에는 네이티브 사용자 번호를 사용합니다. 홍수 단계는 맵 리소스의 시간을 따릅니다. 드론은 제한된 방 타이머를 사용하며, 보급 상자와 방장의 중복 제거된 황금 보급 요청은 네이티브 보상 시드를 공유합니다. 함정 끝점마다 보유한 막대 하나를 소비하며, 소유자가 승인된 두 끝점만 연결할 수 있습니다. 필요한 확인은 보낸 플레이어에게도 전달됩니다. 탈락자는 부활하지 않고 생존자 수는 한 번만 갱신하며, 경쟁자가 있었던 라운드에서 한 명만 남으면 한 번 정산합니다. 모드 25는 마지막 생존 팀을 기준으로 정산합니다. 모드 45에는 공통 아이템 및 탈락 처리가 적용되며, 별도의 좀비 기능은 여기에 포함되지 않습니다. 일반 점수 및 시간 제한은 FinalZone을 끝내지 않습니다. 취소, 방 폐기 및 최종 결과는 모드 타이머를 멈춥니다.

리소스와 오브젝트 제한은 `ingame.config` 필드입니다.

| 키 | 기본값 | 제한 |
|---|---:|---|
| `final_zone_first_object_id` | 65536 | 첫 예약 월드 핸들. 전체 범위는 참가자 핸들보다 작아야 합니다. |
| `final_zone_maximum_objects` | 16384 | 라운드당 재사용하지 않는 전체 핸들 수. 아이템, 배낭, 드론, 보급 및 함정 막대가 공유합니다. |
| `final_zone_maximum_quantity` | 100000 | 아이템 사양별 최대 지급 또는 보유 수량. |

| `final_zone_maximum_golden_supplies` | 3 | 라운드당 서로 다른 황금 보급 요청 수. 0은 지급을 비활성화합니다. |

이 기능은 아직 옵션으로 보호되는 증분 구현입니다. 원장은 지급 수량을 제한하지만 모든 네이티브 인벤토리 슬롯, 무기 변형 및 실시간 탄약 소비를 재현하지는 않습니다. 모드 30의 동맹 및 암살 동작은 아직 확인되지 않았습니다. 자동 검사와 리소스 가져오기는 실제 클라이언트 검증이나 모든 맵 메커니즘의 구현을 의미하지 않습니다.

### 별 모드

`ingame.config.star_mode_ids`와 `star_team_mode_ids`는 개인전과 팀전 별 모드(네이티브 클라이언트의 모드 5와 6)를 지정하며 `dialect.rooms.config.star_items`가 필요합니다. 별 라운드는 `star_round_time_limit_ms`(기본 240000) 동안 진행되고 지도 자체의 별 지점을 사용합니다. 위치, 종류와 생성 시간은 방장의 지도 보고에서 가져오며, 방장이 별 지점을 보고하지 않으면 서버가 지도 `track.wb`의 `#sp_star_` 및 `#sp_bigStar_` helper를 대신 읽습니다(`star_map_fallback`, 기본 `true`). 각 지점은 자체 지연 후 첫 별을 표시하고, 그 별을 가져간 뒤에만 다시 채웁니다. 별 라운드는 각 좌석이 보유한 별 수로 승패를 정하며, 실시간 점수와 결과는 각 팀의 별 수를 팀 총점으로 보냅니다. 결과 표는 목록에 있는 모드에만 전송되므로 최신 방에서 `star_items`를 켜면 `result_scoreboard_modes`에 모드 5와 6도 포함해야 합니다. `star_fever_lead_ms`(기본 0, 꺼짐)는 제한 시간이 끝나기 이 값(밀리초)만큼 전에 빌드의 마지막 별 피버를 시작하며, 현재 검증된 피버 패킷은 kr-1256에만 있습니다. `profiles/kr-1256/stars.patch.yaml`을 적용하면 kr-1256에서 두 모드를 활성화하고 마지막 45초에 피버를 시작합니다. 패치는 전체 점수판 모드 목록을 다시 지정하므로 다른 모드 패치 뒤에 적용할 수 있습니다. 실제 클라이언트 검증은 아직 남아 있습니다.

## 밴픽

밴픽은 원래 클라이언트에 없던 서버 기능입니다. 기본으로 설치되어 켜져 있지만 누군가 규칙을 정하기 전에는 아무것도 금지하지 않습니다. `core`의 `banpick` 행이 서버 전체 문서를 갖고, 각 빌드의 `banpick.room` 행(그 빌드 `ingame` 행의 하위 행)이 그 빌드의 방에 적용합니다. 두 행을 끄면 기능이 사라집니다.

금지는 두 가지입니다.

- **방 금지**는 방장이 정하며 방이 있는 동안만 유지됩니다. `!banpick`(별칭 `!bp`)은 `add <아이템 번호, 이름 또는 그룹>`, `remove <...>`, `set <번호 또는 그룹...>`(목록 전체를 한 번에 바꾸며 오버레이가 이 방식을 씁니다), `clear`, `list [페이지]`를 받습니다. 누구나 목록을 볼 수 있고, 방장만 게임 시작 전에 바꿀 수 있습니다.
- **서버 정책**은 관리자가 `gbanpick`(별칭 `gbp`, 권한 `game.management.banpick`)으로 정합니다. `state_path`(기본 `data/banpick-policy.json`)에 저장되며 저장할 때마다 수정한 리비전을 밝힙니다. `state_path`가 비어 있으면 설정의 `policy`는 읽기 전용입니다.

문서 구조는 클라이언트 정책과 같습니다. `policy.groups`는 모든 빌드가 공유하는 `ShopItem2`의 `MainCategory`/`SubCategory` 시트 번호나 `function` 열로 아이템 그룹을 정합니다. 기본 그룹에는 `weapon`, `sniper`, `rifle`, `shotgun`, `clothes`, `hat`, `character`, `pet`이 있습니다. `policy.policies`에는 정책을 몇 개든 둘 수 있고, 정책마다 범위(`builds`, `modes`, `rooms: all|public|password`)와 유형이 있는 규칙이 있습니다.

| 규칙 유형 | 효과 |
|---|---|
| `block` | 정책이 적용되는 곳에서 아이템 장착을 거부하고, 착용한 채로는 라운드를 시작할 수 없습니다. |
| `confirm` | 방 금지와 같은 강도입니다. 방장에게 경고하고 방장은 그래도 시작할 수 있습니다. |
| `warn` | 허용되지만 누가 착용했는지 방에 알립니다. 새로 들어온 사람은 이미 착용한 모든 사람의 알림을 받습니다. |

방장이 시작을 누를 때 누군가 방 금지 또는 `confirm` 아이템을 착용하고 있으면 모든 멤버에게 누가 무엇을 착용했는지 알립니다. Nirinsou Link 오버레이가 있는 방장은 확인 창을 보고, 그 밖의 방장은 `reclick_window_ms`(기본 10000) 안에 시작을 다시 누르거나 `!bp start`를 입력하면 됩니다. `announcement_items`(기본 25)보다 긴 목록은 개수만 알립니다. 오버레이는 `game.ban.list.changed`, `game.ban.start.confirm`, `game.ban.warn`을 받고 `game.ban.list.get`, `game.ban.catalog.search` 요청으로 목록을 읽습니다. 확인 창의 확인을 포함해 오버레이가 하는 모든 변경은 실행에 묶인 명령 채널(`game.command.execute`)로 보내는 `bp` 명령이므로 직접 입력한 명령과 똑같이 검사됩니다. 이를 위해 `companion.commands` 행을 켜야 합니다(`core`에서는 기본으로 꺼져 있습니다). 메시지 행이 서버 공지를 보내지 않는 빌드는 같은 내용을 시스템 채팅으로 받습니다. 네이티브 클라이언트 검수는 아직입니다.

## 네이티브 광장 파티 모집

지원하는 열세 프로필에는 광장 모집이 활성화되어 있습니다. 사용자 지정 프로필은 `dialect.rooms`와 `ingame`에 각각 `plaza_recruitment: true`를 설정하고 해당 `party` 행을 탑재해야 합니다. 두 옵션의 기본값은 `false`이며, 네이티브 바인딩이나 파티 디렉터리 또는 광장 기능이 없으면 활성화에 실패합니다. `ingame.plaza_recruitment_text_length`는 기본 128 UTF-16 문자이며 1–1024를 허용합니다. 게시와 수정에는 채팅 속도 제한을 적용하지만 모집 취소는 계속 허용합니다.

현재 광장의 파티장만 모집할 수 있습니다. 네이티브 표지판 상태, 말풍선, 파티 구성과 장면 따라가기를 함께 갱신합니다. 취소, 퇴장, 장면 변경 또는 파티장 교체 시 이전 표지판을 지웁니다. KR1256과 CN2019는 파티장이 선택한 분류와 정원으로 페이지당 열 개의 모집 문서를 표시합니다. 목록에서는 현재 노드의 파티장에게만 가입할 수 있으며, 원격 플레이어의 광장 외형을 표시하는 것만으로 다른 노드의 파티 가입을 허용하지는 않습니다. 입장 위치는 네이티브 클라이언트가 결정하고 서버는 실제 위치 보고만 재전송합니다.

## 선택적 장비 방어 테이블

장비 일반 방어는 기본적으로 비활성화됩니다. `kr-812`, `cn-324`, `cn-406`, `cn-404`, `cn-408`, `cn-705`, `cn-706`, `id-400`, `id-1809`, `cn-717`, `cn-774`, `tw-454`, `kr-1256`에서 `--patch profiles/bundles/defence-seeds.patch.yaml`을 추가하여 활성화합니다. 이 패치는 테이블 전달에 필요한 네이티브 TCP 릴레이도 활성화하며, `cn-705`와 `cn-706`에서 기본적으로 비활성화된 관련 행도 포함합니다. UDP는 필요하지 않습니다. `all`에서는 각 빌드의 `local.patch.yaml`에 패치 작업을 넣으세요. 공통 패치는 나중에 추가되는 빌드 행을 수정할 수 없습니다. `cn-705`는 별도 프로필로 사용할 수 있지만 `all`에는 포함되지 않습니다. 검증된 기능 또는 권한 행이 없는 빌드는 패치를 거부합니다.

CN2011(`cn-279`)은 네이티브 피해 처리 과정에서 일반 장비 방어를 로컬로 계산하므로 이 시드 테이블 패치를 사용하지 않습니다.

권한 플러그인은 해당 빌드의 `Config/ShopItem2.xml`과 `defence_seed` 규칙을 읽습니다. 라운드 시작 시 착용 아이템 ID를 고정하고 각 피격자의 동일한 1000바이트 테이블을 모든 수신자에게 보냅니다. 피해 감소는 원래 클라이언트가 적용하며 치명타와 취소 테이블은 분리됩니다. `cn-705` 또는 `cn-706`의 방어를 활성화해도 검증되지 않은 치명타 교환은 활성화되지 않습니다. 옵션을 끄면 기존의 방어 값 0 교환이 유지되고 방어 전용 행은 비활성화됩니다.

균형 잡힌 빈도로 로컬 정수 난수 분포를 근사하며 클라이언트 난수열을 재현하지 않습니다. 카탈로그의 min/max, 설정된 RC/KR/BB 세트 효과와 끝점 정밀도만 반영합니다. `cn-774`와 `tw-454`는 각각 검증된 RC/KR/BB 규칙과 단정밀도 끝점을 사용합니다. 인스턴스 속성, 변신 전용 속성과 별도 특수 보정은 반영하지 않습니다. CN2019의 AI 캐릭터는 다른 시드 인코딩을 사용하므로 이 플레이어 투영에 포함되지 않습니다. 실제 배포에서 활성화하기 전에 원래 클라이언트로 검증해야 합니다. `defence_items_client_path`는 통합 문서를 선택하고 `defence_workbook_max_bytes`는 크기를 제한합니다(기본값 268435456바이트).

## 최신 좀비 모드

`kr-1256`, `cn-774`, `tw-454`에서는 `profiles/<build>/script-zombies.patch.yaml`을 적용하여 `dialect.rooms`와 `ingame` 행 모두의 `script_zombies`를 활성화하고 일반 모드 8을 연결합니다. 두 옵션은 실제 클라이언트 검증 전까지 기본적으로 꺼져 있습니다. 방장의 네이티브 스크립트가 장비 가중치로 여러 좀비니를 선택하며, 서버는 최초 좀비 수를 현재 인원수 나누기 4의 올림값으로 제한합니다. 해당 캐릭터 소유자의 네이티브 확인을 받은 후 팀 34 변신을 적용합니다. 인간은 팀 1로 시작합니다. 이후 감염과 좀비 부활에는 소유자의 사망 또는 부활 증거가 필요하며, 일반 사망 보고만으로 라운드를 종료하지 않습니다. 모든 감염 확인이 완료되면 좀비가 승리하고, 서버 제한 시간까지 인간이 남아 있으면 인간이 승리합니다.

`ingame.script_zombie_round_time_limit_ms`의 기본값은 `180000`, 범위는 `1..3600000`입니다. 모드 8의 네이티브 생명 주기와 부활을 활성화하고 `dialect.rooms.result_scoreboard_modes`에 `8`을 포함해야 합니다. 두 행의 `script_zombies` 설정은 일치해야 합니다. 선택적 패치는 검증된 폭파, 캡틴, 달리기 및 FinalZone 패치와 함께 적용할 수 있으며 각 점수판을 유지합니다. 다른 모드는 빌드에 선언된 peer feed 정책을 유지합니다. 이 세 빌드는 일반 통과 전달을 비활성화하므로 활성화된 모드 밖에서는 공통 변신 작업을 전달하지 않습니다. 네이티브 스크립트 방장이 나가면 선택 상태를 다른 클라이언트로 이전할 수 없으므로 보상 없이 라운드를 취소합니다.

현재 통합은 단일 라운드입니다. 스크립트의 10라운드 요청을 서버의 연속 경기로 구현하지는 않았습니다. 고스트 모드 28, 오리진 모드 43, 좀비 생존 모드 44는 각각 다른 네이티브 규칙을 사용하므로 이 옵션으로 활성화되지 않습니다. 실제 네이티브 클라이언트 검증은 아직 필요합니다.

## 고스트 좀비

`kr-1256` 또는 `cn-774`에 `profiles/<build>/ghost-zombies.patch.yaml`을 적용하면 방 방언과 게임 행 양쪽에서 `ghost_zombies`가 활성화됩니다. 모드 28은 일반 모드 8 및 탈출 모드 32와 변환 바인딩을 공유합니다. 네이티브 방장은 무기 110290을 사용하는 좀비킹 한 명(201 또는 203)을 선택합니다. 스크립트의 후속 무기 0 선택은 추가 변환을 허용하지 않습니다. 확인된 좀비킹의 사망 정리가 완료되면 살아남은 인간이 승리하며, 좀비킹이나 방장이 나가면 보상 없이 경기를 취소합니다. 다른 인간은 자신의 사망/부활 경로를 통해 작은 좀비가 됩니다.

일반 및 고스트 좀비는 현재 캐릭터 소유자가 보낸 네이티브 ULTRA 활성화와 타이머 만료 복원도 동기화하며 공유 HP와 생명 세대를 유지합니다. 충전은 네이티브 게이지가 담당합니다. 스크립트의 10라운드 시리즈는 아직 구현하지 않았습니다. TW454의 완전한 고스트 스크립트 경로는 검증되지 않아 활성화를 거부합니다. 패치는 다른 활성 점수판을 유지하며 실제 클라이언트 검증은 아직 필요합니다.

## 좀비 탈출

`dialect.rooms.config.zombie_escape` / `ingame.config.zombie_escape`의 기본값은 `false`입니다. kr-1256, cn-774 또는 tw-454 단일 빌드에 `profiles/bundles/zombie-escape.patch.yaml`을 적용합니다. `all`에서는 선택한 각 빌드의 무시되는 `local.patch.yaml`에 작업을 넣습니다. 활성화에는 현대 라운드 바인딩, 해당 빌드의 감사된 `zombie_escape` 기능, 점수판 모드 32가 필요합니다. 패치는 점수판 모드 1, 8, 19, 20, 23, 24, 25, 28, 30, 32, 45을 유지하지만 각 모드의 별도 옵션을 켜지는 않습니다. 해당 클라이언트의 좀비 탈출 맵과 스크립트를 사용해야 하며 원래 클라이언트 검증은 아직 완료되지 않았습니다.

방 방언과 게임 플러그인은 같은 좀비 모드를 활성화해야 합니다. 일반 좀비와 좀비 탈출은 하나의 형식화된 변신 바인딩을 공유하므로 함께 활성화해도 네이티브 작업을 중복 등록하지 않습니다. 선택 패치는 지원되는 모든 생존 모드 결과표를 보존하며, 대기실로 돌아오면 라운드 시작 전 팀을 복원합니다.

방장 클라이언트의 스크립트가 초기 좀비 추첨, 별도 좀비 시작 위치, 준비 문, 체크포인트 버튼, 시간제 문, 감염 게이지와 탈출 조건을 제어합니다. 서버는 제한된 방장 선택과 각 플레이어 자신의 이후 감염 또는 리스폰 변신을 검증하고 승인된 peer 변신을 모든 참가자에게 돌려보냅니다. 생명, 결과와 보상 정산은 공통 흐름을 사용합니다. 초기 좀비 수는 접속 중인 플레이어 수를 5로 나누어 올림한 값입니다. 감염 게이지는 살아 있는 플레이어도 직접 감염시킬 수 있으며 버튼 검사가 인간만 허용한다는 근거는 없습니다.

방장은 원래 스테이지 결과로 인간의 탈출을 보고합니다. 접속 중인 인간이 남지 않거나 서버 제한 시간이 끝나면 좀비가 이깁니다. `ingame.config.zombie_escape_round_time_limit_ms`의 기본값은 600000이며 범위는 1..3600000입니다. 일반 사망 스테이지 보고는 이 모드를 끝내지 않습니다. 도중 참가는 거부됩니다. Lua 방장이 나가면 비공개 타이머와 체크포인트 상태를 재생할 수 없으므로 보상 없이 라운드를 취소합니다. 다른 연결 끊김은 설정된 취소 정책을 따릅니다.

이 옵션은 공통 결과 흐름으로 한 스테이지를 정산합니다. 원래 스크립트가 게임 횟수 3을 기록하지만 세 스테이지 시리즈의 의미는 확인되지 않아 구현하지 않았습니다. 자동 테스트가 원래 맵 동작과 UI의 전체 검증을 의미하지는 않습니다.

## 클라이언트 빌드별 장착 설정

`inventory.loadouts` 행은 빌드마다 장착 캐릭터, 의상, 무기, 무기 프리셋 페이지와 활성 슬롯을 별도로 저장합니다. `build_key`에는 `kr-1256`, `cn-279` 같은 안정적인 프로필 식별자를 사용하며, 같은 빌드를 제공하는 노드는 같은 키를 사용합니다. 계정의 아이템 소유권, 수량, 유효 기간, 지갑과 진행도는 계속 공유합니다. 클라이언트 인벤토리에는 자체 `ShopItem2.xml`에 있는 아이템만 표시하며, 캐릭터는 `FighterConfig.xml`도 확인합니다. 호환되지 않는 아이템의 소유권은 유지되며 지원하는 빌드로 돌아오면 다시 표시됩니다.

처음 사용할 때 기존 기록에서 호환되는 선택을 가져오고 기존 장착 규칙으로 필수 장비 위치를 채웁니다. 이후 변경은 해당 빌드에만 적용됩니다. 프리셋 초기화는 이미 저장된 페이지를 덮어쓰지 않습니다. 이 행은 `clientdata` 아래에서 `IInventoryRepository`와 `IPlayerInventoryState`를 격리하고 공유 저장소의 `IInventoryLoadoutStore`를 사용합니다. 사용자 프로필의 로비, 장비 표시, 장비, 상점, 방 프로토콜 및 게임 로직 소비자는 이 하위 트리에 있어야 합니다.

`inventoryview` 행의 `persist_preset_pages` 스위치는 무기 프리셋 페이지를 서버가 소유하는 상태로 저장합니다. legacy 번들과 kr-1256 번들에서 켜져 있으며, cn-774와 tw-454는 페이지 레코드 구조가 달라 꺼 둡니다. 클라이언트에는 페이지를 저장하는 패킷이 없으므로 서버가 기록합니다. 장비 변경이 커밋될 때마다 착용 중인 주무기와 특수 무기를 그 시점의 활성 페이지에 기록하고, 다른 페이지는 각자의 무기를 유지하므로 탭마다 별도의 구성을 가집니다. 주무기를 해제해도 페이지의 무기는 지워지지 않으며 로그인 재전송은 기록하지 않습니다. 다른 페이지로 전환하면 이 빌드의 가방에 해당 페이지 무기가 있을 때 일반 장비 커밋으로 착용합니다. 착용할 수 없는 페이지 무기는 페이지에 남고 착용 구성은 바뀌지 않습니다. 페이지는 해당 빌드의 `inventory.loadouts` 범위에 속합니다. 최신 빌드에서 크리스털이나 펫까지 담는 프리셋 페이지는 아직 다루지 않습니다.

Memory, MySQL, SQLite 공급자는 모두 `max_loadouts_per_player`를 제공하며 기본값은 `32`, 범위는 `1..256`입니다. 한도에 도달하면 기존 설정을 제거하지 않고 새 빌드 설정을 거부합니다. MySQL 마이그레이션 `0038`은 `player_loadouts`를 추가하며 SQLite 스키마 `8`은 기존 계정 상태를 유지하면서 장착 스냅샷을 추가합니다. 업그레이드 전에 영구 저장소를 백업하세요. MySQL 코드를 되돌릴 때 추가된 테이블을 유지합니다. 이전 SQLite 리더는 스키마 `8`을 거부하므로 롤백에는 호환되는 리더가 필요합니다. 플레이어의 새 진행도를 이전 저장 파일로 덮어쓰지 마세요.

## 선택적 아이템 강화

`kr-1256` 프로필에는 `profiles/bundles/item-enhancement.patch.yaml`이 포함되어 있습니다. `BFF_ITEM_ENHANCEMENT_ENABLED`의 기본값은 `true`이며 일반 아이템의 새 Article 할당, 강화 변경, 실험실 작업 및 설정 바인딩을 제어합니다. `item-enhancement.articles` 메타데이터 행은 계속 활성 상태를 유지하며, 검증되는 `initialize_articles` 필드의 기본값은 `false`이고 같은 플래그를 따릅니다. 플래그를 꺼도 저장된 식별자는 계속 해석할 수 있고 장착과 해제를 지원하며 저장된 강화와 개조 속성을 표시합니다. Article 식별자가 없는 일반 인벤토리에는 새 식별자를 할당하지 않습니다. 강화를 활성화하려면 아래 다섯 가지 조합법 값을 모두 명시해야 하며, 값이 없거나 범위를 벗어나면 활성화가 실패합니다.

프로필은 아직 설정하지 않은 조합법 값을 `-1`로 표시합니다. 강화 행은 이를 미설정 값으로 취급하며 다섯 값이 모두 아래 범위를 충족해야 활성화됩니다. `-1`은 성공 확률이나 재료 수량으로 사용되지 않습니다.

강화는 메인 메뉴에서 조건에 맞는 영구 무기 또는 의상 Article 하나를 대상으로 하며, 장착 중이거나 이미 강화된 아이템은 사용할 수 없습니다. 이 번들의 강화와 무기 개조(Modification) 처리는 `kr-1256`을 대상으로 검토되었습니다. 다른 클라이언트 빌드의 지원을 보장하거나 다른 실험실 작업을 활성화하지는 않습니다.

| 환경 변수 | 강화 행 필드 | 필수 정수 값 |
| --- | --- | --- |
| `BFF_ENHANCEMENT_SUCCESS_BASIS_POINTS` | `success_basis_points` | `0..10000`; `5000`은 성공 확률 50%를 뜻합니다. |
| `BFF_ENHANCEMENT_ADDITIVE_SUCCESS_BASIS_POINTS` | `additive_success_basis_points` | `0..10000`; 플레이어가 첨가제를 선택했을 때의 성공 확률입니다(`10000`은 확정 성공). |
| `BFF_ENHANCEMENT_CARD_QUANTITY` | `card_quantity` | 허용된 시도마다 소비하는 카드 `190111`의 수량, `1..1000000`. |
| `BFF_ENHANCEMENT_KIT_QUANTITY` | `kit_quantity` | 허용된 시도마다 네 가지 키트 `190106`, `190107`, `190108`, `190109` 각각에서 소비하는 수량, `2..1000000`. |
| `BFF_ENHANCEMENT_ADDITIVE_QUANTITY` | `additive_quantity` | 플레이어가 첨가제를 선택했을 때 소비하는 첨가제 `101745`의 수량, `1..1000000`. |

이 값은 서버의 조합법 정책을 정의합니다. `.env.example`에 주석으로 적힌 숫자는 예시이며, 기본 경제 값이나 과거 가격을 뜻하지 않습니다. 허용된 시도는 실패하더라도 설정된 카드 수량과 각 키트 수량을 소비합니다. 첨가제를 선택하면 설정된 첨가제 수량도 소비하고 `success_basis_points` 대신 `additive_success_basis_points`를 사용합니다. 재료가 부족하거나 재료 식별이 모호하면 변경을 커밋하기 전에 요청을 거부합니다.

무기 개조는 기본값이 `true`인 `BFF_ITEM_MODIFICATION_ENABLED`로 별도 제어합니다. 활성화하려면 `BFF_ITEM_ENHANCEMENT_ENABLED=true`, 위의 다섯 강화 설정값, 배포 패치의 `item-enhancement` 행에 완전한 중첩 `modification` 정책이 모두 필요합니다. 플래그만으로 재료 수량, 가격, 효과 크기 또는 확률 정책이 제공되지는 않습니다.

| 개조 필드 | 필수 정책 |
| --- | --- |
| `part_quantity` | 정확히 세 개 선택하는 부품 각각의 소비 수량으로 `1..715827882`입니다. 같은 부품을 반복 선택한 총 차감량이 Int32 범위에 들어야 합니다. |
| `apply_lucci_cost`, `delete_lucci_cost` | 한 그룹의 개조 적용 또는 삭제에 드는 명시적 Lucci 비용으로 각각 `0..2147483647`입니다. 무료도 `0`을 명시해야 합니다. |
| `parts` | 1~24개 항목으로 `item_id`와 `(numeric_tag, effect_category)` 조합이 각각 고유해야 합니다. 각 아이템은 네이티브 수량형 개조 부품이어야 합니다. |
| `parts[].numeric_tag`, `parts[].effect_category` | 네이티브 분류는 각각 `0..2`와 `1..8`입니다. 설정한 태그와 효과 분류의 모든 조합에 부품 항목이 있어야 합니다. |
| `parts[].attribute_ids` | 검토된 네이티브 ItemAttr 선택자 `101..156` 중 서로 다른 일곱 개입니다. 같은 숫자 태그에서 각 선택자는 하나의 설정 항목에만 속해야 하며, 다른 태그에서는 재사용할 수 있습니다. |
| `parts[].value0` | 양의 부호 있는 효과 단위로 `1..2147483647`입니다. `160`은 `1.60%`로 표시됩니다. |
| `parts[].negative_values` | 선택자와 일치하는 일곱 개의 `{ attribute_id, value }` 항목입니다. 값은 `-2147483648..0`이며 `-40`은 `-0.40%`로 표시됩니다. |
| `tag_weights`, `effect_weights` | 각 항목은 `key`와 기존 개조 그룹 수 0, 1, 2에 해당하는 세 `weights`를 가집니다. 키는 부품 분류와 일치해야 합니다. 각 가중치는 `1..715827882`여서 같은 부품 세 개의 합이 Int32에 들어야 합니다. |

개조는 메인 메뉴의 조건에 맞는 영구 미장착 무기 Article을 대상으로 합니다. 플레이어는 소유한 부품 세 개를 선택하며, 반복 선택한 부품의 소비 수량은 합산됩니다. 선택한 부품의 태그와 효과 분류 가중치를 각각 합산한 다음, 결과 분류 조합의 일곱 선택자 중 하나를 같은 확률로 선택합니다. 네이티브 실험실 미리 보기에도 같은 정책을 사용합니다. 미리 보기 크기는 부동소수점 백분율이며, 설치된 Article 속성은 부호 있는 정수 단위, 그룹과 숫자 태그를 유지합니다. 이 값은 명시적 배포 정책입니다.

무기마다 강화 상태와 별개로 `0..2`의 세 개조 그룹을 저장할 수 있습니다. 적용은 첫 번째 빈 그룹을 사용하며, 삭제는 설치된 그룹을 지정해야 합니다. 성공한 적용이나 삭제마다 해당 무기의 카탈로그 범위 버전이 증가하며 마지막 그룹을 삭제해도 빈 상태와 버전을 유지합니다. 같은 오래된 저장 계획은 다시 차감할 수 없지만, 이후 새로 해석한 적용 요청은 다른 그룹을 정상 설치할 수 있습니다.

재료 차감과 성공한 강화는 함께 커밋됩니다. 개조의 Lucci 비용, 선택한 모든 재료, 그룹 변경과 필요한 Article/펫 메타데이터도 함께 커밋됩니다. 변경된 Article을 네이티브 처리기가 찾을 수 있도록 커밋한 잔액과 전체 인벤토리를 작업 결과보다 먼저 보냅니다. 소비 플래그를 꺼도 기존 속성은 계속 표시됩니다. 네이티브 클라이언트 검증과 실제 MySQL 환경 검증은 아직 남아 있습니다.

영구 전환(실험실의 ChangeUnlimited 탭, `kr-1256` 전용)은 별도로 기본 비활성화되어 있습니다. 배포 패치에서 활성화된 `item-enhancement` 행에 중첩된 `conversion` 정책을 추가하여 켭니다.

| 전환 필드 | 필수 정책 |
| --- | --- |
| `enabled` | `true`이면 탭을 표시하고 요청을 받습니다. 기본값 `false`는 탭을 숨기고 요청을 거부합니다. |
| `card_item_id` | 전환 한 번에 소비하는 수량형 카드입니다. 예: 원본의 `190151`. 해당 빌드 카탈로그의 수량형 재료여야 하며 전환 대상이어서는 안 됩니다. |
| `minimum_days` | 대상에 남아 있어야 하는 최소 일수로 `1..10000`입니다. 클라이언트도 요청을 보내기 전에 같은 값을 확인합니다. |
| `set_card_quantity` | 선택 사항입니다. 네이티브 세트 전환 한 번이 소비하는 카드 수로 1 이상입니다. 비워 두면 세트는 계속 거부됩니다. 클라이언트는 이 탭에 카드 한 장만 지정하고 세트별 수량은 없으므로 배포 측이 정합니다. |

전환은 메인 메뉴에서 아이템 ID로 선택한 단일 기간제 아이템 하나를 받습니다. 그 아이템은 클라이언트 자체의 전환 플래그가 있어야 하고, 무기나 의상이어야 하며, 아직 장비 식별자가 없고, 착용 중이거나 다른 제외 플래그가 없어야 하며, 남은 시간이 `minimum_days` 이상이어야 합니다(클라이언트의 0.5초 허용 오차 포함). 카드 한 장을 소비하고 같은 행을 영구로 바꾸며 슬롯, 플래그와 장착된 사본을 유지합니다. 강화와 개조가 다루지 않는 아이템이라도 장비 식별자를 받습니다. 서버는 저장소가 계정을 잡고 있는 시점에 타이머를 다시 판정하므로, 기다리는 동안 만료된 타이머, 오래된 요청, 아이템이 영구가 된 뒤의 반복 요청은 아무것도 소비하지 않습니다. 전체 인벤토리는 결과보다 먼저 게시됩니다. `set_card_quantity`를 설정하면 네이티브 세트를 지정한 요청이 세트 행에 나열된 모든 구성원(앞의 `setCnt`개 ID)을 한 트랜잭션으로 전환합니다. 각 구성원은 개별 아이템과 같은 검사를 통과해야 하고, 카드는 한 번만 소비되며, 구성원 하나라도 실패하면 세트 전체가 그대로 남습니다. 응답에는 세트와 첫 구성원의 Article 키가 들어 있습니다. kr-1256 클라이언트는 모든 구성원의 부위 위치가 설정된 경우에만 세트 요청을 보내는데, 그 통합 문서는 전환 가능한 아이템으로만 이루어진 모든 세트에서 이 값을 비워 두므로 원본 클라이언트는 해당 데이터로 요청할 수 없습니다. 원본 클라이언트 검증은 아직 남아 있습니다.

실험실 등급 상승(MakeItemAdvanced 탭, `kr-1256` 전용)은 별도로 기본 비활성화되어 있습니다. 배포 패치에서 활성화된 `item-enhancement` 행에 중첩된 `advancement` 정책을 추가하여 켭니다. `enabled`, `tab_card_item_id`(클라이언트가 이 탭에 표시하는 카드로, 규칙의 카드 중 하나여야 하며 클라이언트는 선택한 카드를 이 값과 비교해 일반 HC 세트의 확인 문구를 고릅니다), 그리고 업그레이드 카드마다 하나씩인 `rules`로 이루어지며, 각 규칙은 `card_item_id`(카탈로그의 수량형 재료, 예: 네이티브 `190247`), `source_tier`(클라이언트의 등급 번호: `3`은 HC에서 고급 HC, `4`는 고급 HC에서 고급 L4HC, `5`는 L4HC에서 고급 L4HC), `card_quantity`(한 번의 등급 상승이 소비하는 카드 수), 그리고 카드를 지정한 네이티브 세트로 제한하는 선택 사항 `set_ids`를 가집니다. 클라이언트는 카드, 가격, 확률을 지정하지 않으므로 아무것도 가정하지 않으며 카드는 서로 달라야 합니다. 서버는 클라이언트 자체 규칙 엔진이 읽는 형태 그대로 규칙을 실험실 설정에 게시하고 같은 규칙으로 각 요청을 판단합니다. 요청은 네이티브 의상 세트와 완전한 세트의 모든 구성원 Article을 지정해야 하고(불완전한 세트는 거부됨), 모든 구성원은 영구이며 착용 중이 아니어야 하고, 카드는 세트의 현재 등급 상승 상태가 허용하는 규칙과 일치해야 하며, 카드는 같은 트랜잭션에서 차감됩니다. 결과는 세트 행 순서의 첫 구성원에 저장되는 네이티브 등급 상승 속성(HC에서 고급 HC는 ItemAttr `100`, 고급 HC에서 고급 L4HC는 `157`, L4HC에서 고급 L4HC는 `158`)이며 통합 문서의 고정 버프 값을 가집니다. 이후의 등급 상승은 이를 대체하고 강화 시도는 이를 유지합니다. Article의 기존 강화 메타데이터에 저장되므로 마이그레이션이 필요 없습니다. 클라이언트에 이 탭의 실패 표시가 없으므로 등급 상승은 결정적이며, 거부된 요청은 닫힘 결과로 응답하고 아무것도 소비하지 않습니다. 완전한 인벤토리가 응답보다 먼저 게시되며 응답은 세트와 속성을 가진 구성원을 지명합니다. 클라이언트는 모든 구성원의 효과를 합치며 어느 구성원이 속성을 가지는지 밝히지 않으므로, 첫 구성원을 고르는 것은 서버 정책입니다. 네이티브 클라이언트 승인은 아직 대기 중입니다.

## 애용 무기

`BFF_FAVORITE_WEAPON_ENABLED`의 기본값은 `true`입니다. 켜면 `item-enhancement.articles`와 `item-enhancement` 행이 클라이언트의 `Config/FavoriteWeaponSystem.xml`(`favorite.workbook_path`)의 `Base`와 `Upgrade` 시트를 읽습니다. 무기 강화에 성공하면 개정 번호와 재료 차감과 같은 트랜잭션에서 해당 무기에 워크북의 `IncreasePointEnchant` 포인트가 더해지며, 실패한 시도는 포인트를 더하지 않습니다. 포인트는 무기와 카탈로그 범위별 음이 아닌 정수로 저장되고, 등급(Normal, Expert, Special, Master)은 항상 `Upgrade` 기준값으로 포인트에서 계산되며 저장되지 않습니다. 이후 무기의 아이템 표현에는 등급과 포인트를 담은 ItemAttr 164가 포함됩니다. 진행도가 없는 무기에는 항목이 없으며, 외부 인벤토리 쓰기로는 포인트를 만들거나 바꿀 수 없습니다. MySQL에는 마이그레이션 `0047`이 필요하며 SQLite는 schema `13`을 유지합니다. 개조로 속성이 설치되면 설치된 그룹과 같은 트랜잭션에서 해당 등급(S, A, B; 설치된 속성의 첫 번째 범주 0, 1, 2)의 워크북 `IncreasePointModification` 포인트가 무기에 더해지며, 개조를 삭제해도 포인트는 더해지지 않습니다. 강화나 개조로 얻은 포인트가 무기의 등급 기준을 넘으면 인벤토리 갱신 뒤 클라이언트의 등급 채팅 알림(S2C 1548, 플래그 0)이 전송되며, `dialect.messages`의 `favorite_weapon_grade_notices` 옵션은 같은 변수를 따릅니다. 경기 포인트, 감소, 등급 상승 보상 및 등급 하락 알림은 구현되지 않았습니다. 네이티브 클라이언트 검증은 아직 남아 있습니다.

## 선택적 칭호와 메달

`kr-812`와 `kr-1256` 프로필에는 `profiles/bundles/titles.patch.yaml`이 포함되어 있습니다. `BFF_TITLES_ENABLED`의 기본값은 `true`이며, `true`로 설정하면 칭호 행과 메시지 바인딩이 함께 활성화됩니다. 이 행은 빌드에 선언된 칭호 카탈로그 스키마를 사용하여 `Config/BF_title.xml`과 `Config/ShopItem2.xml`을 읽습니다.

이 기능은 메달 조회, 메달을 사용한 칭호 교환, 소유하고 있으며 조건에 맞는 칭호의 장착과 해제를 지원합니다. 소유권은 기존 인벤토리를 사용하고 칭호 선택은 빌드별 장착 설정을 따릅니다. 교환 시 메달 차감과 칭호 지급은 원자적으로 커밋되며, 인벤토리 전송은 일반 Article과 펫 메타데이터를 보존합니다. SQLite와 MySQL은 메달 잔액을 영구 저장하며, 메모리 공급자도 로컬 사용을 위해 동일한 작업을 지원합니다.

경기 자동 메달은 기본적으로 별도 비활성화 상태입니다. `titles` 행에 `round_medals_enabled: true`를 설정하고 비어 있지 않은 `round_medal_rules` 목록을 제공해야 합니다. 각 규칙은 네이티브 `medal_id`, 정확한 `mode_ids`, `metric`, 경계를 포함하는 `minimum`과 선택적 `maximum`, 지급 `count`(기본값 `1`), `minimum_participants`(기본값 `2`, 실제 플레이어만 집계)를 지정합니다. 지표는 `Completed`, `Wins`, `Kills`, `Knockdowns`, `Rescues`, `Score`, `Deaths`, `Stars`입니다. 같은 메달은 하나의 규칙에만 사용할 수 있습니다. `max_round_medal_rules`(기본값 `256`)와 `max_modes_per_round_medal_rule`(기본값 `128`)은 보관하는 정책의 크기를 제한합니다. 기준값과 허용 모드는 명시적인 배포 정책이며, 칭호를 활성화하는 것만으로 과거 지급 규칙이 선택되지는 않습니다.

경기 정책은 서버가 인정한 최종 통계를 사용합니다. 메달, 경기 진행도, 지갑 보상과 경기 영수증은 원자적 경기 메달 정산을 선언한 공급자를 통해 같은 트랜잭션에서 커밋됩니다. Memory, MySQL, SQLite는 모두 이 기능을 구현합니다. 완전히 같은 경기를 다시 정산해도 메달은 중복 지급되지 않습니다. 지급 시 칭호 창을 열지 않으며, 다음 메달 조회에서 현재 잔액을 반환합니다. 예를 들어 다음 패치는 실제 플레이어가 최소 두 명이고 인정된 버블 수가 5~9인 아이템전 경기에서 네이티브 메달 하나를 지급합니다. 기준값은 정책 예시입니다.

```yaml
- set:
    id: titles
    config:
      round_medals_enabled: true
      round_medal_rules:
        - medal_id: 30007
          mode_ids: [3]
          metric: Knockdowns
          minimum: 5
          maximum: 9
          count: 1
          minimum_participants: 2
```

기간 제한 획득에는 서버에 설치된 `acquisition_time_zone`(예: `Asia/Shanghai`)을 명시해야 합니다. 빈 값이면 기간 제한 획득을 허용하지 않습니다. 네이티브 획득 기간은 월, 일, 시, 분을 양 끝 경계까지 포함해 비교하고 연도는 무시합니다(`kr-812 sub_4FE3D0`, `kr-1256 sub_EAE090`). 따라서 현지 시간 기준으로 매년 반복되는 기간이며, 연말을 넘는 구간을 자동으로 순환 처리하지 않습니다. 이 제한은 이미 소유한 칭호의 장착에는 적용되지 않습니다.

네이티브 stock과 stock-set 추가 보상은 같은 상점 워크북에서 해석하며 칭호와 메달 비용에 함께 커밋됩니다. Memory와 MySQL은 독립된 영수증을 보관하므로 칭호가 삭제되거나 만료되어도 추가 보상을 반복 지급하지 않습니다. MySQL에는 마이그레이션 `0046`이 필요합니다. SQLite schema `13`에는 추가 보상 영수증 기능이 없으므로 추가 보상이 있는 칭호 획득만 거부하며, 일반 교환과 메달 조회 및 경기 메달은 계속 지원합니다. 현재 확인한 stock 보상은 영구 또는 일수 지급을 사용하며, 루찌 보상이 포함된 stock-set은 지원하지 않습니다. 네이티브 메달 추가 보상 참조에는 수량 열이 없으므로 `bonus_medal_quantity`로 양의 정수 지급량을 명시해야 합니다. 생략하면 해당 획득은 허용되지 않습니다.

커플 및 챌린지 칭호 획득은 아직 지원하지 않습니다. 커플 관계가 존재한다는 사실만으로 다이아 커플링 조건을 충족하지 않으며, Luxury, Gallery, Honor 조건에는 각 시스템의 권위 있는 게임 상태와 자동 지급 경로가 필요합니다. Favorite 칭호는 kr-1256에서의 예외입니다. `BFF_FAVORITE_TITLES_ENABLED=true`(`BFF_TITLES_ENABLED`와 `BFF_FAVORITE_WEAPON_ENABLED`가 필요하며 기본값은 꺼짐, kr-1256 전용)일 때 계정의 무기 Article 1, 2, 3개가 Favorite 달인 등급이면 칭호 400312, 400313, 400314가 훈장 소모 없이 영구 지급되며, 로그인 시와 Favorite 포인트가 지급될 때마다 확인합니다. 지급 시 인벤토리를 게시한 뒤 칭호 창의 진행도(S2C 933, 조건 6, 현재 값은 요구 값을 넘지 않음)를 보냅니다. 확인 시점에 계정이 다른 쓰기 작업 중이면 이번 확인은 건너뛰며, 칭호는 다음 로그인이나 다음 Favorite 포인트 지급 때 지급됩니다. 훈장으로 이 칭호를 얻는 것은 계속 거부됩니다. 네이티브 클라이언트 검증과 실제 MySQL 환경 검증은 아직 남아 있습니다.

## 선택적 사용자 지정 방 규칙

`kr-1256` 프로필에는 `profiles/bundles/custom-room-rules.patch.yaml`이 포함되어 있습니다. `BFF_CUSTOM_ROOM_RULES_ENABLED`의 기본값은 `true`이며, `true`로 설정하면 `dialect.rooms`와 `ingame`의 `custom_room_rules`가 함께 활성화되고 클라이언트 데이터의 `Config/CustomGameMode.xml`을 사용합니다. 이 번들은 다른 빌드에서 해당 기능을 활성화하지 않습니다.

대기 중인 방의 현재 방장만 옵션을 변경할 수 있습니다. 네이티브 카탈로그는 모드 `1`, `3`, `8`, `11`, `13`, `28`, `30`, `32`, `37`, `38`, `39`에서 허용되는 컨트롤과 값을 제공합니다. 기존 모드의 옵션이므로 각 모드의 별도 게임플레이 기능은 자체 활성화 조건을 따릅니다. 변경 알림보다 먼저 전체 방 설정을 동기화합니다. 새 참가자는 현재 설정을 받고, 방장이 바뀌어도 설정을 유지하며, 모드 변경이나 초기화 시 네이티브 모드 기본값을 복원합니다. 사용자 지정 규칙은 방이 존재하는 동안 유지되며 서버 재시작 후 데이터베이스에서 복원되는 설정은 아닙니다.

`ingame` 행은 `custom_room_rules_max_bytes`(기본값 `8388608`), `custom_room_rules_max_rows`(선택한 시트 전체에서 희소 행 채우기를 포함한 `4096`행), `custom_room_rules_max_columns`(`64`), `custom_room_rules_max_cell_characters`(`8192`)로 워크북 파싱 자원을 제한합니다. 클라이언트 데이터가 없거나 바인딩이 지원되지 않거나 설정이 잘못되면 활성화가 실패합니다. 네이티브 클라이언트 검증은 아직 남아 있습니다.


## 선택적 레거시 과학실

`kr-812` 프로필에는 `profiles/bundles/science-lab.patch.yaml`이 포함됩니다. `BFF_SCIENCE_LAB_ENABLED`의 기본값은 `true`이며 `science-lab` 행과 `dialect.messages.config.legacy_science_lab`를 함께 제어합니다. 이 행에는 공유 인벤토리 바인딩, 클라이언트 카탈로그와 일치하는 인벤토리 범위 `build_key`, 네이티브 `Config/ShopItem2.xml` 및 `Config/SynthesisSystem.ini`가 필요합니다. 현재는 검토된 정확한 `kr-812` 빌드만 허용됩니다. 다른 빌드는 요청 리더, 결과 처리 경로와 재료 자격을 검토한 뒤 허용 데이터를 변경해야 합니다. 이 행은 합성과 분해를 처리하며, 기존 item-enhancement 행이 과학실 설정 요청 처리기를 계속 단독 소유합니다.

합성은 서로 다르고, 조건에 맞으며, 장착하지 않았고 만료되지 않은 기간제 아이템 세 개 또는 완전한 네이티브 세트 세 개를 소모하고 설정에 따라 하나를 남깁니다. 네이티브 세트는 `setId`와 다를 수 있는 `stockSetId`와 순서가 정확히 일치하는 `setCnt`개 구성품을 사용합니다. 세트와 일반 아이템을 혼합한 요청은 거부합니다. 한 세트의 모든 구성품은 같은 수명을 가져야 합니다. 분해는 조건에 맞는 무제한 아이템 하나 또는 완전한 무제한 세트 하나를 소모합니다. 두 작업 모두 설정된 수량형 카드를 차감하고, 선택한 첨가제는 별도의 명시적 수량을 차감합니다. 요청은 메인 메뉴에서만 허용합니다. 누락되거나 변경되었거나 모호하거나 장착되었거나 만료되었거나 지원되지 않는 소유권이 있으면 전체 작업을 커밋하지 않습니다.

다음 `profiles/kr-812/local.patch.yaml` 예시는 합성 전용 배포 정책입니다. 숫자는 예시이며 복원한 네이티브 경제 규칙이 아닙니다. 설치된 `SYNTHESISINFO` 값만으로 서버의 레시피 가격이나 확률을 확정할 수 없습니다. 활성화 전에 실제 사용할 정책을 정해야 합니다.

```yaml
- set:
    id: science-lab
    config:
      enabled: true
      synthesis_card_item_id: 100622
      card_quantity: 1
      synthesis_survivor: first
      synthesis_maximum_days: 729
      synthesis_permanent_at_days: 730
- set:
    id: dialect.messages
    config:
      legacy_science_lab: true
```

`card_quantity`는 설정한 레시피에서 공통으로 차감하는 양의 정수 카드 수량입니다. `synthesis_survivor`는 `first` 또는 `uniform`이어야 합니다. 합성은 소수 부분을 포함한 정확한 남은 일수를 합산하고, 네이티브 무제한 표시 기준인 730일보다 작은 `synthesis_maximum_days`를 상한으로 적용합니다. 합계가 그보다 높은 `synthesis_permanent_at_days`에 도달하면 무제한 소유권으로 전환합니다. 무제한 입력도 무제한 결과를 만듭니다. 암묵적인 경제 기본값으로 활성화되는 합성 카드나 분해 레시피는 없습니다.

선택적 `decomposition` 항목에는 `card_item_id`(이 네이티브 카탈로그에서는 `100623` 또는 `100656`), `category`(`0` 액세서리, `1` 의상/세트, `2` 무기), 비어 있지 않은 `rewards` 배열이 들어갑니다. 각 보상에는 네이티브 `stock_id`, 고유 `item_id`, `kind`(`Count` 또는 `Days`), 양의 정수 `amount`, `maximum`, 양의 정수 `weight`가 필요합니다. `Stock` 행은 같은 아이템을 가리켜야 하며 `duration`은 이번에 지급하는 수량 또는 일수와 정확히 같아야 합니다. 클라이언트는 누적 인벤토리 소유량이 아닌 해당 상품 규격을 표시합니다. 판매 중이 아닌 Stock 행도 보상을 나타낼 수 있습니다. 소수 일수의 Stock 보상은 거부하지만 합성 주 결과의 수명은 소수를 계속 유지합니다. 무제한 분해 및 첨가제 보상은 지원하지 않습니다. 네이티브 결과 포맷터는 `Stock.duration: -1`을 무제한으로 처리하지 않으며, 이 카탈로그에는 무제한 소유권을 표시하는 것으로 검토된 Stock 규격이 없습니다. 합성 주 결과의 무제한 전환은 별도의 지원 경로를 사용합니다. 조건은 네이티브 카탈로그와 일치해야 하며 가중치 합계는 부호 있는 32비트 추출 범위 안에 있어야 합니다. 분해마다 보상 하나를 선택합니다.

`permanent_additive_item_id`(`100624`)에는 `permanent_additive_quantity`와 `permanent_additive_basis_points`(`0..10000`)가 필요합니다. 확률이 10000보다 작으면 위 보상 형식의 `permanent_failure_reward`도 필요합니다. 아직 무제한으로 전환되지 않은 합성에서만 이 첨가제를 허용합니다. `bonus_additive_item_id`(`100655`)에는 `bonus_additive_quantity`와 `bonus_reward`가 필요합니다. 첨가제 ID와 작업/효과 역할은 네이티브 `ASSISTINFO`와 대조하며, ID가 0이면 비활성화합니다. 허용되는 레시피 안에서 보상 ID는 충돌할 수 없습니다.

자원 예산은 검증되는 배포 필드입니다. `max_workbook_bytes`는 네이티브 소스당 기본 `134217728`바이트, `max_catalog_rows`는 `65536`, `max_catalog_columns`는 `256`, `max_cell_characters`는 `16384`, `max_in_flight_accounts`는 `128`, `max_decomposition_recipes`는 `64`, `max_rewards_per_recipe`는 `128`입니다. 모두 양의 정수이며 배포에 맞게 높일 수 있습니다. 열 제한은 비어 있지 않은 값에 적용됩니다. 네이티브 표 끝의 서식만 있는 빈 셀은 희소 채움 공간을 할당하지 않지만 인덱스는 계속 증가해야 합니다. 인벤토리 용량과 네이티브 선택/프레임 제한은 별도로 적용됩니다.

Memory, SQLite, MySQL은 하나의 소모 및 지급 트랜잭션을 사용하여 무관한 소유권, 남길 아이템의 메타데이터, 일관된 가방 미러와 슬롯 할당 상한을 보존합니다. 일반 Article 및 펫 준비는 새 보상 행이 만들어진 뒤 실행되며 함께 커밋됩니다. 전체 인벤토리를 결과보다 먼저 전송합니다. 소수 수명은 절대 타임스탬프로 저장하고, 합성 주 결과 일수에는 클라이언트와 동일한 전체 인벤토리 세션 기준 시각을 사용합니다. 결과 전송 시 새로 시작하는 카운트다운이 아닙니다. 분해 및 추가 보상 결과에는 설정한 Stock ID를 보내며 수량과 기간은 클라이언트 `Stock` 테이블에서 읽습니다. 커밋 후 전송 실패는 소유권을 되돌리지 않으며 인벤토리 전송 없이 성공 결과를 알리지 않습니다.

네이티브 선행 문자열은 2차 비밀번호입니다(`kr-812 sub_9E29F0`, `kr-812 sub_4F8A20`). 검증된 비밀번호 확인 서비스가 없으므로 비어 있지 않은 비밀번호와 0이 아닌 진단 요청 경로를 거부합니다. 별도 무기 진화는 지원하지 않습니다. `gspEvolveResult` 경로는 펫에 속하며 독립적인 무기 요청/결과 흐름은 아직 확정되지 않았습니다. 네이티브 게임플레이/UI 검증과 실제 MySQL 과학실 검증은 남아 있으며 자동 프로토콜 및 영속성 검사는 이를 대신하지 않습니다.
