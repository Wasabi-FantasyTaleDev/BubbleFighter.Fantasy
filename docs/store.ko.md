# 스토어 관리 {#store-management}

스토어는 서버 패키지 배포를 위한 관리 인터페이스입니다. 구성된 카탈로그 소스를 탐색하고, GitHub 릴리스 메타데이터를 미리 보고, 서버 패키지를 검증된 스테이징 영역으로 다운로드합니다. 이 페이지의 모든 기능은 관리자 세션으로 보호됩니다. WebUI(또는 `POST /api/auth/login`)로 로그인하면 모든 스토어 요청에 해당 세션 쿠키가 필요합니다. 스토어는 **스테이징만 수행합니다**: 어떤 스토어 작업도 아카이브를 추출하거나, 플러그인을 로드하거나, 애플리케이션 경로를 교체하지 않습니다. 완료된 다운로드는 검증된 파일 목록이지 설치된 플러그인이 아닙니다.

스토어는 핵심 번들에 포함되어 있습니다(`distribution.sources`, `distribution.plans`, `distribution.packages`, `distribution.jobs` 행). `kr-812`, `management`, `all` 프로필이 이들을 포함합니다. 스테이징은 기본적으로 `data/distribution-staging` 아래에 만들어지며 단독 소유자 잠금으로 보호됩니다. 기록 페이지는 기본 20개 항목이고, 여유 공간 예약은 기본 0입니다. 소스는 `data/distribution-sources.json`에 저장됩니다. `state_path`를 비워 두면 소스 목록이 읽기 전용이 됩니다.

## 소스 {#sources}

소스 카드는 구성된 카탈로그 소스를 운영자가 정한 순서로 나열하며, 순서가 중요합니다. 카탈로그를 제공하는 첫 번째 소스가 기본 선택됩니다. 각 행은 ID, 표시 이름, 종류(`http`, `alist`, `github`), 루트 URL, 카탈로그 경로를 가집니다. URL에는 자격 증명, 쿼리, 조각이 없어야 하며 루트는 `/`로 끝나야 합니다. 행을 위아래로 옮기고 추가·삭제한 뒤 전체 목록을 한 번에 저장합니다.

저장은 낙관적 개정을 사용합니다. 편집기는 열 때 설정 개정을 기록하고 저장 시 함께 보냅니다. 그 사이 다른 관리자가 저장했다면 `source_revision_conflict`로 거부되며 대화 상자가 열린 채 유지되어 내용을 확인하고 다시 적용할 수 있습니다.

## GitHub 미러 {#github-mirror}

GitHub 접속이 느리거나 제한된 곳에서는 스토어가 공개 URL 접두사 미러를 통해 GitHub 릴리스 첨부 파일과 압축 파일을 내려받을 수 있습니다. **소스 관리**를 열고 **GitHub 미러 가속**을 켜세요. **자동**을 선택하면 다운로드할 때마다 모든 미러를 측정해 가장 빠른 사용 가능한 미러부터 시도하며, **속도 테스트** 후 특정 미러를 고를 수도 있습니다. GitHub 자체는 항상 마지막 경로입니다. 미러를 거치는 것은 파일 내용뿐입니다. 릴리스 정보와 카탈로그는 항상 GitHub에서 직접 읽고, 미러로 받은 모든 바이트는 GitHub가 공개한 크기와 SHA-256과 대조하므로 미러는 다운로드를 실패시킬 수는 있어도 설치되는 내용을 바꿀 수는 없습니다.

서버는 자신의 주소를 한 번 확인합니다. 중국 본토에 있으면 WebUI를 처음 연 관리자에게 미러를 켤지 묻습니다. 이 대화 상자는 한 번만 표시되며 확인하기 전에는 아무것도 바뀌지 않습니다. 미러 목록, 측정용 파일과 측정 한도는 `data/github-mirrors.json`(`distribution.sources` 행의 `github_mirrors_path`, 비우면 기능이 꺼짐)에 있고, 스위치·선택한 미러·위치 확인 결과는 `github_mirror_state_path`에 저장됩니다.

## 카탈로그 탐색 {#browsing}

카탈로그 페이지는 모든 소스의 패키지를 패키지 식별별로 중복 제거한 하나의 병합 카드 목록으로 표시합니다. 필터로 전체 소스 또는 하나의 소스를 선택할 수 있고, 새로 고침은 모든 카탈로그(또는 한 소스의)를 다시 읽습니다. 실패한 소스는 조용히 사라지지 않습니다. 실패 원인(`source_timeout`, `source_unavailable`, `catalog_invalid`)이 카드 위에 나열되고 건강한 소스는 그대로 표시됩니다.

한 카탈로그에 같은 패키지의 여러 릴리스가 나타나면 게시자의 가장 높은 `revision`이 이깁니다. 동륄이거나 여러 릴리스 그룹의 개정이 모두 unset이면 추측이 아니라 구성 오류입니다. 클라이언트 대상 패키지는 보이지만 서버 대상만 다운로드할 수 있습니다. 선택하면 "클라이언트 플러그인은 미리 보기만 제공됩니다"라고 표시됩니다.

## GitHub 저장소 {#github-repositories}

GitHub 소스는 저장소에서 카탈로그 문서를 읽습니다. 저장소 릴리스 양식은 저장소의 최신 안정 릴리스(또는 지정된 태그)와 그 첨부 파일을 미리 봅니다. 초안과 사전 릴리스는 거부되고, 모든 자산 URL은 요청된 저장소와 태그에 속해야 하며, GitHub가 `sha256:` 다이제스트를 게시하는 경우에만 첨부 파일이 게시자 SHA-256을 가집니다. 미리 보기는 메타데이터일 뿐이며 이 호출로는 아무것도 다운로드되지 않습니다.

`github_repository`와 `github_tag` 필드는 카탈로그 schema 3에 속합니다. 서버와 런처의 엄격한 카탈로그 판독기 모두에서 동작하지만, 이는 잠정적인 조율용 형식이지 공개된 공유 계약이 아닙니다. 런처 릴리스와 형식을 합의하기 전에는 프로덕션 카탈로그를 schema 3으로 다시 게시하지 마세요. 저장소 첨부 파일은 해당 게시자 다이제스트를 가질 때만 다운로드할 수 있습니다. 그렇지 않으면 다운로드가 수행하는 바이트 단위 검증이 비교할 대상이 없으므로 다운로드 버튼이 비활성화됩니다.

## 스테이징으로 다운로드 {#staging}

서버 패키지 다운로드는 세 단계 흐름이며 각 단계는 표시된 내용을 그대로 고정합니다.

1. 카드에서 **다운로드 공급을 선택**합니다. 각 공급은 선택 지문(구성된 소스와 정확한 공급 내용에 대한 SHA-256)과 이를 읽어 온 카탈로그 바이트의 SHA-256을 가집니다.
2. 다운로드를 **계획**합니다. 계획은 이 고정들에 대해 소스, 카탈로그, 릴리스, 첨부 파일을 다시 검증합니다. 소스나 공급이 바뀌면 다른 것을 다운로드하는 대신 `distribution_source_changed` 또는 `distribution_selection_changed`로 거부됩니다.
3. 작업을 **접수**합니다. 작업은 스트리밍하는 동안 모든 파일의 크기와 SHA-256을 검증하고, 데이터 블록을 스테이징 루트 아래에 불투명하게 보관하며, 단계를 보고합니다(`preparing`, `transferring`, `staged`). 다운로드 패널은 진행률을 폴링하고, 스테이징된 작업의 전체 재독립 검증을 요청하고, 진행 중인 작업을 취소하고, 종료된 작업과 그 스테이징을 삭제합니다.

검증 통과는 그 순간 스테이징 볼륨에 무엇이 있었는지를 말할 뿐입니다. 설치 권한을 부여하지 않으며, 이후 디스크 변화는 신뢰하는 것이 아니라 다시 검증으로 발견됩니다.

## 클라이언트 정책 {#client-plugin-policy}

런처가 반드시 사용해야 하거나, 사용할 수 있거나, 사용하면 안 되는 플러그인을 정하는 클라이언트 정책은 설치된 서버의 WebUI에서 편집합니다. 저장에는 관리자 세션 외에 `webui.settings.client_policy` 권한이 필요하며 저장 후 구성 적용이 다시 실행됩니다. 이 규칙은 호환 런처를 구성할 뿐입니다. 클라이언트 바이너리는 서버에 설치되지 않으며 이 규칙이 클라이언트 무결성을 증명하지 않습니다. 관리 API는 [클라이언트 정책](plugins.ko.md#client-plugin-policy), 규칙 유형은 [런처 문서](launcher.ko.md#client-policy)를 참조하세요.

## 관리 API {#administration-api}

WebUI가 호출하는 엔드포인트는 운영자 스크립트가 사용하는 것과 같습니다. 아래 모든 경로는 관리자 세션 쿠키가 필요하고, GET이 아닌 요청에는 동일 출처의 `Origin`과 함께 `X-BFF-Request: 1` 헤더도 필요합니다.

| 방식과 경로 | 용도 |
| --- | --- |
| `GET/PUT /api/distribution/v1/sources` | 소스 목록을 개정과 함께 읽거나 교체합니다. |
| `POST /api/distribution/v1/repository-release` | GitHub 릴리스 하나를 미리 봅니다(메타데이터만). |
| `GET /api/distribution/v1/catalog?sourceId=` | 병합된 카탈로그 스냅숏 또는 한 소스의 목록. |
| `POST /api/distribution/v1/plans` · `/validate` · `DELETE` | 선택을 고정하고, 다시 확인하고, 해제합니다. |
| `POST /api/distribution/v1/plans/{id}/files` | 매니페스트를 검증하고 페이로드 파일을 나열합니다. |
| `GET/POST /api/distribution/v1/jobs` · `GET /{id}` | 기록 페이지와 접수(202, `Location` 헤더 포함). |
| `POST /api/distribution/v1/jobs/{id}/cancel` · `/verify` · `DELETE` | 취소, 스테이징 재독립 검증, 또는 종료된 작업 제거. |

안정적인 오류 코드(`source_revision_conflict`, `distribution_selection_changed`, `distribution_job_not_staged`, `repository_rate_limited` 등)가 실패 원인을 알려 줍니다. HTTP 상태는 잘못된 요청(400), 오래된 고정(409), 업스트림 문제(502/504), 저장소나 구성 문제(503)를 구분합니다.

## 스토어가 하지 않는 것 {#limits}

- 설치와 활성화가 없습니다. 어떤 라우트도 아무것도 추출, 로드, 재시작하지 않습니다. 다운로드는 설치가 아니며, 저장된 의도가 실행 중인 기능은 아닙니다.
- GitHub 미러는 작동하는 척하는 대신 의도적으로 실패합니다.
- 교차 출처 매니페스트 참조는 거부됩니다("아직 지원되지 않음").
- 런처는 아직 이 중 아무것도 소비하지 않습니다. 스토어 카탈로그를 읽지 않으며, 다운로드 엔진이 나오기 전까지 클라이언트 프리셋은 광고 데이터일 뿐입니다.
